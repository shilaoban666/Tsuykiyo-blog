## 一、开场问题：模型没变，为什么上线就变笨

在笔记本里跑演示时，Agent 看起来很能干：读文件、改代码、跑测试、根据报错继续修。搬到生产环境后，同一套提示词、同一个模型，却开始出各种低级问题——文件写到了错误的目录，工具报错后原地重试十几次，长任务跑到一半上下文被截断，出了事故连当时喂给模型什么都查不到。团队的第一反应通常是换更强的模型，换完仍然时好时坏。

差别不在模型，而在模型外面那层东西。演示阶段，开发者本人充当了运行时：帮忙确认路径、判断报错、决定重试、在越界时喊停。生产阶段没有人盯着，这些判断必须由代码承担。承担这些判断的那层代码，就是本文要讨论的 harness。理解它的价值，等于理解“模型会说话”与“系统能干活”之间那段经常被忽略的距离。

这段距离可以用一句话概括：演示时所有模糊判断都有人兜底，上线后所有模糊判断都变成事故。harness 的工作不是把这些判断做得更聪明，而是把它们变成确定的、可检查的、可回放的规则。

## 二、概念界定：运行骨架，不是框架

本文把 harness 定义为：承载模型、工具、上下文、权限与评测的运行骨架。这个定义里有五个被承载的对象，和一个关键词——骨架。骨架不产生智能，它决定智能能否被安全、稳定、可重复地调用。同一个模型换一套骨架，表现可以差出一个档次，原因就在这里。

骨架通常包含六个部分。提示装配负责把系统规则、任务说明、检索证据与历史观察组织成每轮的输入；工具网关负责注册、校验、执行与限流；循环控制负责步数、终止、重试与熔断；状态管理负责事件日志与检查点；权限沙箱负责文件、网络、进程的边界；可观测性负责把决策输入、候选动作与结果挂到同一条轨迹上。

六者的接口关系可以这样理解：循环控制是主干，每一轮向提示装配索取上下文，向工具网关请求执行动作，向状态管理读写检查点，向权限沙箱申请临时能力，向可观测性上报事件。任何两个组件之间直接耦合，都会让替换与测试变难。例如让提示装配直接调用工具，看似省了一层，实际把权限检查与错误处理绕过去了。

harness 与框架、SDK、编排器的边界也常被混淆。框架提供抽象，例如链、图、代理类；SDK 封装模型与工具的调用细节；编排器描述多步骤或多代理的流程。它们都可能包含一部分运行时能力，但 harness 的独特职责是运行期约束与故障处理：超时、重试、预算、隔离、审计。一个项目可以用框架搭 harness，也可以完全不用框架；反过来，只引入框架而不设计约束，得到的通常是一个能跑的演示，而不是一个能值班的系统。

判断一个项目有没有 harness，有个笨办法：把模型换成一个只会返回固定动作的桩，系统还能不能正常跑完流程、拦住越权、记录轨迹、在失败时给出结构化结果。能，说明约束在代码里；不能，说明约束其实寄生在模型的理解力上。

## 三、机制拆解：一轮请求的生命周期

把一轮请求拆开，harness 的职责就具体了。下面是一段示意伪代码，省略了具体存储与协议。

```python
def run_turn(run, tool_call):
    ctx = assembler.build(run.goal, run.state, budget=run.remaining_tokens)
    ability = sandbox.request(run.tenant, tool_call.name, tool_call.args)
    if not ability.allowed:
        return observe(run, error="permission_denied", retryable=False)
    if not limiter.acquire(run.tenant, tool_call.name):
        return observe(run, error="rate_limited", retryable=True, after=2)
    try:
        result = gateway.call(tool_call, timeout=ability.timeout,
                              idempotency_key=run.key_for(tool_call))
    except ToolError as e:
        result = normalize(e)          # 统一成 {code, message, retryable}
    run.state.append(event(tool_call, result, ctx.hash))
    tracer.emit(run.id, ctx, tool_call, result)
    return result
```

这段代码体现三个原则。第一，权限判断发生在执行之前，而不是在执行失败后补救；拒绝也要作为一条观察返回，让模型知道此路不通，而不是让它反复尝试。第二，所有工具错误被归一化成同一结构，带错误码与是否可重试，模型才能做出下一步决策。第三，每次调用都落事件并上报轨迹，事件里带上下文哈希，事后可以还原“模型当时看到了什么”。

反过来，用失败模式可以反推每一层的需求。工具被误用，问题多半在网关的 schema 与描述，而不是模型笨；循环停不下来，问题在循环控制缺少预算与重复动作检测；上下文溢出，问题在装配层没有配额与压缩；越权操作，问题在沙箱把边界交给了提示词。把故障归到具体层，修复才有方向，而不是一遍遍重写系统提示。

这张失败模式表还有第二个用途：它是一份验收清单。上线前逐条问“这类故障如果发生，会被哪一层拦住”，答不上来的那一层就是缺口。多数事故不是没有约束，而是约束被放在了错误的层——例如把路径校验写在工具实现里，工具一换就失效。

## 四、工程取舍与反例

第一个取舍是薄与厚。薄 harness 只做循环与工具转发，把约束交给上层业务；厚 harness 内置预算、审批、回放与多租户。薄的好处是起步快、侵入小，坏处是每个业务都要重复实现一遍安全逻辑；厚的好处是统一治理，坏处是抽象一旦泄漏，排查会变得非常绕。可行的路径是先薄后厚：把权限、预算、轨迹三件最难事后补的东西先做进去，其余按需扩展。

第二个取舍是同步与异步。交互式任务需要流式返回与快速中断，长任务需要后台队列与检查点。两者共用一套循环控制，但超时、重试与恢复语义不同。把交互式循环直接改造成长任务队列，通常会留下“进程重启后任务丢失”的隐患。

常见反例有四类。其一是“胶水 harness”，一堆 if/else 直接写在业务处理函数里，没有统一的事件模型，换一个工具就要改一遍主流程。其二是“提示词权限”，系统提示写“不要删除文件”，但沙箱仍以全权限运行，模型一旦被注入诱导就绕过约束。其三是“日志即答案”，只记录最终输出，不记录中间观察，故障无法复现。其四是“无幂等重试”，超时后自动重试写操作，导致重复下单或重复发信。

还有一个容易忽视的反例：把评测排除在 harness 之外。评测不是上线前跑一次的脚本，而是运行骨架的一部分——它决定灰度时如何采样、失败如何回流、版本如何对比。如果 harness 不能稳定重放一次运行，任何评测结论都只是一次性的。换句话说，可重放性不是调试便利，而是 harness 是否成立的底线。

## 五、工程案例：一次“测试通过、PR 里却没有改动”的事故

背景示意：一个代码维护 Agent 跑在 CI 里，任务是修复仓库里的 lint 报错并提交 PR。它用的是相当完整的框架，模型也不弱。

输入：一个仓库快照，任务说明三条——只改 `src/` 下的文件、不修改导出签名、修复后必须跑通 lint 与单测。

失败轨迹（示意）：沙箱把“工作目录白名单”配成了仓库拷贝路径，但 Agent 的补丁实际写到了挂载进来的原始工作区；测试跑在拷贝路径上，读到的是未修改的代码，于是“lint 通过、单测通过”被如实报告；循环控制只有 max_steps=30 而没有无进展检测，Agent 在同一个 lint 规则上反复修改同一个文件 17 次；装配层没有给系统约束预留配额，第 6 步时就触发窗口截断，最早的任务说明被压缩掉，导出签名在下一次修改中被改掉；观测只记录了最终结论。结果是 PR 里 0 处改动却被标记成功，另外两个下游仓库因为导出签名变化编译失败。

按层拆开看，四个缺陷各归一层：路径解析属于沙箱（边界用字符串前缀匹配而不是真实路径校验）；重复劳动属于循环控制（缺无进展熔断）；约束丢失属于装配（系统规则与可压缩的观察共用同一预算）；事后无法解释属于观测（只存输出不存输入）。

处理也是按层做的。沙箱层把可写根收敛为“工作区即唯一根”，路径在网关侧做真实路径解析与越界校验，越界返回 permission_denied 而不是让工具自己判断；测试与写操作改用同一个挂载，避免读写分裂。循环控制层加无进展检测：连续两次补丁哈希相同即熔断，预算从 30 步降到 12 步并加 10 分钟墙钟上限。装配层给系统约束留保底配额（示意 800 token），压缩只作用于观察历史，且压缩事件本身要落日志。观测层改为每步记录 prompt 哈希、工具调用、diff 摘要，支持按 run_id 重放。最后把完成条件从“模型说好了”改成代码判定：lint 全绿、diff 非空、导出签名哈希未变。

结果（示意）：同类任务 40 次，误报成功 0 次，平均步数 7.3（原 14.8），上下文溢出 0 次，其中 6 次因触碰导出签名被拒绝并转人工。没有任何一处改动依赖换模型。

这起事故的教训是：四个缺陷里没有一个属于“模型不够聪明”。它们分别是路径、循环、配额与记录，都是可以在没有模型参与的情况下被检查出来的东西。

## 六、从 Demo 到生产还差什么

Demo 与生产之间通常隔着四件事，每一件都属于 harness，而不属于模型。

一是从“进程内的循环”到“可中断可恢复的任务”。Demo 里循环跑在一个函数调用栈里，重启即丢失；生产需要检查点，恢复时不能重复已完成的写操作。

二是从“一个人的凭据”到“多租户的配额与审计”。Demo 用开发者的 key 跑通即可；生产要按租户隔离配额、密钥与日志，还要能回答“这条记录是谁触发的”。

三是从“我看日志”到“轨迹可重放”。Demo 出问题可以问开发者当时怎么回事；生产只能靠记录还原，缺了装配后的上下文，复盘就是猜。

四是从“出错重跑”到“幂等与补偿”。Demo 里重跑没有代价；生产里重试可能是一次重复扣款，不可重试的写操作必须有补偿或转人工路径。

## 七、落地检查清单

1. **依赖方向单向**：装配、网关、状态、沙箱、观测之间不互相直连，全部经主干调度；代码里能查出反向依赖。
2. **权限先于执行**：每次工具调用先过沙箱判定，拒绝也返回结构化观察，且拒绝原因可统计。
3. **错误归一在网关**：业务代码见不到原始异常，所有错误映射为固定错误码加 retryable 与 hint。
4. **四闸与熔断齐全**：步数、token、墙钟、成本四项上限，加连续无进展熔断，任一触发返回结构化未完成。
5. **事件只追加可重放**：同一 run_id 的事件序列可重放，重放得到的上下文哈希与原始一致。
6. **检查点不重复副作用**：进程重启后从最近检查点恢复，已完成写操作不重复执行（幂等键或进度标记）。
7. **超时分层收紧**：连接超时 < 工具超时 < 步骤超时 < 任务超时，外层永远大于内层。
8. **租户隔离到资源**：配额、密钥、日志按租户分区，跨租户数据在接口层即不可见。
9. **轨迹含决策输入**：记录装配后的上下文哈希与候选动作，而不只是最终输出与耗时。
10. **版本可对比**：新旧 harness 版本能按比例采样对比，历史运行能用相同输入重跑。

## 八、常见误区与面试追问

**追问一：我们已经用了某个 Agent 框架，是不是就等于有 harness 了？**

答：框架给的是抽象与调用便利，harness 要的是运行期约束。框架通常不管幂等、超时分层、租户配额与可重放。能跑通流程不等于能值班，这两件事的验收标准不一样。

**追问二：提示词里已经写清楚“不要删除文件”，为什么还要沙箱？**

答：因为提示词是建议，沙箱是强制。模型可能被注入诱导、可能理解偏差、可能在长上下文里忘掉约束。只要约束能被自然语言绕过，它就不是边界。

**追问三：重试是标准工程实践，为什么说写操作不能随便重试？**

答：读操作重试是幂等的，写操作重试是重复副作用。区别不在重试次数，而在有没有幂等键、以及工具是否被标注为不可重试。把这两类混在一个重试策略里，迟早会重复扣款或重复发信。

**追问四：harness 做厚了，会不会拖慢迭代？**

答：会，所以顺序很重要。先做权限、预算、轨迹三件最难事后补的，其余按需扩展。反过来先做审批流与多租户，通常会把还在探索期的产品拖死。

**追问五：可重放真的那么重要？出了问题看日志不行吗？**

答：日志记录结果，重放记录输入。复盘时需要知道“模型当时看到了什么才做出那个决定”，只有结果日志回答不了。而且没有重放，评测结论也无法跨版本比较。

## 九、小结与延伸阅读

harness 是把模型能力转化为系统可靠性的那层契约。它的六个组件围绕一个目标：让每一次决策都有边界、可观察、可恢复。它的价值不在让模型更聪明，而在让系统在模型不聪明时仍然安全。判断一个团队是否真的在做 harness，看三件事就够了：权限是否由运行时强制、失败是否有结构化语义、运行是否可重放。

延伸阅读建议：官方文档类可看主流 Agent 平台的运行时与沙箱说明；工程博客类可看各框架如何组织循环、工具与轨迹；论文类可关注 agent 系统评测中对可复现性的讨论。阅读时把“故障落在哪一层”作为主线，比记住组件清单更有用。
