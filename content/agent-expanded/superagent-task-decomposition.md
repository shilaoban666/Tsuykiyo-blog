## 一、开场问题：为什么子代理总在“各做各的”

一个常见的场景：Superagent 接到“把这份季度经营分析整理成给管理层的简报”。它很自然地拆成三件事——拉数据、写分析、做排版，分别派给三个子代理。两小时后收回来三份东西：拉数据的给了一张宽表，写分析的写了一段没有数字支撑的判断，做排版的把两者拼在一起，格式很漂亮，结论却对不上。复盘时发现，不是子代理能力不行，而是派发时没人说清“交给你的输入是什么、要交出什么、凭什么算完成”。

这类失败几乎都能追到同一个根上：分解只分了“动作”，没有分“契约”。本文要回答的是，任务怎么切、切完怎么派、派完怎么收，才能让多个执行者的产出拼回一个整体。

值得注意的是，这类失败在单代理时被掩盖了。一个 Agent 自己做完全程，中间状态留在同一个上下文里，“口径”这种隐含假设自然一致；一旦切开，隐含假设就变成了必须显式传递的信息，而多数团队的第一版派发只传了目标，没传假设。

## 二、概念界定：三元组与两种失败

先给判据。一个子任务是否“可独立描述”，看它能否写成“输入—输出—验收”三元组：输入是执行者开始工作时必须拿到的事实与约束；输出是它可以交付的、结构稳定的产物；验收是一组可检查的断言，说明什么样的输出算合格。三者都能写清，才适合派发；有一项写不清，就说明这块还没想明白，应该留在上层继续分解，或者由派发者自己完成。

这个判据的价值在于它可反驳。你写不出验收断言，通常不是“还没想好怎么写”，而是“这块本身没有明确的正确性标准”，那就该由人负责，而不是派给一个无法被验收的执行者。

粒度由耦合度决定，而不是由字数决定。两个步骤如果共享大量中间状态、需要反复互相确认，它们就该在同一个执行者手里；如果彼此只通过一份明确的产物交接，就可以切开。切得太细，协调次数上升，每次交接都要重新构造上下文，成本会超过并行带来的收益；切得太粗，单个子代理的上下文被塞满，注意力被稀释，产出质量下降。

由此有两种典型失败。一种是“碎切”：把任务切成十几个微步骤，每个子代理只看到一小片，最后没人对整体负责，合并阶段变成第二次开发。另一种是“整包”：名义上派了子代理，实际上把整个任务原样转交，子代理面对的和 Superagent 一样的复杂度，派发没有产生任何分工收益。两种失败看似相反，根因相同——都没有回答“这个子任务凭什么可以独立交付”。

## 三、机制拆解：派发契约五要素

派发契约至少包含五项：目标、上下文、可用工具、预算、截止条件。缺一项，子代理就会用自己的默认值填补，而默认值往往与上层预期不同。

```yaml
task:
  id: t-analyze-q3
  goal: "产出 Q3 经营分析的关键结论，每条结论必须附指标与口径"
  inputs:
    - ref: "artifact://q3-finance-wide-table"
    - constraint: "口径以财务月报为准，不采用业务侧口头数据"
  output_schema:
    type: object
    required: [findings, evidence, open_questions]
  tools: [query_metrics, read_doc, compute_ratio]
  budget: {tokens: 60000, wall_clock_min: 12, cost_cny: 3.0}
  deadline: "2026-11-13T18:00:00+08:00"
  acceptance:
    - "每条结论至少引用一个指标 ID"
    - "比率类结论标注分子分母口径"
  on_fail: return_to_parent
```

这段配置里，最容易被省略的是 acceptance 与 on_fail。前者决定收回来的东西能不能直接用，后者决定失败时是重试、降级还是升级。把它们写进契约，等于在派发前就把验收标准谈好，而不是等产出回来再争论。

契约里还有一类隐性内容：默认值。预算里没说并发上限，子代理可能开八个并行查询；没写“不得修改源数据”，它可能顺手清洗了宽表。稳妥的做法是把最容易被误判的默认值写成显式的 deny 列表，而不是指望模型从不越界。

回收阶段要做三件事：结构化物化、冲突消解、部分成功上报。结构化物化是指子代理必须按 output_schema 交付，而不是一段自由文本；这样合并时可以程序化校验，也便于把证据挂到具体结论上。冲突消解是指两个子代理给出矛盾结论时，不能简单取其一，要回到证据层比对来源、时间与口径。部分成功上报是指允许子任务只完成一部分，但必须显式标注完成了哪些、缺哪些、为什么缺，让上层决定是否继续。

合并本身也有策略。常见的有三种：拼接，适合彼此独立的产物；归并，适合同一维度的多个候选，需要去重与排序；仲裁，适合结论冲突，需要第三方证据或更高权限的判断。选错策略的典型症状是“拼接了本该仲裁的结论”，最后文档里同时存在两个互相矛盾的判断。

还有一个容易漏掉的环节是“交接物的版本”。子任务产出后如果又被上层修改，后续依赖它的子任务必须知道用的是哪一版。稳妥的做法是给每份产物一个内容摘要，派发时写明依赖的具体版本，产物更新则让依赖方重跑或显式确认。否则会出现“下游按旧版结论继续做，上游早已改口”的隐性错误，而这种错误在最终文档里几乎看不出来，只能靠版本记录回溯。

## 四、工程取舍与反例

第一个取舍是派发深度。允许子代理再派发，系统的组织能力更强，但预算、责任与可观测性都会变复杂。稳妥的做法是限制最大深度，并要求每一层都能独立验收，不能把验收责任一路下推到底层。

第二个取舍是上下文给多少。给全量上下文，子代理理解更充分，但 token 成本高且容易把无关信息带进判断；给切片，成本低但可能缺失关键前提。折中的做法是给“任务必需 + 可回查入口”：必需的事实直接给，其余以引用形式给出，子代理需要时再取。

第三个取舍是并行与依赖。能并行的子任务应该并行，但并行会带来重复查询与配额争抢。派发前做一次依赖分析，把共享的前置查询提到上层执行一次，再把结果分发给各子任务，通常比每个子代理各查一遍更划算。

反例方面，最常见的是“契约缺验收”：派发时只写了目标，收回时才发现产出不可用，只能返工。其次是“上下文倒灌”：把整份全局状态塞给每个子代理，子代理看到了与自己无关的冲突信息，反而不敢下结论。第三是“回收不看证据”：只读子代理的总结，不看它引用的原始数据，验收变成走过场。

## 五、工程案例：一个多代理的季度经营分析场景

把开头那个失败的季报场景重做一遍（示意），能看清每一条判据落在哪里。

输入：一份集团财务宽表、一封管理层对上一版简报的批注、一条硬约束“口径以财务月报为准”。目标产物是六页简报，每条结论必须能追到指标。

冲突一：口径错位。数据子代理拿到的宽表是集团口径，分析子代理按事业部口径写结论，两者对不上。处理是把“口径”从背景描述升级为硬约束，并把输入的引用改成物化产物加口径声明字段；分析子任务在启动时先校验产物的口径字段，不匹配直接失败，而不是猜。

冲突二：输出是自由文本。分析子代理交回一篇两千字的文章，成稿阶段只能人工摘。处理是要求按 output_schema 交出 findings 数组，每条含 metric_id、value、caveat；成稿子任务改成按字段渲染，标题与图表由程序生成，人只润色判断句。

冲突三：版本错配。图表用的是第二版数据，成稿引用的是第一版结论，最终稿里出现了两个不同的同比数字。处理是给每份产物加内容摘要，依赖里写明版本；上游更新后，下游被标记为 stale 并触发重跑，成稿阶段拒绝拼接 stale 产物。

冲突四：部分成功被掩盖。图表子代理有两个事业部缺数据，仍然交出了完整的图，只是图例里悄悄少了两项。处理是部分成功必须显式声明 missing 数组与原因，成稿时必须显示缺口；宁可留白并标注，不接受静默省略。

结果：交付从两天缩到一天，返工从三轮降到一轮，代价是前期要花时间建模 output_schema，以及上游数据每变一次就要触发一次下游重跑。后者用 stale 标记加增量重跑控制，不是靠要求上游“别改”。

## 六、边界与失败模式

分解假设目标是稳定的。目标在过程中被修改（管理层新增一个对比维度），原有的三元组全部作废，应当重建而不是打补丁。很多系统的错乱不是出在某个子任务，而是出在“目标变了但契约没变”。

验收断言写不出，就是没想明白。不要用“由专家判断”糊过去，那等于把一个没有标准的任务派给了无法被验收的执行者。正确做法是把它留在人手上，或者先做一个小样本把标准谈出来。

并行会重复查询。两个子代理查同一份资料，不只是浪费预算，还可能得出不同口径的结论。共享前置提到上层执行一次，是收益最确定的一项优化。

粒度过细的判据是交接成本。如果交接物无法用一段话说清，或者交接需要附带五个附件，那说明切开的位置不对。粒度过粗的判据是上下文溢出：子代理需要反复回看同一批材料才能下结论。

子代理无法感知未写进契约的隐含约束。所有“大家都知道”的前提，对子代理都是不存在的。这不是模型缺陷，而是契约缺陷。

## 七、落地检查清单

1. 每个子任务都能写出输入、输出、验收三元组。判据是任取一个子任务，三句话能写完，且验收是断言而不是形容词。
2. 输入是物化的产物引用，附口径或版本声明。判据是子任务启动时能校验输入的版本与口径，不匹配即失败。
3. 输出有 schema 且可程序化校验。判据是合并阶段不读自由文本，只读结构化字段。
4. 契约包含预算与截止时间。判据是超预算会被中断，中断时保留已完成部分。
5. 契约包含显式禁止项。判据是子代理没有越权修改源数据或扩大查询范围，且越权会被拦截而不是事后发现。
6. on_fail 明确。判据是失败时能确定是重试、降级还是升级，且路径可复现。
7. 冲突有消解策略。判据是两个矛盾结论会被登记为冲突并回到证据层，而不是被拼接进同一份文档。
8. 部分成功必须显式声明缺口。判据是最终产物中每个缺口都有 missing 标记与原因。
9. 依赖写明版本。判据是上游更新后，下游能被识别为 stale 并触发重跑。
10. 共享前置查询在上层执行一次。判据是同一份数据在同一轮编排中被拉取的次数不超过一次。

## 八、常见误区与面试追问

**问 1｜任务分解是不是越细越好？**
不是。细分只在“每个子任务都能独立验收”时带来并行收益，超过这个点，交接成本会超过收益。可操作的判据是：交接物能否用一段话说清、能否用一个 schema 表达。做不到就该合并。

**问 2｜验收标准能不能写成“结论看起来合理”？**
不能。这不是断言，无法判定真假，也无法在失败时定位。至少要落到可检查的形态：引用了哪个指标、口径是什么、数值在什么范围。剩下的“合理性”用抽检处理，而不是写进契约充当验收。

**问 3｜output_schema 会不会限制子代理的表达能力？**
会，而且是有意的限制。自由度留在需要判断的地方（结论措辞、取舍理由），结构留在需要被机器处理的地方（数值、引用、缺口）。把全部自由度留给自由文本，代价是合并阶段只能靠人读。

**问 4｜子任务之间能不能直接通信？**
能，但要克制。直接通信省掉一次中转，却会产生绕过全局状态的隐性约定。稳妥做法是允许子任务读写指定的共享条目，其余信息必须经上层。否则“下游按旧版结论继续做”这类错误无法归因。

**问 5｜部分成功该不该上报？**
必须上报，而且要结构化。把部分成功当成功上报，缺口会一路传到最终产物；把部分成功当失败上报，会丢掉已经完成的价值。正确做法是显式声明完成了什么、缺什么、为什么缺，让上层决定继续还是重排。

## 九、小结与延伸阅读

任务分解的质量，不取决于切了多少块，而取决于每一块能否用输入、输出、验收三句话说清。派发是把这三句话连同预算与截止条件一起交出去，回收是按同样的标准把产物接回来并处理冲突与缺口。三者构成一个闭环，缺一环，多代理就退化成多次单机调用。

延伸阅读建议：论文类可关注任务分解与层级规划的研究，重点看它如何定义子任务边界；官方文档类可看多代理框架中 handoff 与 delegation 的接口语义；工程博客类可看编排系统如何处理部分成功与冲突合并。阅读时把“验收标准写在哪里”作为观察点。
