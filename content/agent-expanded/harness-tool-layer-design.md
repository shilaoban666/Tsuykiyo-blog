## 一、开场问题：工具从五个加到五十个，成功率反而下降

一个内部助手最初只接了五个工具：查文档、查工单、发消息、建日程、读表格。模型选得很准，用户也满意。后来按需求把工具扩到五十个，覆盖十几个业务系统，结果选择错误明显增多：该查订单时去查了发票，该更新时调用了创建，参数里把用户 id 填成了工单 id。团队困惑的是，模型能力没有下降，为什么表现变差。

原因有两层。浅层是选择空间变大，名称相近、描述含糊的工具互相干扰；深层是工具契约不完整，模型只能靠猜。一个工具如果只告诉模型“叫什么、大概做什么”，却不告诉它“参数长什么样、成功返回什么、失败怎么区分、重复调用会怎样”，那么每次调用都是一次赌博。工具层的质量，正是由这些看似琐碎的契约细节决定的。

把这件事想清楚，工具数量的意义就变了。五十个工具不是五十份能力，而是五十份需要模型逐份阅读的说明书。说明书越含糊，模型在“读说明书”上花掉的注意力越多，留给实际判断的越少。工具层设计的第一个目标，是让每份说明书短到能被认真读完，又准到不会读错。

## 二、概念界定：工具契约的四个面

一个可用的工具定义包含四个面。名称要能表达动作与对象，最好带业务域前缀，避免 search 这种放之四海皆准的词。参数 schema 要能判别对错，用类型、枚举、必填、范围与格式把歧义压到最低，而不是靠自然语言叮嘱。返回值要稳定，成功与失败共享同一外壳，字段含义固定，避免这次返回数组、下次返回对象。错误语义要可行动，区分参数错误、权限不足、资源不存在、冲突、限流与下游故障，并明确哪些可重试。

除此之外还要标注副作用等级。只读工具可以随意重试；可重试写工具需要幂等键，重复执行不产生额外效果；不可重试写工具（付款、删除、对外发送）必须一次性执行，失败后转人工或走补偿，不能由模型自行重试。副作用等级不是文档里的备注，而应作为工具元数据进入网关，由运行时强制执行。

很多团队把工具定义当成 API 文档的附属品，写几句描述就上线。实际上，工具定义是模型与系统之间的唯一契约，模型看不到后端实现，只能看到这份定义。定义模糊，模型就只能靠先验猜；定义精确，模型的选择空间被收窄，稳定性自然上升。

四个面里最容易做假的是“返回值稳定”。团队往往在联调时看到成功路径返回漂亮，就认为契约完成了。真正的问题出在失败路径：同一个接口，超时返回 HTML 错误页，业务校验失败返回 200 加 error 字段，权限不足返回 403 加纯文本。模型面对三种形状，只能靠猜哪一种是失败。

## 三、机制拆解：schema、幂等键与错误归一化

先看一个参数 schema 的示意。它不追求覆盖所有情况，而是把最容易出错的字段钉死。

```json
{
  "name": "orders.refund",
  "description": "对已支付的订单发起退款；仅当订单状态为 paid 时可用。",
  "side_effect": "non_retryable_write",
  "input_schema": {
    "type": "object",
    "required": ["order_id", "amount_cents", "reason_code"],
    "additionalProperties": false,
    "properties": {
      "order_id": {"type": "string", "pattern": "^ord_[0-9a-f]{12}$"},
      "amount_cents": {"type": "integer", "minimum": 1},
      "reason_code": {"type": "string",
        "enum": ["damaged", "late", "wrong_item", "customer_request"]},
      "note": {"type": "string", "maxLength": 200}
    }
  }
}
```

这份 schema 做了几件事：必填字段明确，金额用整数分避免浮点误差，原因用枚举而不是自由文本，禁止额外字段防止模型塞入后端不认识的参数，订单号用正则约束格式。描述里写清前置条件“仅当状态为 paid”，让模型在调用前就能排除不适用的场景。这些约束不是为了限制模型，而是为了把“能不能调”的判断从猜测变成检查。

幂等键的设计要解决“键从哪来”。常见做法是由运行时根据业务实体与动作生成，例如 order_id 加 refund 加请求序号，而不是让模型自由填写。网关在执行前查这个键是否已处理：已成功则直接返回原结果，处理中则返回“进行中”，失败且可重试才真正重放。这样即使模型因为超时重复发起，也不会造成二次退款。

错误归一化是第三个关键。后端各有各的异常格式，网关要把它们映射成固定错误码，并附带重试建议。下面是一段示意映射。

```python
ERROR_MAP = {
    "VALIDATION_ERROR":   dict(code="invalid_argument", retryable=False,
                               hint="检查必填字段与枚举取值"),
    "UNAUTHORIZED":       dict(code="permission_denied", retryable=False,
                               hint="当前身份无此权限，请换用有权限的工具"),
    "NOT_FOUND":          dict(code="not_found", retryable=False,
                               hint="确认实体 id 是否正确"),
    "CONFLICT":           dict(code="state_conflict", retryable=False,
                               hint="先读取最新状态再决定是否重试"),
    "RATE_LIMITED":       dict(code="rate_limited", retryable=True,
                               hint="等待后重试，避免并发"),
    "UPSTREAM_TIMEOUT":   dict(code="upstream_timeout", retryable=True,
                               hint="只读可重试；写操作先查幂等结果"),
}
```

错误码的粒度要适中。全都归成 internal_error，模型无法决策；把后端几百个错误码原样透出，模型也记不住。按“模型下一步该做什么”来分类，通常六到十类就够：改参数、换工具、等一会、查状态、找人、放弃。

还有一个细节值得单独说：retryable 与 hint 必须是给模型的行动建议，而不是给人看的解释。“服务暂时不可用”是解释，“等待 2 秒后重试一次，仍失败则改用只读接口确认状态”才是建议。前者会让模型随意再试，后者让它知道下一步做什么。

## 四、工程取舍与反例

第一个取舍是描述长度。描述太短，模型不知道适用场景；描述太长，挤占上下文且重点被淹没。可行的写法是固定结构：一句话说明做什么，一句话说明何时用，一句话说明何时不要用，再列一两个参数示例。把“不要用”写清楚，往往比多写十个形容词更能减少误选。

第二个取舍是工具数量与分组。工具多时，一次性全量暴露会让选择变难。按任务阶段或业务域分组，每轮只给当前阶段相关的工具，是更稳的做法。分组本身也是信息：它告诉模型当前处于哪个环节，哪些动作是下一步该考虑的。

第三个取舍是严格与宽容。additionalProperties 设为 false 能防止脏参数，但也会让模型偶尔多传一个字段就失败；设为 true 更宽容，却可能把拼写错误悄悄吞掉。对外部系统写操作建议严格，对内部只读查询可以适度宽容，并在网关侧记录被丢弃的字段用于改进描述。

常见反例有四类。其一是“万能工具”，一个 execute 接口接收任意命令字符串，等于把权限与校验全部绕过。其二是“裸异常”，工具失败时把堆栈直接返回，模型要么复述给用户，要么编造成功。其三是“伪幂等”，声称支持重试但没有幂等键，靠“应该不会重复”来赌。其四是“描述与实现不一致”，文档说只读，实际会写库，模型据此做出错误规划。

还有一个隐蔽的反例：把重试次数写死在网关里，对所有工具一视同仁。只读工具重试三次可能没问题，写工具重试三次就是三次副作用。重试策略必须与副作用等级绑定，且总重试预算要计入任务成本，否则一次故障会悄悄烧掉大量调用。

## 五、工程案例：一次 128 元变成 384 元的退款

背景示意：某电商客服 Agent 接入退款工具，后端退款接口没有幂等支持。网关沿用了团队的统一重试策略：超时重试三次。

输入：用户要求对订单 ord_7f3a91c2d4e5 退款 128.00 元。

失败轨迹（示意）：第 1 次调用 refund，下游处理成功但响应在回程超时；网关判定 upstream_timeout 可重试，自动重试第 2 次；后端又超时；第 3 次成功返回。上游看是“一次成功”，下游实际落了 3 笔退款。与此同时，第 2 次重试时后端返回过 400 加 DUPLICATE_REQUEST，被错误映射成 invalid_argument，模型据此判断“参数有问题”，把金额改成 128.01 又调了一次。T+1 对账时才发现三笔退款、金额不等。整个过程中没有任何一步被系统判为异常。

根因有三个，全在工具契约。副作用等级只写在文档里，网关的重试策略按工具名白名单配置，refund 被漏掉了；幂等键没有，重复请求无从识别；错误映射把“重复请求”归到了“参数错误”，把模型引向了改参数。

处理做了五件事。其一，side_effect 进入网关元数据并强制生效：refund 标为 non_retryable_write，自动重试预算 0，超时只做状态查询不做重放。其二，幂等键由运行时生成，格式为 `refund:{order_id}:{request_seq}`，网关维护幂等表（key → running/succeeded/failed 与结果快照），重复请求在 running 状态返回 in_progress，succeeded 直接返回首次结果并标记 deduplicated。其三，错误映射拆出 duplicate_request：retryable=false，hint 明确“不要修改参数，先查幂等结果或对账”，同时在工具策略层禁止“改参数重试”这个动作。其四，把金额上限做成前置条件：schema 增加 precondition `amount_cents <= refundable_amount(order_id)`，由网关在执行前读取可退金额校验，超出直接返回 invalid_argument 并附可退上限。其五，加对账：每小时比对退款事件数与下游退款单数，差值非零即告警。

结果（示意）：上线三个月重复退款 0 起，duplicate_request 命中 47 次（都被幂等层正确吸收并返回原结果），退款平均耗时增加约 180ms，来自幂等表查询。改动没有换模型，也没有加长提示词。

最值得记的是那个 180ms。幂等要付代价，而且代价落在每一次正常请求上，不只是出问题的时候。这笔钱必须提前算进延迟预算，否则上线两周后就会有人提议“把幂等查表去掉，反正没出过事”。

## 六、与相邻概念的边界

工具层容易被和三类相邻概念混在一起。

与 API 网关的边界：API 网关关心的是流量、鉴权与路由，工具层关心的是“模型能不能选对、选错能不能收场”。同一后端能力，在工具层可能被拆成两个工具（例如 orders.get_brief 与 orders.get_full），因为模型在不同阶段需要不同粒度；这对 API 网关来说是不可理解的拆分。

与调用协议的边界：无论用哪种工具调用协议或 MCP 这类集成方式，解决的都只是“怎么把工具暴露给模型、怎么把参数传下去”。副作用等级、幂等键、错误码分类都不在协议里，必须自己设计。协议统一了接线方式，统一不了语义。

与 RPC 的边界：RPC 假设调用方是确定性程序，出错会按代码分支处理；工具层的调用方是概率模型，同一个错误它可能改参数、可能换工具、可能直接道歉。所以工具层必须把“下一步该做什么”编码进错误里，而 RPC 只需要给出错误码。

## 七、落地检查清单

1. **名称带域带动作**：`domain.action` 形式，禁止 execute、run、do 这类无信息量的名字。
2. **schema 可判别**：必填、类型、枚举、pattern、范围齐全；写操作 additionalProperties=false。
3. **前置条件可执行**：precondition 出现在元数据里并能被网关校验，而不是只写在描述里当建议。
4. **副作用有等级**：read／retryable_write／non_retryable_write 三档，网关按等级强制重试策略。
5. **幂等键运行时生成**：由实体加动作加序号构成，模型无权填写，键的生成规则可测试。
6. **幂等表可查状态**：running／succeeded／failed 三态明确，重复请求返回首次结果而非再次执行。
7. **错误码 6–10 类**：按“下一步动作”分类，每类带 retryable 与可执行的 hint。
8. **返回同构**：成功与失败共享外壳；投递结果与业务效果分成两个字段。
9. **重试预算绑副作用**：写操作默认 0 次自动重试，只读不超过 2 次，重试消耗计入任务成本。
10. **契约进 CI**：每个工具有 schema 校验用例、错误映射用例、幂等用例，改动必须过测试。

## 八、常见误区与面试追问

**追问一：描述写详细一点，是不是就不需要 schema 约束了？**

答：不能互相替代。描述影响“要不要选这个工具”，schema 影响“参数对不对”。自然语言约束在长上下文里会被稀释，schema 校验每次都生效。两者都写，但不要用描述去弥补 schema 的缺失。

**追问二：所有工具都配幂等键，是不是就安全了？**

答：只对有副作用且可识别实体的工具有效。幂等键要能唯一标识“同一次业务意图”，如果键里含时间戳或随机数，每次重试都是新键，等于没做。而且幂等只能防重复，防不了“参数被模型改过”的第二次调用。

**追问三：错误码是不是越细越好？**

答：不是。判断标准是“模型能否据此改变下一步动作”。两个错误码如果导致同一个动作，就该合并；一个错误码如果对应两种完全不同的处理，就该拆开。六到十类通常够用，剩下的细节放 message 里给人看。

**追问四：工具数量到多少就该分组？**

答：不看绝对数量，看单轮可分辨度。经验阈值是同一轮暴露超过十来个工具时，误选率开始明显上升（示意）。更可靠的做法是按阶段裁剪，让每一轮的可选集合都小到能被仔细读完。

**追问五：为什么不让模型自己决定要不要重试？**

答：因为模型看不到幂等状态，也不承担重复扣款的后果。它看到超时，最自然的反应就是再试一次，而这恰好是最危险的动作。重试是运行时的策略，应该由副作用等级和幂等表决定，模型只应该收到“已处理，结果为 X”这样的事实。

## 九、小结与延伸阅读

工具层的目标不是把接口都接进来，而是让模型一次选对、错了能安全收场。做到这一点靠四件事：可判别的 schema、明确的副作用等级、稳定的返回结构、可行动的错误语义。工具数量是结果，不是指标；一个只有五个工具但契约清晰的系统，通常比五十个含糊工具更可靠。

延伸阅读建议：官方文档类可看主流模型厂商对工具调用 schema 与错误处理的约定；工程博客类可看 API 设计中的幂等键与重试实践；论文类可关注工具学习与函数调用评测中对参数准确率的度量。阅读时重点看“失败路径”，那才是工具层真正的分水岭。
