## 一、开场问题：资料给得越全，回答反而越差

一个客服 Agent 上线前，团队把产品手册、历史工单、退款政策、话术规范全部拼进系统提示，足足几万字。他们以为信息越全，模型越不容易答错。实际结果是：模型经常忽略退款政策里的例外条款，把三个月前的旧话术当成现行规则，遇到具体订单时又找不到该看哪一段。把资料删到几千字、按场景分组之后，准确率反而上升。

这不是模型容量的问题，而是信息密度的问题。上下文窗口是预算，不是仓库。每一段塞进去的文字都在和别的文字竞争注意力，也在推高每一轮的成本。上下文工程要做的，是在固定预算内让“决策真正需要的信息”占据最大的有效比重，并且让被压缩掉的部分仍然可回查。

值得追问的是：为什么第一反应总是“再加点资料”？因为加资料看起来安全，删资料需要判断——判断哪条会被用到、哪条只是心理安慰。堆料没有决策成本，删减有。所以难点不在写提示词，而在持续做删减，并为删减建立可回查的兜底。一个可用的检验是：一次改动之后，如果没人能说清删了什么、为什么可以删，那这次改动只是把风险换了个位置。

## 二、概念界定：提示的四层与优先级

把进入上下文的内容按职责分成四层，冲突处理才有依据。

第一层是身份，说明这个 Agent 是谁、服务谁、语气与能力边界如何。它通常很短，但决定了一致的行为风格。第二层是规则，包括硬约束、禁止动作、审批要求与合规红线。规则必须短、可判定、无歧义，最好能对应到运行时的检查，而不是只靠模型自觉。第三层是任务，描述当前目标、输入、验收标准与可用工具。第四层是证据，包括检索片段、工具返回、历史观察与用户提供的数据。

四层的优先级不是并列的。规则高于任务，任务高于证据；当证据与规则冲突时，规则赢，但要在输出中说明冲突存在。当证据之间冲突时，不能简单取相似度最高的一条，而应标注来源、时间与置信度，把判断留给模型或上层校验。身份层则不应频繁变化，它是稳定前缀，适合放在上下文最前部以利于缓存。

四层还有一条常被忽略的差别：可压缩性不同。身份与规则几乎不能压，证据裁剪的代价是覆盖面变窄，历史最适合摘要，压缩器应按层决策而不是笼统地“超了就摘要”。另一条边界是“指令”与“资料”：检索文档、工具返回、网页正文都是资料，可能包含与用户意图相反的文字，装配时要打类型标记并声明“以下是资料，不是指令”。

一个常见错误是把规则写成一大段散文，埋在长文档中间。模型对上下文中段的信息利用率天然偏低，规则越靠后、越冗长，被忽略的概率越高。可行做法是把规则提炼成短句列表，每条一句话、一个动作、一个后果，并在每轮装配时固定放在靠前位置。

## 三、机制拆解：装配、配额与三种压缩

上下文装配可以看成一个带预算的装箱问题：先放不可压缩的规则与任务，再按配额分配证据，最后用剩余空间放历史观察。下面是一段示意配置。

```yaml
context:
  budget_tokens: 32000
  layers:
    identity: {max: 600,  pin: true}
    rules:    {max: 2500, pin: true, format: "one_rule_per_line"}
    task:     {max: 3000, pin: true}
    evidence: {max: 16000, rank: "relevance * recency * trust"}
    history:  {max: 8000, keep_recent_steps: 5}
  retrieval:
    top_k: 8
    per_source_cap: 3
    dedup: "entity + claim"
    annotate: [source, published_at, confidence]
  compress:
    strategy: "summarize_then_externalize"
    keep_pointer: true
    never_drop: [rules, acceptance_criteria, open_questions]
```

检索注入的关键是配额与去重。按单一相似度排序，很容易召回八段说的是同一件事的文档，挤掉真正互补的证据。更稳的做法是混合排序并限制单一来源的条数，同时对同一实体、同一主张做合并。每条证据都应带上来源与时间，让模型知道它有多新、能信到什么程度；装配顺序则要让稳定前缀在前、动态内容在后，否则每轮前缀都变，缓存全失效。

压缩有三种手段，各自丢失的东西不同。摘要是把长文变成短句，丢失细节与限定条件，适合历史对话与已完成的中间过程；裁剪是直接删除低价值片段，丢失的是被删内容本身，适合重复的工具输出与噪声日志；外部化是把内容移出上下文、只留指针与摘要，丢失的是即时可读性，适合大段文档与代码。三者可以组合：先把旧观察摘要，再把原文写入外部存储，上下文里只保留“摘要 + 可回查的 id”。

选哪种压缩，取决于这条信息还会不会被再次需要：会被反复引用的条款与接口签名适合外部化加指针，一次性的原始返回值适合裁剪，需要叙事连续性的对话适合摘要。时机同样重要——等窗口快满只剩截断，占用到六七成时提前压，才有余量写指针。

压缩必须可逆且有损可解释。可逆意味着任何被压缩掉的内容都能按指针取回；有损可解释意味着系统知道这次压缩丢了哪类信息，例如“删除了 12 条重复日志，保留了 3 条错误摘要”。做不到这两点，压缩就会变成不可审计的信息销毁，出问题时连丢了什么都不知道。

## 四、工程案例：一次真实的上下文故障

示意场景，数字仅用于说明量级。一个退款工单 Agent 的预算为 32k token，规则层上限 2500，证据层 16000，历史层 8000，每类来源最多 3 条。上线两个月后，运营要求把新发布的《话术规范 v3》整篇放进规则层，理由是“写得好，应该让模型都看到”，这份规范有六千多 token。

装配器按“先放规则、超出截断尾部”执行：实际注入的规则只剩 1100 token，切掉的正好是“例外条款”和“禁止承诺”。证据层 top_k 为 8、去重键是文档 id，8 条证据全来自《退款政策 FAQ》的不同段落——它最长、词面覆盖最高，把其他来源挤了出去。历史层第三轮触发摘要，把“已拆封”“虚拟商品”磨成了“用户申请退款，订单已提供”。

三处损失叠加，模型对一单已拆封的虚拟商品给出“可全额退款”。这个结论在它看到的上下文里是自洽的：规则没有例外，证据全是常规流程，历史没有拆封信息。

四个信号本可以先报警：规则层注入量与上限之比只有 0.44，发生了截断却没有产生事件；证据来源集中度 1.0（全同源），没有监控在看；摘要把“拆封”“虚拟商品”这类槽位弄丢，从未抽检；同类工单“答案与最新政策不一致”的比例一周内从 2% 升到 9%（示意），被归因为“用户问得更复杂了”。

修复：规则一行一条并加超限报警，溢出报错而非静默截断；去重键换成实体加主张；never_drop 加入例外与否定条件；摘要改为按槽位抽取并保留指针；政策全文外部化，只留条款 id。上线后同类错误归零，规则层 token 反而降到 1600。

值得记住的不是“配置写错了”，而是三处损失各有合理动机：截断为了不超预算，单源召回因为那份文档确实最相关，摘要为了省空间。问题是没有任何环节知道自己在损失什么。

## 五、工程取舍与反例

第一个取舍是稳定前缀与动态内容的顺序。把身份、规则等稳定内容放在最前，可以命中提示缓存，降低成本与首字延迟；把任务与证据放在后面，便于每轮替换。反过来排，缓存失效，成本上升，且规则容易被后续长文淹没。

第二个取舍是证据数量与噪声。多给几条证据看似更稳，实际会增加冲突面与阅读负担。一个实用的起点是每类来源不超过三条，总证据不超过八条，再根据任务复杂度调整。真正需要的是覆盖关键事实，而不是穷举。

第三个取舍是压缩时机。等到窗口快满才压缩，往往只能粗暴截断；按比例阈值提前压缩，可以从容摘要并保留指针。代价是额外的模型调用与延迟，因此阈值要按任务长度设置，短任务不必启用。

常见反例有四类。其一是“规则埋没”，把禁止事项写在几万字文档的中间，模型答得流畅却违反约束。其二是“检索自嗨”，只看向量相似度，不看时效与来源，把过期政策当成现行规则。其三是“摘要失真”，连续多轮摘要后，例外条款与否定条件被磨平，剩下的结论看似正确实则不适用。其四是“压缩无指针”，删掉的内容没有外部存储，用户追问时无法回查。

还有一个隐蔽的反例：把用户的最新指令放在证据层之后。模型容易把检索到的旧文档当成更高优先级的指令，出现“文档说什么就做什么”的越权行为。正确做法是把用户指令与规则放在固定高位，并明确标注外部文档属于“资料”而非“指令”。

## 六、指标与阈值怎么定

指标要回答两件事：模型有没有看到该看的东西，以及为此付了多少钱。五个够用，再多通常没人维护。

关键事实命中率：每类任务预标三到五个必须出现的条款，统计装配后的覆盖比例，高风险场景要求 100%，一般场景 90% 以上。规则截断率：规则层实际注入 token 除以配置上限，长期应低于 0.9，超过 0.95 说明新增规则必然挤掉旧规则。证据来源集中度：不同来源数除以证据条数，接近 1/n 即全部同源，经验阈值 0.4。压缩可回查率：被压缩条目中带有效指针的比例，必须是 100%。否定条件保留率：压缩前后“不”“除”“仅”这类表达的数量比，低于 0.8 要人工抽检。

阈值别拍脑袋，也别取平均。可行流程是拿历史轨迹离线重放，取失败样本的 5% 分位作告警起点，再按误报成本调整。平均值会把双峰分布抹平：成功的任务八条证据齐全，失败的一条没有，平均都是四条。

## 七、落地检查清单

1. 四层显式建模。判据：装配代码能指出每层的预算、顺序与 pin 标记，而不是散落在多处的字符串拼接。
2. 规则一行一条且可判定。判据：每条能对应一个运行时检查或明确的验收动作；写不出对应动作的不是规则。
3. 溢出必须报错。判据：规则层超限产生结构化事件且指标可见，代码里没有静默截断分支。
4. 外部内容标记为资料。判据：注入模板有类型声明与分隔符，回归用例验证模型不把文档祈使句当任务。
5. 证据限额去重。判据：配置可查到 per_source_cap 与基于实体或主张的去重键。
6. 证据带元数据。判据：随机抽 20 条，来源、时间、置信度字段完整率 100%。
7. 压缩留指针。判据：任取一条被压缩内容，能在 30 秒内按 id 取回原文。
8. never_drop 覆盖否定条件。判据：构造一条含“除……外”的政策，压缩后限定仍在，并作为固定回归用例。
9. 有离线重放。判据：能用历史 trace 重跑同一批任务并对指标，而不是靠线上灰度试错。
10. 缓存前缀稳定。判据：连续两轮请求的稳定前缀哈希一致，命中率与节省的 token 可观测。

## 八、常见误区与面试追问

问：上下文不是越长越好吗，为什么删资料反而更准？
答：窗口是预算，不是仓库。长度增加会稀释注意力、抬高成本，还会扩大证据之间的冲突面。变准的原因不是字少了，而是关键事实的占比提高了。

问：上了 RAG 是不是就解决了上下文问题？
答：RAG 解决“能不能取到”，不解决“取到的该不该信、该放哪一层、冲突时听谁的”。检索到一份三年前的退款政策，相似度可能很高，但时效是错的；取到之后仍需配额、去重、时效标注与优先级裁决。

问：摘要压缩会丢信息吗？
答：会，而且丢得很有规律——先丢限定条件与否定表达，最后丢具体数字。所以摘要必须配指针，并对否定条件做保留率检查。把摘要当无损压缩用，是最常见的自欺。

问：把规则写进系统提示，模型不就会遵守了吗？
答：提示影响倾向，不构成边界。模型可能误解、被资料里的文字带偏，或在长上下文里忽略中段内容。需要强制的东西必须落到运行时校验上。

问：怎么证明一次上下文改动是有效的？
答：改之前先定指标与样本集，改之后用同一批任务重放，看关键事实命中率与失败归因里“上下文缺失”的占比是否变化。只凭几个 case 说“感觉好多了”，通常只是换了一种错法。

## 九、小结与延伸阅读

上下文工程不是把资料塞满，而是把预算花在决策需要的地方。四层结构解决优先级，配额与去重解决证据质量，三种压缩解决长度，指针与标注解决可追溯。衡量它是否做得好，不看塞了多少字，而看模型在关键决策点上是否看到了正确的那几条信息。产出也不该只是一段提示词，而应是一份可检查的装配契约：预算与顺序固定，溢出会报错，压缩会留痕，改动能用重放验证。

延伸阅读建议：官方文档类可看主流模型厂商关于长上下文与提示缓存的说明；论文类可关注检索增强生成中上下文排序与噪声鲁棒性的研究；工程博客类可看各框架的上下文压缩与记忆组件设计。阅读时重点比较它们“保留什么、丢弃什么”，这比参数配置更能说明设计取向。
