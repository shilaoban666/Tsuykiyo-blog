## 一、开场问题：一半成功，算成功还是失败

一个合同审查系统把任务拆成四段：抽取条款、比对模板、标注风险、生成意见。某次运行中，前三段都完成了，第四段在生成意见时模型超时。系统按“失败”处理，整单退回重跑。重跑时，抽取条款的子代理换了一个参数，抽出来的条款集合与上次不完全一样，于是前一次已经标注的风险全部作废，人工复核过的那部分也要重看。一次超时，代价是整条链路重来，还丢掉了人工已经确认的成果。

这个案例暴露的不是超时处理问题，而是“部分成功”没有被定义。系统只有成功与失败两个状态，中间那大片“完成了一部分、且这部分仍然有价值”的地带被丢掉了。本文讨论的是：怎样把失败分类、怎样定义部分成功、怎样补偿与重试，才能让一次子代理故障不至于推翻全部工作。

## 二、概念界定：四类失败与三种可恢复性

失败至少要分成四类，因为恢复动作完全不同。第一类是超时：子代理在规定时间内没有返回，可能仍在运行，也可能已经卡死。第二类是明确错误：工具返回权限拒绝、参数非法、下游不可用，错误码清楚。第三类是低质产出：调用成功、格式正确，但验收不通过，例如结论没有证据、字段填了占位内容。第四类是结论冲突：多个子代理各自都合格，但结论互斥。

与四类失败对应的，是三种可恢复性。可重试：同样的输入再跑一次有机会成功，例如瞬时超时、限流。可修补：整体不可用，但部分产出可复用，例如三段完成一段失败。不可恢复：前提被证伪、权限被永久收回、外部副作用已发生且不可撤销，只能升级或补偿。

把失败分类之后，“部分成功”才有精确定义。本文把它定义为：子任务产出的一个子集，满足三个条件——可独立验收、不依赖失败部分、向上层明确标注了缺口。三个条件缺一，就不是部分成功，而是“半成品”，半成品不应被当作成果复用。

四类失败之间会相互转化，这一点在实现里经常被忽略。超时如果没有及时处理，会退化成低质产出，因为拿到的是半截结果；低质产出如果被下游复用，会退化成结论冲突。因此在分类之外还要记录“首次失败类型”，恢复动作按首次类型决定，而不是按当前表现决定。

## 三、机制拆解：检查点、补偿与重试预算

恢复机制的骨架是“检查点 + 补偿登记 + 重试预算”。检查点让已完成的工作可复用，补偿登记让已发生的副作用可撤销，重试预算防止系统在同一个故障上无限消耗。

```yaml
task_state:
  id: t-contract-8821
  status: partial
  completed:
    - step: extract_clauses
      artifact: "artifact://clauses-8821-v2"
      verified: true
    - step: compare_template
      artifact: "artifact://diff-8821"
      verified: true
    - step: mark_risks
      artifact: "artifact://risks-8821"
      verified: false          # 人工复核未完成
  failed:
    - step: generate_opinion
      kind: timeout
      retryable: true
      attempts: 2
  side_effects:
    - action: create_review_ticket
      undo: close_ticket
      idempotency_key: "8821:ticket"
  next:
    action: retry
    budget_left: {attempts: 1, wall_clock_min: 4}
```

这份状态里，completed 的每一项都带 verified 标记，failed 带失败类型与可重试判断，side_effects 带撤销动作与幂等键。恢复时按顺序做四件事：先看失败是否可重试，再看已完成部分是否仍与当前前提一致，然后决定复用还是重算，最后处理副作用。

“已完成部分是否仍一致”是最容易漏的一步。子代理超时后，外部世界可能已经变化：合同被对方修改、审批人换了、额度被占用。直接复用旧产出，会把过期结论带进新结果。稳妥的做法是给每个产出记录它依赖的前提摘要，恢复时重新校验前提，不一致就标记为“需重算”，而不是默默复用。

补偿要按逆序执行，且必须幂等。已经创建了工单，补偿是关闭工单；已经占用了额度，补偿是释放额度；已经发出了通知，补偿是发更正而不是再发一遍。补偿动作本身也可能失败，因此要有补偿的重试与人工兜底，不能假设补偿一定成功。

重试预算要写死三个数：次数、退避、升级条件。次数不是越多越好，同一个确定性错误重试十次只是浪费；退避要带抖动，避免多个子代理同时重试打垮下游；升级条件要明确，例如“重试两次仍失败”或“失败原因属于权限类”，触发后转人工或降级交付。

降级交付是最后一道防线。当无法完整完成时，返回“已完成部分 + 缺口清单 + 建议下一步”，比返回一个笼统的失败更有用。降级交付的关键是诚实：不能把未完成的部分包装成已完成，也不能因为怕用户失望而省略缺口。

超时还有一层实现细节：超时那一刻子代理可能仍在运行、可能已经死掉、也可能刚产出结果但没来得及回传。因此超时后的第一个动作不是重试，而是查询执行状态；查询自己也要带超时，查不到按“未知”处理，走保守路径——读操作可重试，写操作一律先查副作用登记。

## 四、工程取舍与反例

第一个取舍是快速失败与尽力而为。快速失败能让错误尽早暴露，但会浪费已完成的工作；尽力而为能保住部分成果，但可能把错误拖到更晚。可行的分界是：前提性错误快速失败，执行性错误尽力而为。

第二个取舍是重试与补偿。重试便宜，但如果失败原因是副作用已经发生，重试会造成重复。因此重试前必须先查副作用登记，确认该动作未被执行或已被补偿，否则应走“跳过并继续”而不是“重跑”。

第三个取舍是复用与重算。复用已完成产出能省时间，但可能带入过期前提；全部重算最安全，但代价高。折中是“前提未变则复用、前提已变则重算”，前提摘要的粒度决定了这个策略的精度。

反例有三类。其一是“全有全无”：只有成功与失败两个状态，一次超时推翻全部工作。其二是“盲目重试”：不区分失败类型，对所有错误一律重试，重复副作用与配额浪费随之而来。其三是“假降级”：声称降级交付，实际把缺口藏在正文里不标注，用户以为拿到了完整结果。

还有一类反例是“补偿缺失”：系统设计时只考虑正向流程，没考虑撤销，等到需要回滚时才发现外部系统没有对应的撤销接口。这类问题的修复成本远高于事前设计，因此在接入任何写操作时，都应先问一句“如果这一步之后失败，怎么撤”。

检查点的粒度决定恢复的代价。粒度太粗（整单一个检查点），恢复等于重跑；太细（每步一个检查点），落盘与校验开销会吃掉收益。可行的粒度是“可独立验收的产物”：一个能被单独检查、单独交付、单独回滚的中间结果，就值得一个检查点。反过来，检查点如果依赖了失败部分，复用就会把缺口带进下一段。

恢复流程本身也需要限流。一次下游抖动可能让几十个子任务同时进入恢复，查询状态、重算、补偿一起涌向同一个下游，把局部故障放大成区域故障。可行做法是给恢复动作排队并限制并发，同时对同一依赖的恢复做合并：同一份产物被多个子任务复用时，只重算一次。

## 五、工程案例：一次失败

（示意场景）合同审查四段：抽取条款、比对模板、标注风险、生成意见。某次运行前三段完成，第四段在第 90 秒超时。系统按全有全无处理，整单重跑。重跑时抽取代理换了参数，条款集合从 42 条变成 45 条，上一次标注的 11 个风险点全部失效，人工已确认的 6 个也要重看。

代价可量化（示意）：整单重跑 35 分钟，其中人工复核 18 分钟是重复劳动；更麻烦的是两份结论不一致，业务方不知道该信哪一版，最后按“以最新为准”处理，等于把第一批人工确认白扔了。

改成检查点复用后：前三段带前提摘要落盘，第四段失败只重跑第四段，风险标注保留，人工复核标记随条款 id 迁移。同一次故障的恢复时间（示意）降到 6 分钟，只产生一个版本的结论。前提摘要的粒度是关键：太粗（只记合同号），条款一变就判不出；太细（记全文哈希），改个错别字就要全部重算。可行粒度是“影响结论的那几个字段”。

## 六、指标怎么定

恢复能力的指标要能区分“恢复得快”与“恢复得对”。

四个指标：平均恢复时长（从首个失败信号到任务重新可交付，必须按失败类型分组，混在一起看没有意义）；成果复用率（复用产出占已完成产出的比例，偏低说明检查点粒度不对或前提校验太严）；补偿成功率（补偿动作一次成功的比例，偏低说明撤销接口不可靠）；假降级率（声明降级交付、但缺口后来被下游发现的比例，这是最该盯的一个）。

假降级率难统计，因为它依赖下游反馈，通常要人工回访或抽查。可行做法是给每个降级交付打标记，一周后抽样回访，把发现的缺口记进指标。这个数字一旦抬头，说明降级交付在变成隐瞒缺口的借口。

阈值上，恢复时长按失败类型分别设上限，超过上限直接升级人工而不是继续重试；复用率不必追求高，前提变化频繁时低复用是正确行为。

## 七、落地检查清单

1. 失败分四类且分类可机器判定。判据：每条失败记录有 `kind` 字段，四类之外的新类型必须先进分类再进重试。
2. 超时先查状态再决定动作。判据：超时后有状态查询记录，写操作未查副作用前不重试。
3. 部分成功有明确判定。判据：产出带 `verified` 标记，未验证部分不得计入完成。
4. 产出记录前提摘要。判据：恢复时能重算前提哈希，不一致自动标记“需重算”。
5. 副作用有撤销动作与幂等键。判据：接入写操作前先确认下游有撤销接口，没有则改为两步提交。
6. 补偿按逆序执行且自身可重试。判据：补偿失败进入人工队列，不允许静默跳过。
7. 重试预算写死三个数。判据：次数、退避（带抖动）、升级条件在配置里可见，不由代码临时决定。
8. 同因失败不重复消耗。判据：同一确定性错误重试两次后强制升级，日志记录“不再重试”的理由。
9. 降级交付诚实。判据：返回体含缺口清单与建议下一步，缺口不出现在正文里冒充已完成。
10. 恢复过程本身可观测。判据：每次恢复记录起点、复用项、重算项、耗时，能画出恢复时间分布。

## 八、常见误区与面试追问

**问：失败重试几次合适？**
答：看失败类型。瞬时错误两到三次带退避就够，确定性错误（参数非法、权限拒绝）一次都不该重试。次数写进配置，不写在代码里。

**问：部分成功能不能直接当结果交付？**
答：只有满足三个条件才能：可独立验收、不依赖失败部分、缺口被明确标注。缺一条就是半成品，交付出去等于把风险转给下游。

**问：补偿失败了怎么办？**
答：补偿本身也要有重试预算与人工兜底，并且必须有告警。假设补偿一定成功，是这类系统最常见的设计缺陷。

**问：为什么不干脆全部重算，最安全？**
答：代价高，而且重算会引入版本漂移——同一任务两次运行产出不同结论，人工确认过的成果作废。前提未变就复用，既省成本也保一致性。

**问：超时时间怎么定？**
答：按 P95 执行时长留余量，再叠加下游超时之和。定得太短会频繁误判，定得太长会让故障暴露太晚，两个方向的代价都要算进去。

## 九、小结与延伸阅读

多代理系统的可靠性，不取决于能否避免失败，而取决于失败之后能保住多少、撤销多少、多久恢复。可操作的落点是：把失败分成四类，把部分成功定义成可独立验收的子集，用检查点复用成果，用补偿登记撤销副作用，用重试预算与升级路径限制损耗。

延伸阅读建议：官方文档类可看重试、幂等与补偿事务的标准做法；工程博客类可看智能体超时与部分失败的复盘；论文类可关注容错多智能体系统的失败语义与恢复策略。
