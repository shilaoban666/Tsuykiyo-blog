## 一、开场问题：脚本跑得很好，做成服务就崩

一个团队把内部 Agent 从命令行脚本改造成共享服务，最初只有五个人用，一切正常。开放给全公司后，问题集中爆发：有人提交了一个耗时很长的分析任务，把并发槽位占满，交互式查询排在其后；某个租户的密钥配置错误，重试风暴打满了下游配额；扩容时新实例启动，旧实例被直接杀掉，正在执行的任务丢失，用户看到“已完成”却没有任何产出。

单机脚本假设“一次只有一个人、一个任务、资源管够”。共享服务没有这些假设。瓶颈从模型能力转移到运行时：谁先执行、资源如何隔离、扩容时任务如何交接、失败如何补偿。这些是调度与多租户问题，不是提示词问题。

更麻烦的是，这些问题互相缠绕。配额算错会导致重试，重试会加剧排队，排队超时又触发客户端重试，最后表现成一个与初始原因无关的故障。运行时设计得不好，故障不是发生在某个组件里，而是在组件之间来回震荡。

## 二、概念界定：运行时负责什么

Agent 运行时是 harness 的平台化形态：它在单次运行的循环之外，增加任务接入、排队、调度、租约、配额与生命周期管理。可以把它分成四层。接入层负责认证、限流与请求校验；队列层负责排队、优先级与去重；调度层负责选择执行实例、分配资源与处理抢占；执行层就是前面讨论的 harness 循环，负责任务真正跑完。

多租户隔离有四个维度：密钥、数据、工具权限、配额。密钥隔离防止一个租户的凭证被另一个租户使用；数据隔离保证上下文、日志与长期记忆不串；工具权限隔离确保租户只能调用被授予的工具；配额隔离限制单个租户能消耗的模型调用、并发与时延资源。四个维度缺一，都会出现“看起来隔离了，实际没有”的情况。

任务的生命周期也需要明确：提交、排队、运行、挂起、完成、失败、取消、超时。每个状态都要有对应的资源释放与通知机制。很多系统只关心“运行中”，忽略了排队超时、取消后的清理与失败后的重试归属，导致资源泄漏与重复执行。

还有一个常被忽略的概念是“任务所有权”。任务由谁创建、谁有权取消、谁接收失败通知、谁为副作用负责，这些在单机脚本里是隐含的，在共享服务里必须显式记录。没有所有权，取消请求会在客户端、网关与调度器之间互相推诿，最后没人真正停止执行。

## 三、机制拆解：队列、租约与优雅终止

调度的核心是平衡三件事：交互式请求的低延迟、长任务的吞吐、租户之间的公平。一个可行的结构是双队列加配额：交互式请求走短队列，长任务走批队列，调度器按租户配额与优先级取任务，避免单租户垄断。

```yaml
runtime:
  queues:
    interactive: {max_wait_s: 10, weight: 6}
    batch:       {max_wait_s: 3600, weight: 1}
  scheduler:
    policy: "weighted_fair"
    per_tenant_concurrency: 4
    preemptible: ["batch"]
  lease:
    ttl_s: 60
    heartbeat_s: 15
    on_expiry: "requeue_once_then_fail"
  shutdown:
    grace_s: 120
    on_sigterm: "stop_accepting_then_checkpoint"
  quota:
    dimensions: [concurrency, tokens_per_day, cost_per_day, tool_calls_per_min]
```

租约是长任务不丢的关键。执行实例领取任务时获得一个有时限的租约，并定期心跳续约。实例崩溃后租约过期，任务被重新入队；为了避免重复执行，重新入队要携带幂等键，并要求执行端在开始前检查该任务是否已有完成记录。on_expiry 设为“重排一次再失败”，可以避免无限重试。

心跳与租约的时间比例决定故障检测的灵敏度。心跳间隔太接近租约时长，一次网络抖动就会误判实例死亡，把正在跑的任务重排成两份；租约太长，实例真挂了要等很久才被发现。经验上心跳取租约的三分之一到四分之一，并在租约里带自增版本号，避免旧心跳覆盖新租约。

优雅终止同样重要。收到终止信号后，实例应先停止接受新任务，再对运行中的任务做检查点，最后在宽限期内退出。直接杀进程会让检查点丢失，恢复时只能从头开始，甚至产生重复副作用。宽限期要与最长单步耗时匹配，太短等于没有。

四维配额的执行要前置。并发限制在调度层做，token 与成本限制在循环层做，工具调用频率在网关层做。三层各管一段，避免所有判断堆在一个地方。配额耗尽的返回要明确，告诉调用方是“暂时排队”还是“今日额度已用完”，并给出重置时间。

公平调度需要防止“噪声邻居”。一个租户的长任务如果与另一个租户的交互请求共享线程池，会拖慢后者。按队列隔离资源、按权重分配槽位、对批任务启用抢占，是常见的组合。抢占要以检查点为前提，否则被抢占的任务等于白跑。

排队本身也需要可观测。用户在等待时最关心的不是队列算法，而是“前面还有多少、大概多久”。给出位置、预计等待与超时时间，比一个漂亮的调度策略更能减少重复提交；反过来，一个看不到排队的系统，用户会用刷新和重试把队列压垮。

## 四、工程取舍与反例

第一个取舍是公平与吞吐。严格公平会让大任务频繁被切碎，吞吐下降；完全按先来后到又会让小请求被大任务堵住。加权公平是折中，但权重需要按业务价值校准，不能拍脑袋。

第二个取舍是隔离强度与成本。每个租户独立实例隔离最好，但资源利用率低；共享实例加逻辑隔离更省，但需要严格的密钥与数据边界。可行的分层是：高风险租户独享，普通租户共享但按配额限制。

第三个取舍是扩容速度与任务安全。快速扩容能吸收突发流量，但新实例需要预热，旧实例需要交接。扩容策略应与任务类型绑定：交互式可以快速替换，长任务必须走检查点与租约交接。

常见反例有四类。其一是“无队列”，请求直接打给执行实例，突发流量下全部超时。其二是“租户只隔离数据”，密钥与工具权限共用，一个租户的误操作影响所有人。其三是“扩容即杀进程”，新实例起来后旧实例被立即终止，长任务丢失。其四是“配额只在入口算”，运行中的任务绕过配额，账单事后才爆。

还有一个隐蔽的反例：把重试放在调度层而不带幂等。任务失败后自动重排，看似提高成功率，实际会让有副作用的步骤执行多次。重试必须与幂等键、完成记录和补偿逻辑一起设计，否则只是把失败变成重复。

## 五、工程案例：一个多租户的批量分析场景

输入：某数据平台（示意）把 Agent 做成共享服务，承载四十个业务团队。任务分两类：夜间批量归因，单次三十分钟到两小时，允许中断；白天交互式问数，期望秒级响应。上线第一个月，暴露四个问题。

冲突一：队列混用。批任务与交互请求同队列，早上九点的问数请求排到八分钟。处理是拆双队列，交互权重 6、批任务权重 1，批任务在八点半之后标记为可抢占，抢占前必须已落检查点。结果早高峰等待压到一分钟以内，代价是批任务墙钟时间整体变长——这是明确的取舍，不是调参失误。

冲突二：认证失败引发的重试风暴。某租户密钥过期，SDK 把 401 当可重试错误，五次重试叠加二十并发，把下游配额打满，其他租户一起报错。处理是把错误分类写进运行时：认证与参数错误不重试，限流与超时可重试；同时给每个租户设重试预算（每分钟重试次数上限），超出即熔断并在返回里写明原因。

冲突三：滚动发布丢任务。旧实例收到终止信号后直接退出，运行中的归因任务没有检查点，用户界面却显示“已完成”。处理是三步终止：停止接单、落检查点、在宽限期内退出；调度器在实例失联后把任务标为未知状态，重排一次并提示这是重跑。这里的关键不是宽限期多长，而是状态机必须承认“未知”这个状态，不能把失联当成成功。

冲突四：配额只算入口。一个租户在循环里反复调用模型，入口配额早已通过，token 消耗在运行中累积到日额度的三倍。处理是把日额度拆到循环层，每次模型调用前检查剩余预算，超限时以 quota_exhausted 中断并保留已完成的部分结果。

结果：四个月后，重复执行归零，越权与串数据事件为零，早高峰等待稳定在一分钟内；代价是实例数上升约一半、检查点存储成为新的容量项、批任务平均完成时间变长。这些代价都写在容量规划里，而不是等出问题才发现。

## 六、边界与失败模式

租约依赖时钟。用本地时钟算过期时间，在时钟漂移或虚机暂停后会误判，必须用单调时钟或由调度器统一裁决，租约本身带版本号，旧版本续约直接拒绝。

内存队列不持久。进程崩溃时内存里的排队任务全部消失，用户只看到提交成功。队列至少要落盘，且入队与出队的顺序要能在重启后重建。

幂等键的生成位置决定重放是否安全。由入口生成、贯穿全链路是最稳的；由执行端临时生成，等于每次重跑都是新任务，重排就变成了重复副作用。

抢占只能回滚自己的状态。已经发出的外部请求、已经写入的下游数据不会因为你落过检查点就消失。可抢占的任务必须把外部动作设计成可补偿，或者干脆标记为不可抢占。

公平无法用单一指标证明。平均等待时间好看，可能只是某个租户被长期饿着。要按租户看等待时间分布，尤其是 P99 与最长饥饿时长。

## 七、落地检查清单

1. 任务有显式状态机，且包含“未知/失联”状态。判据是实例崩溃后，任务不会停在“运行中”超过一个租约周期。
2. 队列持久化。判据是杀掉调度进程重启，排队中的任务数量与顺序可恢复。
3. 租约用单调时钟或中心裁决。判据是把实例时钟回拨五分钟，不会产生双份执行。
4. 心跳间隔不超过租约的三分之一。判据是模拟一次网络抖动，不触发任务重排。
5. 终止流程为三步且宽限期大于最长单步耗时。判据是发布期间长任务的成功率不低于基线的 95%（示意阈值，按业务定）。
6. 幂等键由入口生成并写入任务记录。判据是同一任务重排两次，副作用只发生一次。
7. 错误分类驱动重试。判据是认证类错误的重试次数为 0，可在轨迹中查询到分类字段。
8. 配额分三层执行。判据是人为把日额度调到很小，任务在循环层被中断而不是跑完再报错。
9. 每次配额拒绝都返回原因与重置时间。判据是调用方能区分“排队中”与“额度耗尽”。
10. 按租户观测等待时间分布。判据是能随时回答“哪个租户过去一小时被饿得最久”。

## 八、常见误区与面试追问

**问 1｜加个任务队列就算 Agent 运行时了吗？**
不算。队列只解决“先来后到”，运行时还要有租约（防丢）、状态机（含未知态）、配额（防单租户吃满）与优雅终止（防发布丢任务）。缺一项，故障就会从队列漏到业务层。

**问 2｜权重怎么定才不算拍脑袋？**
按业务价值和服务目标校准，再用观测数据回验：看各租户等待时间分布与饥饿时长，看批任务被抢占的比例。权重是策略参数，必须有对应的验证指标，否则只是把公平问题换成了调参问题。

**问 3｜用 K8s 的自动扩缩容不就能解决了吗？**
扩容解决容量，不解决公平与交接。资源不够时扩副本有用；单租户吃满配额时，扩副本只会让更多副本一起被它吃满。调度策略与扩容策略是两件事。

**问 4｜幂等键应该由谁生成？**
入口生成，贯穿调度、执行与补偿。执行端只认键、不重新计算键值。由执行端临时生成，等于每次重跑都被当成新任务，重排立刻变成重复副作用。

**问 5｜抢占会不会导致活锁？**
会。被抢占的任务重排后又把配额抢回去，形成来回抢占。常见缓解是优先级衰减（被抢占一次降一级）或让出窗口（被抢占后一段时间内不再被优先调度）。没有衰减机制的抢占，只在理论上是公平的。

## 九、小结与延伸阅读

从脚本到运行时，变化的是约束：任务要排队，资源要隔离，长任务要租约与检查点，扩容要优雅交接，配额要分维度前置。模型能力决定上限，运行时决定这个上限能否被稳定地兑现。运行时不是 harness 的简单放大，而是把单次运行的约束扩展到多任务、多租户与故障域；判断一个平台是否成熟，看它在实例崩溃与流量突增时是否还能说清每个任务的状态。

延伸阅读建议：工程博客类可看任务队列的公平调度与租约设计；官方文档类可关注容器编排系统的优雅终止与资源配额；论文类可关注多租户系统中的噪声邻居与隔离研究。阅读时把“任务在故障时去了哪里”作为主线，这比调度算法本身更能暴露设计缺陷。
