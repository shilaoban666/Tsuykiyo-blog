## 一、开场问题：会调用工具的聊天框，算不算 Agent？

很多团队第一次做 Agent，是从给聊天模型接上三五个工具开始的：查订单、发邮件、读数据库。演示很顺，一旦放进真实业务，问题立刻暴露——模型查完订单忘了自己为什么查，发完邮件又重复发一遍，遇到工具报错就把异常文本原样复述给用户。表面看是提示词不够好，深层原因是系统只提供了“动作”，没有提供“闭环”。本文要回答的就是一个判定问题：一个系统在什么条件下可以被称为 Agent，而不是一段较长的提示词或一条固定的自动化流程。

这个问题之所以重要，是因为它决定了团队把工程预算花在哪里。如果把它当成提示词问题，投入会集中在措辞、示例和语气上；如果把它当成闭环问题，投入会落在状态管理、工具契约、终止判断与失败恢复上。前者在演示阶段见效快，后者才决定系统能不能在无人值守的夜里跑完一百个任务而不闯祸。两套答案对应两套验收方式：前者验收“答得像不像”，后者验收“在预算内把事做完且没有越界”。

## 二、概念界定：五要素与三条分界线

先把术语钉死。本文所说的 agent，是感知-决策-行动循环系统：它读取环境状态，基于目标选择动作，执行动作后再读取新的状态，如此往复，直到满足终止条件或触发预算上限。这个定义有三个关键词：循环、状态变化、可终止。缺少任何一项，都更接近“一次函数调用”而不是 Agent。

展开来是五个要素。目标，是系统要达成的可判定结果，而不是一句愿望；状态，是当前已知的事实集合，包括用户输入、工具返回、已执行动作的历史；动作，是 Agent 可以施加于外部世界或内部状态的操作，通常以工具调用形式出现；观察，是动作执行后返回的新信息，包括成功结果与结构化错误；终止，是明确判断“继续做没有意义”的信号，可能来自任务完成、明确失败、预算耗尽或人工中止。

用这五要素可以划出三条分界线。单轮问答没有状态推进，也没有动作，它只做一次映射，不属于 Agent。固定工作流有动作也有状态，但动作序列由人预先写死，模型只在个别节点做分类或抽取，它的控制权在人手里，属于“带模型节点的流程”。自主 Agent 则把“下一步做什么”的决定权交给模型，由循环控制层负责约束。三者不是先进与落后的关系，而是控制权与可预测性的不同配比。

还需要区分“工具调用”和“Agent”。工具调用是接口能力，它让模型能影响外部世界；Agent 是运行形态，它决定这些调用如何被组织成朝向目标的序列。一个系统可以有二十个工具却仍然是工作流，也可以只有一个工具却是完整的 Agent。判断标准不在工具数量，而在是否存在“观察—再决策”的回路。同样，harness 也不是 Agent 本身，它是承载模型、工具、上下文、权限与评测的运行骨架；骨架再完整，若没有目标牵引的循环，也只是被动执行的管道。

把自主性当成连续刻度比当成开关更好用：动作顺序完全写死是 0 分，模型只在固定节点做分类是 1 分，模型决定下一步但可用工具由阶段限定是 3 分，模型能自己加步骤、自己组合工具是 4 分。生产系统大多落在 1 到 3 分之间，收益也主要来自这一段。反过来，“我们的 Agent 不好用”最常见的错配是：按 5 分的期望设计，按 2 分实现，中间那几档约束一件没做。

## 三、机制拆解：一次闭环长什么样

最小闭环可以用十几行伪代码描述。注意其中三件事：状态是显式传递的，终止条件是运行时代码判断的，工具错误被当作观察而不是异常抛出。

```python
state = init_state(goal, context)
for step in range(MAX_STEPS):
    decision = model.decide(goal=goal, state=state, tools=tool_specs)
    if decision.kind == "finish":
        return finish(decision.answer, state)
    if decision.kind == "ask_human":
        return suspend(decision.question, state)
    result = tools.call(decision.name, decision.args)   # {ok, data, error}
    state = reduce(state, decision, result)            # 只追加可审计的事实
    if budget.exhausted(state):
        return fail("budget_exhausted", state)
```

这段伪代码里，工具的最小结构由四部分组成：名称、参数 schema、返回值、错误语义。名称要能表达副作用，例如 search_orders 与 refund_order 的语义强度完全不同；参数 schema 要能判别对错，枚举、必填与类型约束比自然语言描述更可靠；返回值要稳定，成功与失败共享同一外壳，避免模型在两种格式间猜测；错误语义要可行动，告诉模型“参数缺失”“权限不足”还是“下游超时”，并给出是否可重试。四者缺一，闭环就会在某个角落漏气。

再往下一层，状态更新函数 reduce 决定了系统是否可审计。稳妥的做法是只追加事实，不覆盖历史：每次工具调用记录参数、结果、耗时与决策理由，形成事件序列。这样即便最终答案错了，也能回放是哪一步观察被误读。反过来，如果状态是一个被反复覆盖的字典，故障排查就只能靠猜，重复执行与漏执行也难以区分。

还有一处容易被忽略：模型看到的工具列表应当按当前阶段裁剪。全量暴露会让选择空间过大，而按阶段给出少量工具，等于把一部分规划前置到工程侧，稳定且便宜。这也解释了为什么同样的模型在不同产品里表现差异巨大——差别往往不在模型，而在它每一步能看到什么、能做什么。

decision.kind 只有三个取值是刻意的：执行、结束、求助。三种取值对应三种运行时动作，语义闭合才能写成代码；如果放任模型输出“我觉得该换个思路”这类自由文本，控制层就只能把它整段当指令去猜。

## 四、工程取舍与反例

自主性不是免费的。每一步都要一次模型调用，步数上升会同时放大延迟、token 成本与出错概率；更麻烦的是不可控性——同一输入可能走不同路径，回归测试难以稳定复现。因此在工程上要主动设计“退化路径”：当任务步骤固定、验收标准清晰、时延敏感时，应把 Agent 退化为确定性工作流，只在小范围内保留模型判断。退化的时机可以写成规则：同一类任务连续多次（示意阈值 50）走同一条工具序列且无分支决策，就把这条路径固化成工作流，只在入口保留一次意图分类。

常见的反例有三类。第一类是“提示词包装”，系统提示写了几千字，要求模型“先思考再行动”，但没有任何状态机与终止判断，模型一旦跑偏就无限自我解释。第二类是“工具堆砌”，把几十个接口一次性塞给模型，缺少分组与使用场景说明，选择错误率随工具数量上升。第三类是“异常直抛”，工具失败时把堆栈或英文错误原样返回，模型只能道歉或编造成功，闭环在错误处理处断裂。

一个实用的收敛办法是给每次运行设四道闸：最大步数、最大 token、最长墙钟时间、最大成本。任一触发都返回“未完成 + 已完成部分 + 建议下一步”，让人或上层系统接手。这比让模型“再想想”更可靠，也便于把失败变成可统计的数据，而不是每次都要人工读日志。四道闸里最容易漏的是成本那道：步数与 token 都能从运行记录直接读，成本要折算成钱，团队往往觉得上线后再补，真出问题时才发现某个工具已经被循环调用了两百次。

## 五、工程案例：一封“已为您退款”的错误邮件

背景示意：某电商客服后台接入一个工单处理 Agent，四个工具——orders.get（只读）、orders.refund（写，不可重试）、mail.send（对外发送）、ticket.update（内部写）。目标由用户工单原文给出。

输入：“我 10 号下的单到现在没收到，订单号 ord_7f3a91c2d4e5，直接给我退款吧。”期望是判断该订单是否满足退款条件，满足则退款回信，不满足则说明原因并给出下一步。

实际轨迹（示意）：第 1 步 orders.get 返回 status=shipped，模型判断“已发货不能直接退款”，但没有终止；第 2 步调 mail.send，正文写“已为您办理退款，3 到 5 个工作日到账”；第 3 步再查订单，状态仍是 shipped，模型认为“上次可能没成功”；第 4 步第二次发送；第 5 步第三次……直到 12 步预算耗尽。三分钟对外发出 5 封同内容邮件，退款一次没发生，工单状态也没更新。

这不是提示词问题，是三个结构缺陷同时起作用：终止条件缺失，模型没有“完成态”判据，收尾只能靠预算；副作用等级没进运行时，mail.send 被当成可重试的普通工具，五次调用就是五次真实发送；观察语义错位，mail.send 返回 `{ok: true}` 只代表“邮件投递成功”，模型读成了“退款成功”，于是“再确认一次”退化成“再发一次”。

处理做了四件事。目标改写成可判定命题：“输出 decision 属于 {refund_ok, need_return, need_human} 之一并附证据”，decision 一旦产生就结束运行。退款前置条件下沉到工具定义，input_schema 之外增加 precondition（订单状态必须为 paid），由网关调用前校验，不满足直接返回 state_conflict，retryable=false，hint 指向退货流程。mail.send 标注 side_effect=non_retryable_write，幂等键由运行时按 ticket_id 加 template_id 生成，同一工单同一模板第二次调用直接返回首次结果并标记 deduplicated。返回值里增加“业务效果”字段，邮件工具返回 `{delivered: true, business_effect: none}`，模型不再把投递成功当业务完成。

结果（示意）：同类工单 200 条，重复对外发送 0 次，错误承诺退款 0 次，平均 4.2 步完成；其中 31% 落到 need_return，系统生成退货指引并挂起等人工确认。成本没有上升，步数减少抵消了新增的校验开销。

最值得看的是第四个改动：它没有增加任何能力，只是把“工具做了什么”和“业务上意味着什么”分开写。多数被归咎于“模型幻觉”的事故，工程上都能追溯到这类语义混用。

## 六、落地检查清单

1. **目标可判定**：能写出一个检查函数，输入状态、输出 pass/fail 加证据。写不出来，说明目标还是愿望。
2. **状态只追加**：任意一次运行都能从事件日志重放，重放得到的模型输入哈希与原始记录一致。
3. **终止四闸齐全**：步数、token、墙钟、成本四项都有上限，任一触发返回结构化“未完成 + 已完成部分”。
4. **工具返回同构**：成功与失败共享同一外壳（ok、code、data、retryable、hint），由网关强制，不靠工具作者自觉。
5. **写操作有等级**：每个写工具标注可重试与否，幂等键由运行时代码生成，模型无权填写。
6. **工具集裁剪**：单轮可见工具数量有上限（示意 12 个），每个描述里明确写出“何时不要用”。
7. **错误可行动**：错误码按“模型下一步做什么”分类，覆盖改参数、换工具、等待、查状态、找人、放弃六类。
8. **无进展熔断**：连续两次相同（工具、参数）调用，或状态未发生任何变化，立即停止并上报。
9. **轨迹可回放**：每次运行留下 prompt 哈希、候选动作、观测与决策理由，能回答“模型当时看到了什么”。
10. **退化路径存在**：至少有一类高频任务能被配置成确定性工作流，且切换不需要改代码。

## 七、常见误区与面试追问

**追问一：我们把系统提示写到三千字，要求它“先规划再行动”，这算 Agent 吗？**

答：不算，那只是把指令写得更长。判定看控制权在谁手里、有没有观察回流。如果模型输出被解析成固定序列的调用、中途不允许改，它就是一条用自然语言配置的工作流。提示词长度与自主性没有因果关系。

**追问二：工具越多能力越强，为什么不把所有内部 API 都接上？**

答：工具数量增加的是选择空间，不是能力。选择空间超过模型的分辨能力时，错误率上升得比覆盖率快。更实际的是契约成本：每个工具都要写清参数、返回、错误与副作用，维护五十个含糊工具的负担远大于五个精确工具。

**追问三：模型自己会说“完成了”，为什么还要用代码判断终止？**

答：因为模型看不到预算，也无法为自己的判断负责。它可以合理地认为任务完成，同时系统已经花了三倍成本，也可能在失败时坚持“再试一次就好”。终止是运行时的权力，不是模型的自我认知。

**追问四：复杂任务是不是应该直接上多 Agent？**

答：先看任务能否切成低耦合子问题，再看验收标准能否切分。两个条件都满足，多 Agent 的并行与分工才可能抵消协调成本；否则单 Agent 加更多工具通常更简单。

**追问五：给 Agent 加一层反思，是不是就能自我纠错？**

答：取决于信号从哪里来。只是让同一个模型“再看看对不对”，它倾向于确认自己，多跑两轮只是把错误论证得更长。有测试、校验器、外部检索或人工确认作为信号，反思才是纠错。

## 八、小结与延伸阅读

Agent 的判定不看提示词长度，也不看工具数量，而看是否存在以目标为牵引、以状态为载体、以动作为输出、以观察为反馈、以终止为边界的循环。工具调用是这个循环的接口，harness 是承载这个循环的运行骨架，二者都不能替代对闭环本身的设计。

延伸阅读建议分三类：论文类可关注 ReAct 与 agent survey 中对“推理—行动”交替的界定；官方文档类可对比主流厂商工具调用协议里对参数 schema 与错误码的约定；工程博客类可看各框架如何实现 plan-and-execute 与 supervisor 模式。阅读时重点看控制流与失败处理，而不是复述结论。
