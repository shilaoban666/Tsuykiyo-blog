## 一、开场问题：同一个模型，换个规划方式就忽好忽坏

很多团队做过这样的对比：同一个模型、同一套工具，直接让模型边想边做，任务大多能完成；换成先列完整计划再执行，简单任务变稳了，长任务却经常在第三步就偏离；再加一轮“执行后反思”，有时明显改善，有时只是把同一个错误论证得更自信。于是问题变成：规划范式到底在改变什么，什么任务该用哪一种？

答案不在“哪种更先进”，而在任务的两个属性：动作是否可逆，以及每一步是否能拿到可靠反馈。这两个属性决定了错误的代价与发现错误的时机，也决定了一种范式是省钱还是烧钱。

这两个属性还决定了另一件事：谁来承担“判断对错”的成本。ReAct 把判断摊到每一步，靠观察即时报错；Plan-and-Execute 把判断集中到验收环节，靠结构减少分歧；反思则额外买一次判断机会。范式之争常常是成本分配之争，而不是智能水平之争。

## 二、概念界定：三种控制流

ReAct 是最接近直觉的一种：模型在每一步交替产生推理与动作，动作执行后把观察拼回上下文，再决定下一步。它的控制流是短视的，只规划下一步，但因为每一步都看到最新观察，对环境的适应性最好。代价是全局性差，容易在局部最优里绕圈，且步数一多，早期目标容易被淹没。

Plan-and-Execute 把规划前置：先由模型产出步骤列表，再由执行器逐步完成，必要时才回到规划器修订。它的优点是全局结构清晰、可并行、可预算，适合步骤之间依赖弱、单步结果可判定的任务。缺点是计划基于执行前的信息，一旦环境在第三步发生变化，僵化的计划会把错误一路带到底。

反思循环则是在执行之后增加一次评估：对照目标检查结果，找出偏差，再决定重试、修补还是放弃。它可以是每步一次，也可以是整任务一次。反思的价值完全取决于评估信号从哪里来——如果只是让同一个模型“再看看对不对”，它倾向于确认自己；如果有测试、规则校验、外部工具或人工反馈，反思才是有效纠错。

三者并非互斥。工程上常见的组合是：用轻量计划定骨架，用 ReAct 处理每一步的不确定性，用带外部信号的反思做收尾校验。真正需要决定的是：计划做多细、反思多久触发一次、什么条件下重排整个计划。

还有一类常被误当成第四种范式的东西：让模型对同一问题采样多次再投票。它降低的是输出方差，不是规划能力——五次采样都基于同一份上下文，方向错了就错五次。把它当“反思”用，往往只是把开销翻倍。

## 三、机制拆解：把重规划写成条件

规划系统最容易犯的错，是把“重规划”交给模型的心情。可靠的做法是把它写成显式条件：只有满足特定信号时才允许改动计划，其余情况只修补当前步骤。下面是一段示意配置。

```yaml
planner:
  mode: plan_then_execute
  max_steps: 12
  plan_granularity: "one_verifiable_outcome_per_step"
  replan_when:
    - "step_failed_twice"
    - "observation_contradicts_assumption"
    - "new_hard_constraint_from_user"
  patch_only_when:
    - "single_step_timeout"
    - "missing_optional_parameter"
  reflect:
    after: each_step
    require_external_signal: true   # 测试、校验器、检索证据或人工确认
    max_reflect_rounds: 2
```

这段配置里有两个约束值得展开。第一，计划粒度以“一个可验证产出”为单位，而不是以“一次工具调用”为单位。粒度过细会让计划变成冗长的调用脚本，失去应变空间；粒度过粗则一步失败就无法定位。第二，反思必须绑定外部信号。没有信号的反思最多做一次，用于检查遗漏项；做两三轮就会退化为自我肯定，既烧 token 又掩盖问题。

重规划还需要区分“重排”与“修补”。重排会丢弃已有进度，成本高但能纠正方向性错误；修补保留进度，只替换当前步骤，成本低但可能治标不治本。一个可操作的判据是：如果失败的步骤影响了后续三个以上步骤的前提，就重排；如果只影响当前产出，就修补。这个判据可以用代码判断，不必再问模型。

另一个细节是计划的表示形式。自由文本计划对人类友好，对执行器不友好；结构化计划（步骤 id、依赖、验收条件、回滚动作）便于调度与审计，但生成成本更高。折中做法是让模型输出结构化骨架，再由渲染层生成人类可读的说明，二者同源，避免“说的”和“做的”不一致。

replan_when 里的第二条最容易被写空。“观察与假设矛盾”看起来很自然，但代码怎么知道矛盾？可行做法是把关键假设显式登记：执行前把“当前副本数为 3”“该接口幂等”这类前提写成断言，每步执行后校验断言。断言失败即矛盾，不依赖模型自述。

## 四、工程取舍与反例

把两个属性画成四象限，选择就清楚了。动作可逆且反馈密集，例如查资料、跑测试、改草稿，适合 ReAct 加轻反思，快速试错成本低。动作可逆但反馈稀疏，例如多步数据分析，适合 Plan-and-Execute，用结构换稳定。动作不可逆但反馈密集，例如线上变更，适合“计划 + 前置校验 + 人工审批”，反思必须发生在执行前。动作不可逆且反馈稀疏，例如对外付款，任何自主规划都不合适，应退化为确定性流程加双人复核。

常见反例有四类。第一类是“反思成瘾”，每一步都反思，调用次数翻倍（来源：示意），但评估信号仍是模型自评，结果只是把错误写得更长。第二类是“计划僵化”，计划生成后不允许修改，环境变了仍按原步骤执行，最后用一堆成功的小步骤拼出错误的总结果。第三类是“粒度错配”，把“打开网页、点击搜索、输入关键词”都列为计划步骤，计划变成操作录屏，模型失去了处理意外的空间。第四类是“反思无出口”，反思发现失败后没有降级路径，只能重试，直到预算耗尽。

还有一个组织层面的反例：把规划质量当成提示词问题，反复调措辞，却不记录每次失败发生在哪个步骤、属于哪类偏差。没有失败分类，就无法判断该换范式还是该补工具。可行的做法是给每次运行打三个标签：失败步骤、失败类型（信息缺失、工具错误、计划错误、验收错误）、是否可重试。积累几十条之后，范式选择就不再靠感觉。

## 五、工程案例：一次把线上变更交给 ReAct 的代价

背景示意：一个内部运维 Agent 负责调整各环境配置，工具包括读改 ConfigMap、改 Deployment、滚动重启、读日志。任务输入：“把 staging 的日志级别从 info 调到 debug，确认生效。”

失败轨迹（示意）：模型采用 ReAct，边看边做。第 1 步列出 3 个 pod，直接给其中 1 个 pod 打了环境变量补丁并触发重启，该 pod 变成 debug；第 2 步对第 2 个 pod 重复同样操作；第 3 步发现 Deployment 模板没改，于是修改模板并触发滚动更新，前两个 pod 被回收，改动一起丢失；第 4 步读日志确认“有 debug 输出”，判断成功退出。实际结果是：服务中断约 4 分钟，改动基本没留下，还留下一次非计划的滚动重启。

三个问题都出在范式与任务属性不匹配。动作不可逆（改 pod、触发重启都会中断服务），却用了短视控制流；验收信号是模型自评加“日志里有没有 debug 字样”，而不是读回 Deployment spec；计划粒度按“一次操作”而不是“一个可验证产出”，导致三次成功的操作拼出错误的总体结果。

处理分四步。其一换范式：改为 Plan-and-Execute，计划固定为三个可验证产出——改写 Deployment 模板（验收：读回 spec 的日志级别字段等于 debug）、滚动更新完成（验收：所有 pod Ready 且 replicas 一致）、生效确认（验收：抽查两个 pod 的调试端点返回值）。其二加前置约束：任何涉及重启的动作先做 dry-run 并输出 diff，人工确认后才执行，同时记录当前 revision 作为回滚点。其三反思绑定信号：只有验收断言失败时才进入反思，输入是读回的 spec、pod 事件与日志摘要，最多 2 轮，失败则回滚。其四重规划显式化：spec 读回不符 → 只修补当前步骤；pod 无法 Ready → 先回滚再重排。

结果（示意）：同类变更 23 次，服务中断 0 次，平均 4.1 分钟完成（原 6.8 分钟，主要省在不再反复试错），触发回滚 2 次，都是验收断言正确捕捉到的失败。改动里没有换模型，也没有加长提示词。

值得记住的是那三个“可验证产出”。一旦计划按产出而非按操作切分，验收就有了落点，重规划也有了判据——因为你能指出到底是哪个产出没达成，而不是笼统地说“好像没成功”。

## 六、落地检查清单

1. **可逆性已登记**：每个工具标注 reversible／compensable／irreversible，不可逆动作必须前置校验或人工确认。
2. **每步有外部验收**：每个步骤能指向一个外部检查（测试、read-back、断言），而不是模型自评“已完成”。
3. **粒度对得上**：计划里每个步骤都能写成一条验收断言；写不出断言的步骤说明切得太细或太粗。
4. **重规划条件是代码**：replan 的触发条件可枚举、可判定，不依赖模型判断“要不要改计划”。
5. **修补与重排有判据**：失败影响三个以上后续步骤的前提就重排，否则修补，判据落在代码里。
6. **反思有出口**：max_reflect_rounds 有上限，超限后必须有降级路径（回滚、转人工、放弃），不允许只重试。
7. **计划四字段齐全**：步骤 id、依赖、验收条件、回滚动作。缺回滚动作的不可逆步骤应被拒绝执行。
8. **假设显式登记**：执行前把关键前提写成断言，执行后逐条校验，“观察矛盾”才有客观含义。
9. **失败有分类**：每次运行记录失败步骤、失败类型与是否可重试，能按类型统计，而不是只统计成功率。
10. **反思成本可计量**：统计反思轮次占总步数与占总 token 的比例，超过阈值告警。

## 七、常见误区与面试追问

**追问一：反思多跑几轮是不是更稳？**

答：没有外部信号时，多跑几轮只是让模型把自己的结论重复论证几次，成本上升、结论不变。有信号时，一轮通常就够定位偏差。把轮次上限设成 2 并加降级路径，比调高上限有效。

**追问二：Plan-and-Execute 是不是比 ReAct 更高级？**

答：不是升级关系，是成本结构不同。计划前置把判断集中到验收，省的是随机的试错；代价是对环境变化的适应差。步骤依赖弱、单步可判定时才划算，反过来就是给自己上枷锁。

**追问三：计划写细一点，是不是就不容易跑偏？**

答：细到“一次工具调用”就变成脚本，模型失去处理意外的空间；跑偏通常来自假设错了，而不是步骤不够细。判断标准是每个步骤能不能对应一条验收断言，能对应就够了。

**追问四：模型自己说任务完成了，为什么还要跑一遍校验？**

答：因为完成感来自文本连续性，不来自事实。校验是把“它认为”换成“可观测”，尤其不可逆动作，验收必须在外部发生。省这一步，等于把失败推到用户那边发现。

**追问五：能不能用一套规划逻辑覆盖所有任务，靠配置切换？**

答：配置可以切换参数，切不了代价结构。可逆性不同的任务，验收位置、审批位置、重试策略都不同，这些是代码结构，不是开关。强行统一的结果通常是：安全的任务被拖慢，危险的任务被放开。

## 八、小结与延伸阅读

ReAct 用适应性换全局性，Plan-and-Execute 用结构换灵活，反思用额外调用换纠错机会。选择它们时先问两件事：这个动作做错了能不能撤回，这一步做完有没有独立信号判断对错。可逆且反馈密集就允许短视，不可逆就前置校验，反馈稀疏就加强结构，三者都不满足就不该交给自主规划。换句话说，范式的价值在于匹配错误的代价与发现的时机，而不是提供一种通用的思考姿势。

延伸阅读建议：论文类可对比 ReAct、Plan-and-Solve 与 Reflexion 的控制流差异，重点看它们何时产生额外模型调用；工程博客类可看主流框架对 plan-and-execute 与 supervisor 的实现说明；官方文档类可关注编排框架中条件边与检查点的用法。阅读时把“何时重规划”当作核心问题，而不是记住某个范式的名字。
