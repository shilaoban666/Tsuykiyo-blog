## 一、开场问题：每次调试都要等模型

做过 Agent 的人大概都有这个体验：改一行提示，跑一次任务，等十几秒，输出还是不对；再改一行，再等十几秒。如果任务里有五六个工具调用，一次完整跑下来要一分钟以上，其中大部分时间花在等网络。更麻烦的是，同样的输入两次跑出来的结果不同，你无法判断是这次改动有效，还是模型本来就抖。

于是调试变成了一种体力活：靠反复试跑来积累直觉，而不是靠断言来验证假设。本文讨论的是怎样把本地开发环境做成“可重放、可断言”的形态：轨迹能按步重演，外部依赖能用夹具替代，模型响应能缓存，失败场景能主动构造。

## 二、概念界定：三件套与两条时间线

本地开发环境的核心是三件套：轨迹、回放、夹具。轨迹是运行时写下的事件序列，每一步包含模型输入、决策、工具调用、工具返回与耗时。回放是拿一份轨迹重新走一遍流程，可以选择“照原样重演”或“在某一步替换输入后继续”。夹具是预先录制或手工构造的外部响应，用来替代真实 API，让测试在无网络环境下稳定运行。

两条时间线要分开：开发时间线与运行时间线。开发时间线关心“我改的这行有没有用”，需要快速反馈与可比较的对照；运行时间线关心“线上这次为什么失败”，需要完整证据与不可篡改的记录。两者共用同一份轨迹格式，但用途不同：开发时追求可编辑，运行时追求只追加。

判断一个本地环境是否合格，可以看三个能力：能不能在任意一步暂停并查看当时的完整上下文；能不能修改某一步的输入或工具返回后继续跑；能不能在没有网络的情况下把一组任务跑完并给出通过与否。三个能力具备，调试才从“试”变成“验”。

补一条容易被忽略的要求：轨迹要带版本指纹。这份轨迹是在哪个模型、哪版提示、哪份工具清单下产生的，必须写在文件里。没有指纹，一年后回放出来的结果与当时无关，你甚至无法判断差异来自代码还是来自环境。

## 三、机制拆解：轨迹格式与假工具

先定轨迹格式。一条轨迹由若干事件组成，事件类型至少包括：run_start、model_call、decision、tool_call、tool_result、run_end。每个事件带步号、时间戳、父事件引用与负载。下面是一段示意。

```json
{
  "run_id": "r-20261113-0412",
  "events": [
    {"step": 0, "type": "run_start", "input": {"goal": "退款申请核查"}},
    {"step": 1, "type": "model_call", "prompt_hash": "p-7f2a",
     "context_tokens": 3120, "latency_ms": 1840},
    {"step": 1, "type": "decision", "kind": "tool",
     "tool": "get_order", "args": {"order_id": "A-1024"}},
    {"step": 1, "type": "tool_result", "ok": true,
     "data": {"status": "paid", "amount": 199}},
    {"step": 2, "type": "decision", "kind": "finish",
     "answer": "订单已支付，可进入退款流程"}
  ]
}
```

有了这份格式，回放器可以按步重演：在第 1 步之前插入断点，查看模型当时看到的完整消息；把 tool_result 的 data 改成 {"status": "refunded"}，继续跑，看 Agent 会不会重复退款；把某一步的决策替换成“调用另一个工具”，观察后续分支。这些操作在真实环境里要么做不到，要么代价很高。

回放器至少要有三种模式，混用会出事。严格模式：所有模型调用与工具返回都从轨迹读取，不允许真实调用，用于确定性回归。宽松模式：仅工具返回从夹具读取，模型调用走真实，用于“改了提示想立刻看效果”。分叉模式：从某一步起改为真实调用，用于探索“如果当时换一个决策会怎样”。报告里必须写明用了哪种模式，否则读者无法判断结论的适用范围。

假工具是第二件基础设施。每个工具至少要有三个版本：成功桩，返回固定结构的数据；失败桩，返回指定错误码与可重试标记；慢响应桩，延迟指定时间后返回或超时。三个版本覆盖了大多数分支，而且行为完全确定，测试可以断言“遇到不可重试错误时，Agent 应该在一步内终止并上报”，而不是“看它这次表现如何”。

模型响应也要能缓存。把（提示摘要、工具列表、上下文摘要）作为键，把模型返回作为值存下来，下次命中直接返回。缓存的好处是快与可复现，风险是掩盖了模型的真实波动。稳妥的做法是缓存只用于回归测试，探索性开发仍走真实调用，并且定期清空缓存重跑，确认结果不依赖旧缓存。

成本可控的本地评测闭环由三部分组成：一个小规模任务集（覆盖主要路径与典型边界）、一套确定性夹具、一个每日回归任务。任务集不求大，但要求每个任务都有明确的通过断言。每日回归跑完给出三件事：通过数、新增失败、与昨日的差异。差异比绝对值更重要，因为它能告诉你今天的改动打破了什么。

## 四、工程取舍与反例

第一个取舍是真实与仿真。全真实环境最可信，但慢、贵、不稳定；全仿真最快，但可能与线上脱节。可行的分层是：单元级用假工具，集成级用录制回放，发布前用真实环境跑一小批冒烟。三层各司其职，不要指望一层解决所有问题。

第二个取舍是轨迹的详细程度。记录全部上下文，回放最完整，但存储与脱敏成本高；只记摘要，便宜但排查时缺证据。折中是“摘要常驻、原文按需”：默认存哈希与长度，开启调试模式时存原文，并设置保留期限。

第三个取舍是本地与云端的一致性。本地跑通、线上失败，常见原因是环境差异：模型版本、工具权限、网络超时、索引版本。减少差异的办法是把这些配置也纳入本地环境，并在启动时打印一份“环境指纹”，线上失败时先比对指纹。

反例有三类。其一是“日志当轨迹”：只打了一行行文本日志，没有结构化事件，无法按步回放，排查靠肉眼拼接。其二是“夹具太完美”：所有假工具都返回成功，错误路径从未被测试，线上第一次遇到限流就崩。其三是“本地评测集污染”：任务集里的样本被反复用来调提示，最后通过率很高，但换一批任务就原形毕露。

还有一类反例是“回放不可信”。回放时用了新的模型版本或新的提示，却没有在轨迹里标注，导致“回放通过”与“线上失败”无法对齐。回放必须锁定版本，并在报告里写明用的是哪份配置。

本地环境还有一个隐性收益：它让失败可以被分享。一份轨迹文件加一份配置指纹，就能让同事在自己的机器上复现同一个问题，而不必约时间一起看线上环境。这种可传递性，往往比省下的那点等待时间更值钱。

## 五、工程案例：一次回放不可信事件

以下场景为示意，数字用于说明量级，不代表任何真实系统。

某团队的客服 Agent 有个偶发问题：遇到含多个订单号的会话时，偶尔只处理第一个。他们把一条线上失败轨迹录回本地，改了提示里的分号处理逻辑，回放三条轨迹全部通过，于是发布。上线两小时后同样的输入再次失败。

11:00 复现失败后，值班人做了三件事。第一，把线上那条失败轨迹与本地回放的那条并排 diff：事件结构一致，参数一致，但本地轨迹里模型给出的决策是“逐个处理”，线上是“只处理第一个”。第二，看回放报告，发现报告里只写了“strict 模式，3 条全通过”，没有记录用的是哪版模型与哪版提示。第三，查配置中心，发现回放当天团队把模型升级到了一个新别名，而轨迹是三天前录的。

根因有两层。表层是版本未锁定：回放走了新模型，行为与录制时不同，却因为用的是同一批夹具而被误认为“同一条路径”。深层是假工具的覆盖不足：那条轨迹里工具返回的是“成功”，但线上失败还有一半原因是某个查询接口因权限调整返回 403，本地夹具里根本没有这个分支。

处置分了四步。第一步，给轨迹文件加 config 块，写死 model_id、prompt_hash、tool_manifest_hash 与索引摘要；回放器启动时对比当前环境，不一致就拒绝启动并提示“请指定 --config 或重新录制”。第二步，给假工具补上权限拒绝桩，并把任务集里“权限变更”“下游超时”两类边界各补三条。第三步，回放报告改为强制打印模式与版本指纹，并把“本次回放覆盖了哪些夹具分支”列为必填栏。第四步，把“回放通过”从发布门禁的充分条件降级为必要条件，发布前仍要跑一次真实冒烟。

复盘有三条结论。其一，回放的绿色只证明“在这份配置下这条路走得通”，不证明线上走得通，除非版本被钉死。其二，夹具的覆盖面决定了回放的价值上限：只有成功返回的夹具，回放只能验证 happy path，而线上失败大多发生在错误分支。其三，报告要写清“用了什么”，而不是只写“结果如何”；前者让人判断结论能不能用，后者只能让人盲目相信。

## 六、落地检查清单

以下九条按“能不能靠本地环境挡住一次回归”设计，每条带判据。

1. 轨迹是结构化事件流。判据：能按步号取出某一步的完整模型消息与工具返回，不依赖文本日志拼接。
2. 每条轨迹带配置指纹。判据：文件里有 model_id、prompt_hash、tool_manifest_hash；缺任何一项即视为不可回放。
3. 回放默认锁定版本。判据：当前环境与轨迹指纹不一致时，回放拒绝运行而不是静默继续。
4. 回放模式显式声明。判据：strict、loose、fork 三种模式在报告里可见；同一批结论不混用模式。
5. 假工具至少三态。判据：成功、不可重试失败、超时各有一个桩，且都能被任务集触发。
6. 缓存可控。判据：有清空缓存的命令，且回归模式默认启用、探索模式默认关闭。
7. 断点可查看上下文。判据：能在任意一步暂停并导出当时的消息数组与 token 数。
8. 无网络可跑完整任务集。判据：断网后跑一遍，通过率与联网时一致。
9. 每日回归给出差异。判据：报告包含今日通过数、新增失败清单、与昨日的差异；差异项有人认领。

清单之外还有一个软要求：单个任务的本地跑通时间要在一分钟内。超过这个数，人就会跳过验证直接发布。

## 七、常见误区与面试追问

**问一：有了线上日志，为什么还要本地回放？**
线上日志回答“发生了什么”，回放回答“如果换一种决策会怎样”。日志是不可编辑的历史，只能看；回放可以改一个工具返回、换一个分支，从而验证假设。另一个现实原因是成本：线上试错的代价是真实用户，本地试错的代价是几秒钟。

**问二：轨迹要不要存全量上下文？**
默认不存。全量上下文里有用户隐私、有长文档，存储与合规成本都高。可行做法是存哈希加长度，排查时凭授权回捞原文，并设置保留期限。需要权衡的是“事后能不能查清”，如果业务对可追溯性有硬要求，就对该类任务单独开启原文留存。

**问三：夹具和模型缓存有什么区别？**
夹具替代的是外部系统的响应，缓存替代的是模型的响应。两者都会过期，但过期方式不同：夹具过期是接口契约变了，缓存过期是模型行为变了。混在一起管理会导致排查时无法判断“这次差异是数据旧了还是模型变了”，所以要分开存、分开清。

**问四：本地回放能替代线上测试吗？**
不能。回放的世界是你录下来的那个世界，真实世界的输入分布、权限状态、下游抖动都在变。合理的位置是：回放负责挡住已知的回归，线上小流量负责发现未知的分布。把回放当发布门禁的替代品，等于假设世界不再变化。

**问五：小团队只有半天时间，先做什么？**
先做两件事：把当前运行的决策与工具返回写成结构化 JSON（不用框架，几十行代码），再写一个只读的轨迹查看器（按步打印消息）。这两件事做完，排查效率立刻变化，因为你不再靠文本日志猜。回放器与夹具可以等有第二个人用的时候再做，那时需求也更清楚。

## 八、小结与延伸阅读

本地开发环境的价值，是把 Agent 的不确定性收敛到可控范围：轨迹让每一步可见，回放让假设可验证，夹具让外部依赖可确定，缓存与每日回归让成本可控。四者合起来，调试才从“多跑几次看看”变成“改一处、验一处”。

判断这套环境是否真的有用，只需看一件事：同事能不能只拿一份轨迹文件，在自己的机器上复现你遇到的问题。能，说明失败是可传递的；不能，说明你仍然只有一个“在我机器上是好的”说法。

延伸阅读建议：官方文档类可看调试器的断点能力与测试框架的 fixture、snapshot 机制；工程博客类可看智能体开发循环与回放调试的实践；开源仓库类可看轨迹查看器与 mock 工具的设计，重点看事件模型如何组织。
