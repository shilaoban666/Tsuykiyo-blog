## 一、开场问题：安全评审开成了表态会

一个 Agent 项目上线前开安全评审，会议室里坐满了人。安全团队说“要注意最小权限”，架构师说“我们有审计日志”，产品经理说“用户体验不能受影响”。两个小时后会议结束，结论是“总体可控，建议上线”。上线第三周，一个本应只读的客服助手被发现有写权限，把一条测试数据写进了生产库；查日志时又发现，日志里只有工具名，没有参数，无法确定写了什么。

这场评审的问题不在于没人重视安全，而在于讨论停留在原则层面：每个人都在表态，没有人逐项确认。原则无法被验收，清单可以。本文把上线前的安全检查拆成可勾选的条目，每条给出判定口径与责任人，让“是否安全”变成“哪些项已确认、哪些项未确认”。

## 二、概念界定：清单的三条原则

第一条原则是“可验证”。每一条都不能是“应妥善管理密钥”这种无法判定的话，而要写成“生产环境密钥不写入代码仓库与镜像，且可在不重启服务的情况下轮换”。能验证，才能打勾；不能验证，就只是愿望。

第二条原则是“有责任人”。每条检查项要明确谁提供证据、谁审核。安全团队不可能独自完成所有检查，权限配置是平台团队的事，数据分级是业务团队的事，审计字段是开发团队的事。责任不清，清单就会变成一张没人认领的表格。

第三条原则是“分级放行”。不是所有项都必须在上线前完成，但未完成项必须显式记录风险、补偿措施与复核时间，并由有权限的人签字。允许带风险上线，不允许带着未知上线。

清单本身也要版本化。每次上线用的清单版本、勾选结果、例外项，都应归档，事后复盘时才能回答“当时检查了什么、漏了什么”。

## 三、机制拆解：三组检查项

清单按三组组织：权限、数据、审计与应急。每组给出关键条目与判定口径。

```yaml
checklist: agent-release-v3
groups:
  permission:
    - id: P1
      item: 默认拒绝，工具权限按任务授予，任务结束即回收
      evidence: 权限配置导出 + 一次越权调用的拒绝记录
    - id: P2
      item: 高风险工具（写库、付款、对外发送）需二次授权或人工确认
      evidence: 审批流截图 + 一次真实拦截日志
    - id: P3
      item: 密钥不落代码与镜像，支持轮换，泄漏有吊销流程
      evidence: 仓库扫描报告 + 轮换演练记录
  data:
    - id: D1
      item: 输入输出按敏感级别分类，敏感数据不进入不受控的第三方
      evidence: 数据流图 + 出口白名单
    - id: D2
      item: 记忆与日志有保存期限，用户删除请求可贯穿两者
      evidence: 删除演练：请求后检索不到残留
    - id: D3
      item: 提示与上下文中不包含未脱敏的生产数据
      evidence: 抽样检查记录
  audit:
    - id: A1
      item: 每次工具调用记录参数、结果、来源与耗时
      evidence: 一条完整轨迹样例
    - id: A2
      item: 高风险动作有阈值告警，告警可达值班人
      evidence: 一次告警演练
    - id: A3
      item: 可一键停用，停用后任务可安全中断并可恢复
      evidence: 停机演练记录
```

这三组条目覆盖了最常见的失守点。权限组防的是“能做的事超出该做的事”，数据组防的是“数据流到了不该去的地方”，审计组防的是“出了事查不清、停不下”。

每条都要有判定口径，否则打勾仍然是表态。以 P1 为例，“默认拒绝”不能只看配置文件，要实际发起一次越权调用并确认被拒绝；以 D2 为例，“删除请求可贯穿”不能只看代码，要真的提交一次删除请求，然后在记忆与日志里检索残留；以 A3 为例，“可一键停用”要实际演练，确认正在运行的任务能中断、已产生的副作用有记录、恢复后不会重复执行。

应急停机是最容易被写成“有预案”的一项。可验证的版本是：停机开关的位置、谁有权按、按下后发生什么、正在执行的任务如何处置、恢复时如何避免重复副作用。这五个问题都能答上来，才算有停机能力。

审计字段要一次定好。最小集合包括：任务 ID、步骤号、工具名、参数摘要、结果状态、耗时、调用者身份、策略判定结果。参数摘要要能在需要时还原，但不能把敏感原文长期留存，折中是存哈希加脱敏片段，必要时凭授权取原文。

日志的保存期限要与合规要求对齐，而不是“永久保留最安全”。保留越久，泄漏面越大、删除成本越高。可行的做法是按数据级别分档：敏感操作日志短期保存并加密，普通运行日志按排障需要保存，到期自动清理，清理动作本身也要留痕。

## 四、工程取舍与反例

第一个取舍是检查成本与上线速度。全量检查会拖慢发布，抽查又可能漏。可行的做法是按变更范围决定检查深度：只改提示的发布走轻量清单，涉及权限、数据流、外部依赖的发布走全量清单。

第二个取舍是集中管控与团队自治。平台统一管控一致性好，但业务团队觉得慢；团队自治灵活，但标准容易漂移。折中是“平台定基线、团队做增量”，基线项不可豁免，增量项由团队按业务风险补充。

第三个取舍是阻断与告警。阻断能防止事故，但误判会影响业务；告警不打断业务，但依赖人响应。通常对不可逆动作阻断，对可疑行为告警，并确保告警有人接、有处置时限。

反例有三类。其一是“清单当文档”：写完就归档，上线时不逐项核对，出事才发现某项从未验证。其二是“证据造假”：用配置文件截图代替实际演练，配置写着拒绝，实际因为一个默认放行而没有生效。其三是“例外无主”：某项未达标，标注“后续处理”，但没写谁处理、何时处理，最后永远不处理。

还有一类反例是“只查上线不查变更”。上线时检查得很严，上线后加了一个工具、改了一条权限，没人复核。清单应绑定变更：权限、工具、数据流发生变化时，相关条目要重新确认。

清单的最后一页应当留空，专门写“本次未覆盖的范围”。例如“本轮未验证多租户隔离”“未测试模型供应商故障切换”。写清楚没查什么，比声称什么都查了更可信；读清单的人也能据此判断，这次上线到底承担了哪些未知。

## 五、工程案例：一次越权写入事件

以下场景为示意，数字用于说明量级，不代表任何真实系统。

某客服 Agent 的定位是“只读”：查订单、查物流、生成答复。上线第三周，数据团队发现生产库里多了一批状态为“测试”的订单，创建者标记为客服账号。追查发现，这个 Agent 有一个“创建补偿工单”的工具，权限模板是从另一个服务复制来的，那个服务确实需要写权限，复制时把写库权限一起带了过来。

发现路径并不体面：不是监控发现的，是数据团队在做对账时看到脏数据。值班人随后查日志，日志里只有工具名与耗时，没有参数，也没有调用者身份。于是三个问题同时暴露：谁写的、写了什么、为什么权限会在。

权限问题的根因在评审环节。评审时安全团队问过“是否最小权限”，平台团队回答“按模板分配”，双方对“模板里有什么”都没有逐项核对。模板是从别的服务复制的，复制动作发生在半年前，没有任何人重新审过。清单里有“默认拒绝”这一条，但当时的勾选依据是模板文档，而不是实际调用测试。

数据问题的根因在环境隔离。这个 Agent 的沙箱只隔离了网络，没有隔离数据库连接；写权限一旦存在，就能直接落到生产库。团队此前的假设是“只读 Agent 不需要数据隔离”，这个假设在权限失误面前失效。

审计问题的根因在字段设计。日志框架默认只记工具名与结果码，参数被视为“可能含敏感信息”而不落盘。这个决定在隐私上是对的，但没有配套的“参数摘要 + 授权回捞”机制，于是出了问题反而查不清。

处置分四步。第一步，回收写权限，改为按任务授予，任务结束即回收；同时把权限模板纳入评审对象，模板变更需要重新确认。第二步，补审计字段：参数存哈希与脱敏片段，敏感原文加密且凭审批回捞。第三步，给数据库连接加只读账号，写操作必须经由受控服务。第四步，清理脏数据并通知下游，同时把这次事件写成一条回归用例：以只读身份调用写工具，必须被拒绝。

复盘有三条结论。其一，权限错误往往不是“有人故意放开”，而是“复制粘贴时没看内容”，所以模板本身要进评审。其二，清单上打勾的依据必须是实际调用记录，而不是配置文件——配置文件说拒绝，运行时可能因为一条默认规则而放行。其三，审计字段要在上线前定，事后再补，历史数据永远补不回来。

## 六、上线前最后 10 分钟

清单是发布前几天的活，最后十分钟做的是另一件事：确认那些“一旦出错就无法挽回”的开关都在正确位置。以下七项，按顺序过一遍。

第一，停机开关。找到它，确认自己有权限，并在预发按一次，看任务是否真的中断、日志是否留下记录。第二，本次变更的权限 diff。只看这一版新增或放宽了什么，逐条问“为什么需要”。第三，日志级别。确认关键字段没有被为了降噪而关掉，尤其是参数摘要与调用者身份。第四，告警通道。发一条测试告警，确认值班人的手机真的响了。第五，回滚路径。把旧版本号与回滚命令写在发布单上，确认旧配置仍然可用。第六，出口与脱敏开关。确认外发走代理、敏感字段按分级脱敏。第七，观察窗口与判停指标。约定上线后看哪三个指标、超过什么阈值就停。

这七项的共同点是：它们都不增加功能，只降低“出事之后无法收场”的概率。十分钟换的是确定性，不是完备性。

## 七、落地检查清单

以下九条是把上面的三组条目变成可以按顺序核对的表，每条给出判据与证据形态。

1. 权限默认拒绝且被实测。判据：以无权限身份调用高危工具被拒绝；证据是一条拒绝日志。
2. 高危工具二次授权。判据：写库、付款、对外发送三类动作中至少抽取一次，走完审批或确认流程。
3. 密钥不进代码与镜像。判据：仓库与镜像扫描无命中；轮换演练能不停机完成。
4. 数据分级落到字段。判据：数据流图上每个出口都标了级别；敏感字段进入第三方前被拦截或脱敏。
5. 删除请求可贯穿。判据：提交一次删除，在记忆与日志中检索不到残留，清理动作有记录。
6. 审计字段完整。判据：抽一条轨迹，能回答谁、何时、调了什么工具、参数摘要、结果、耗时、策略判定。
7. 告警可达。判据：演练一次阈值告警，值班人在约定时限内确认收到。
8. 停机可演练。判据：停机后运行中的任务被中断、副作用有记录、恢复不重复执行。
9. 例外有主。判据：每条未完成项有风险描述、补偿措施、责任人与复核日期。

清单的用法是逐条要证据，而不是逐条打勾。证据拿不出来，就记为例外，不要记成通过。

## 八、常见误区与面试追问

**问一：每次上线都要全量跑一遍清单吗？**
不必，但要看变更面。只改提示文案的发布，权限与数据流没有变化，可以走轻量清单；涉及权限、工具、数据流、外部依赖的变更必须全量。判断标准是“这次改动是否改变了 Agent 能做的事或能碰到的东西”，与代码行数无关。

**问二：安全团队不批，怎么推进？**
把争议从“要不要做”变成“做哪一档”。给出三档方案：完整实现、基线加补偿措施、限期整改，并写明每档的残余风险。多数僵局来自双方对风险的量级没有共识，而不是立场对立。给出可验证的补偿措施，比反复解释“业务很急”有效。

**问三：审计日志存多久合适？**
按数据级别分档，而不是统一一个数字。敏感操作日志短期保存并加密，普通运行日志按排障需要保存，到期自动清理。要点是“删除也要留痕”，否则无法证明清理真的发生了。存得越久泄漏面越大，这个成本要显式计入，而不是默认“留着更安全”。

**问四：平台已经有沙箱，还需要权限清单吗？**
需要。沙箱隔离的是执行环境，权限清单管的是“这个任务被允许做什么”。两者覆盖不同层面：沙箱能挡住文件系统与网络的越界，但挡不住“用本来就有权的工具做不该做的事”。反过来，权限清单也挡不住实现层的漏洞。

**问五：怎么证明“一键停机”真的可用？**
只能演练。演练要覆盖四件事：谁有权按、按下去多久生效、正在执行的任务怎么处置、恢复后会不会重复执行。演练记录要包含时间戳与观察到的现象，而不是一句“已演练”。没有演练记录的停机能力，等同于没有。

## 九、小结与延伸阅读

上线安全的落点不是表态，而是可验证的条目：权限是否默认拒绝并实际拦截过、数据是否有分级且有删除演练、审计是否记全并真的能停。每条有证据、有责任人、有例外记录，清单才有意义。

一句话判断清单的质量：随便挑一条，问“证据在哪”，如果没人能在一小时内拿出来，这条就还没算完成。

延伸阅读建议：标准规范类可看人工智能风险管理框架与管理系统标准中的控制项结构，学习它如何把原则拆成可审计条目；官方文档类可看云厂商的密钥管理与审计日志最佳实践；工程博客类可看公开的上线安全评审模板，重点看它如何定义证据。
