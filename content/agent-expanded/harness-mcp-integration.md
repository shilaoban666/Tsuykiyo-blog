## 一、开场问题：接一个很顺，接十个就乱

第一次接 MCP，体验通常很好：起一个 server，声明几个工具，host 自动发现，模型马上能用。于是团队把十几个内部系统都包成 server，问题随之而来。两个 server 都有 search 工具，模型分不清该用哪个；一个 server 的参数是 snake_case，另一个是 camelCase，schema 映射频繁出错；某个 server 超时后不返回，整个对话卡住；更麻烦的是，一个 server 返回的文档里夹带了“忽略之前的指令”，模型差点照做。

这说明协议解决的是“怎么接”，没有解决“接进来之后怎么管”。MCP 让工具的发现与调用有了统一形状，但权限、配额、结果可信度、故障隔离仍然要由 harness 承担。把协议当成安全边界，是接入阶段最常见的误判。

单个 server 出问题是孤立的，十个 server 出问题会互相放大：一个慢 server 占住的并发槽位，让另一个本来正常的 server 调用排队；一份被污染的返回，经由共享上下文影响后续所有判断。接入数量上来之后，harness 要回答的已经不是“调用能不能成功”，而是“局部失败会不会外溢”。

## 二、概念界定：host、client、server 与能力协商

MCP 的角色划分是理解接入细节的起点。host 是承载模型的宿主应用，负责决定哪些 server 可用、哪些工具暴露给模型；client 是 host 内部与单个 server 保持连接的组件，通常一个 server 一个 client；server 对外声明能力，例如提供工具、资源或提示模板。三者之间通过结构化消息通信，工具发现、调用与结果返回都有明确的消息形状。

能力协商发生在初始化阶段：双方交换协议版本与支持的能力集合，确认哪些特性可用。版本不匹配时要有降级策略，例如高版本客户端连接低版本 server，应关闭对方不支持的字段，而不是直接失败。工具发现返回名称、描述与输入 schema，host 需要把它们映射成内部工具定义，并处理命名冲突、类型差异与缺失字段。

降级要分成两类看。字段级降级，例如某个可选的进度回调不支持，关掉即可，主流程不受影响，可以自动处理；语义级降级，例如分页语义从 cursor 变成 offset，消息能通但结果会错，必须人工确认，通常意味着这个版本的 server 不在本次放行范围内。把两类降级混在一个开关里，结果是要么过度保守、要么悄悄出错。

传输层同样影响接入形态。stdio 适合本机进程，生命周期与 host 绑定，进程退出即连接断开，异常暴露得直接；http 适合远端服务，需要单独处理鉴权、重连与背压。两者的超时语义也不同：stdio 卡住往往意味着进程挂死，http 卡住可能只是网关排队。按同一套超时参数处理两者，是接入初期最省事的做法，也是后期最难排查的那类故障的来源。

需要强调的是，MCP 的“工具”是协议层的描述，不等于 harness 的“能力”。协议能告诉你这个 server 声称可以删文件，但不能告诉你当前用户是否有权删、这个动作是否可重试、返回值是否可信。把这些判断留给协议，等于把安全交给了对端。

## 三、机制拆解：映射、调用与隔离

接入的核心工作可以分成四段：发现与映射、调用与超时、结果归一化、信任隔离。下面是一段示意配置，展示命名空间与信任级别的处理。

```yaml
mcp:
  servers:
    - name: "crm"
      transport: "stdio"
      trust: "internal"
      namespace: "crm"
      tool_prefix: "crm_"
      timeout_ms: 8000
      max_concurrency: 4
    - name: "web-research"
      transport: "http"
      trust: "external"
      namespace: "web"
      tool_prefix: "web_"
      timeout_ms: 15000
      max_concurrency: 2
      sanitize_output: true
  mapping:
    on_name_conflict: "prefix_then_dedupe"
    on_schema_mismatch: "reject_with_reason"
    drop_unknown_fields: true
  isolation:
    per_server_circuit_breaker: {errors: 5, window_s: 60, cooldown_s: 30}
    context_quarantine: true      # 外部内容不进入系统规则层
```

命名冲突是最先遇到的问题。两个 server 都提供 search 时，直接暴露会让模型随机选。加前缀并按业务域分组是可行的解法，前缀本身也是语义提示。schema 映射要严格：对端类型与内部类型不一致时，宁可拒绝并返回明确原因，也不要做隐式转换，否则模型会收到看似成功实则错位的结果。

超时与取消必须由 host 控制。server 可能因为下游依赖卡住，也可能实现了流式返回却迟迟不结束。host 应为每次调用设置超时，并在超时后发送取消消息，同时释放本地资源。只等不取消，会堆积连接与 goroutine，最终拖垮整个 host。取消本身也要有超时：对端不响应取消时，host 必须本地强制回收，不能等对端配合。

信任隔离是接入多个 server 时最容易被忽略的部分。内部 server 的返回可以进入证据层，外部 server 的返回应被视为不可信内容：做内容清洗、标记来源、限制它进入系统规则层，并禁止它触发高权限动作。context_quarantine 的含义就是把外部内容放在独立的证据区，而不是与系统提示混在一起。

结果归一化要统一成功与失败的外壳。不同 server 的错误格式各异，有的返回错误码，有的抛异常，有的在正常结果里塞一个 error 字段。host 应把它们映射成统一结构，并保留原始错误用于排查。归一化不是抹平差异，而是让模型看到稳定的接口，让工程师看到完整的细节。

还有一个工程细节是工具发现的缓存与失效。server 的工具集可能随部署变化，host 若只在启动时发现一次，就会长期暴露已下线的工具；若每次调用都重新发现，又增加往返开销。可行的做法是缓存工具清单并设置较短的有效期，在调用返回 unknown_tool 时强制刷新一次，同时把工具集版本写入轨迹，便于解释模型当时为何看不到某个工具。工具描述本身也需要版本化：同一个工具在不同版本里参数含义可能变化，若轨迹只记录工具名而不记录描述版本，事后回放就会出现“同样的调用，当时却合理”的困惑。

多租户场景下还有一个容易被低估的环节：凭证注入。凭证应由 host 按租户解析并注入到 client，而不是让 server 自己持有全局凭证；同时要假设 server 会把收到的凭证写进错误信息或日志，所以在结果进入模型上下文之前做一次出站过滤。这条比命名规范更接近真实事故的来源——越权往往不是模型主动干的，而是凭证在错误链路上被复用了。

## 四、工程取舍与反例

第一个取舍是接入粒度。把整个业务系统包成一个大 server，工具少但每个都很宽；拆成多个细粒度 server，工具清晰但连接与发现成本上升。可行的划分是按权限边界拆：需要不同授权级别的工具放在不同 server，便于独立管控。

第二个取舍是同步与流式。流式返回能改善长任务的体验，但增加了取消、重连与部分结果的复杂度。对短查询用同步，对长任务用流式，并在协议层明确“部分结果不代表成功”。

第三个取舍是信任级别。把所有 server 都当成内部可信，接入最快，但一个被污染的 server 就能影响全局；全部按外部不可信处理，安全但体验受限。按数据来源与部署位置分级，是更现实的路径。

常见反例有四类。其一是“无命名空间”，工具名直接透传，冲突后靠模型猜。其二是“协议即权限”，认为 server 声明了工具就等于授权，跳过了 harness 的能力校验。其三是“超时无取消”，host 侧超时返回，server 侧仍在执行，产生幽灵副作用。其四是“外部内容直入”，把网页或第三方返回原样放进系统提示，给提示注入留下入口。

还有一个隐蔽的反例：把 server 的健康检查做成一次性。server 可能在运行中能力退化，例如某个工具开始持续返回空结果。host 需要按调用结果动态降权，并在连续失败时熔断，而不是只在启动时握一次手。

## 五、工程案例：一个多租户的 MCP 接入场景

输入：某内部平台（示意）把 CRM、工单、知识库三个内部 server 和一个外部检索 server 接到同一个 host，供十二个团队共用。分析团队的一次请求需要先用 crm_search 找客户，再用 web_search 找公开信息；法务团队的请求主要走知识库。上线两周，暴露了三类冲突。

冲突一：工具重名。CRM 与知识库都暴露了 search，模型在两条路径之间反复横跳，有时一个请求里两边都调。处理是加前缀并把描述改写成可区分的动作语义——“检索 CRM 客户主数据”与“检索内部知识库条目”，同时在租户配置里默认只启用该租户订阅的 server。结论是：可解析性由前缀解决，选择歧义只能靠描述与默认可见性解决，两者不能互相替代。

冲突二：并发互斥。分析团队的一次长任务占满了外部检索 server 的并发槽位（该 server 设为 2），法务团队的调用在 host 侧排队直至超时，而它本来只需要一次内部查询。处理是把并发配额从“每 server 全局”改成“每租户每 server”，并为交互式请求保留一个专用槽位。代价是连接总数上升，空闲连接需要单独回收，否则几百个租户的连接会把文件描述符耗尽。

冲突三：schema 漂移。工单 server 升级后把 priority 从字符串改成整数，host 缓存里仍是旧定义，模型按旧 schema 传了 "high"，调用返回业务错误，重试三次都失败。处理是在工具清单缓存里记录 schema 摘要，摘要变化时拒绝新调用、强制刷新并要求重建会话，而不是在失败后静默重试。

结果：外部内容全部落在隔离证据区，越权调用与注入事件为零；工具选择错误明显下降。代价是首次发现变慢、工具名变长后模型偶尔拼错。后者用别名表缓解，别名只在 host 侧展开，不暴露给 server，避免把别名语义泄漏成协议的一部分。

## 六、边界与失败模式

MCP 能统一的是消息形状，下面这些事情它既不解决，也不该指望它解决。

语义正确性：schema 对得上不代表参数含义对。两个 server 都叫 date_range，一个闭区间一个半开区间，类型校验全部通过，结果差一天。这类差异只能靠描述版本与契约测试兜。

租户边界：server 只认自己收到的凭证，跨租户越权必须在 host 侧拦。指望 server 区分“这个请求来自哪个租户”，等于要求每个对端都实现一遍你的权限模型。

下游不可见：server 内部再调三个服务，失败细节被它吞掉，host 只看到超时。必须要求对端把内部原因写进结构化错误，否则排障只能靠猜。

中间层缓存：工具清单可能被反向代理或网关缓存，不同租户看到不同版本。清单要带版本戳与生成时间，否则“工具消失”这类问题无法归因。

## 七、落地检查清单

1. 命名空间唯一：全量工具名可在构建期枚举且无冲突。判据是出现冲突时启动失败，而不是运行时随机选一个。
2. 映射严格：类型不一致直接拒绝。判据是错误码能区分 schema_mismatch 与业务错误，且日志里保留对端原始类型。
3. 每次调用都有 host 侧超时与取消。判据是超时后 server 侧能看到 cancel，host 连接数回到基线。
4. 外部内容隔离。判据是系统提示与指令区不出现任何外部原文，证据区条目都带来源与信任级别。
5. 逐 server 熔断。判据是熔断器有 closed/open/half-open 三种可观测状态，且有明确的恢复探测。
6. 工具清单有 TTL 与强制刷新。判据是下线工具在 TTL 后不再出现在可选集合，unknown_tool 能触发一次刷新。
7. 描述版本入轨迹。判据是任取一条历史调用，能还原当时的工具描述与 schema 摘要。
8. 每租户每 server 并发配额。判据是单 server 打满时，其他 server 的调用延迟不受影响。
9. 凭证按租户注入并做出站过滤。判据是用正则扫描返回给模型的文本，不出现凭证样式字串。
10. 健康判断是动态的。判据是持续返回空结果的工具会被降权，而不是一直挂在可选列表里占位。

## 八、常见误区与面试追问

**问 1｜MCP 是不是安全边界？**
不是。它统一的是发现与调用的消息形状，鉴权、最小权限、内容隔离仍然在 host。把 server 的“我能做”当成“被允许做”，等于把授权交给了对端声明。

**问 2｜工具名冲突加个前缀就算解决了吗？**
只解决了可解析性。模型仍会选错，尤其当两个工具描述都在讲“检索”。还需要默认可见性（按租户只暴露订阅的 server）和描述里的适用边界。前缀是必要条件，不是充分条件。

**问 3｜为什么不做一个宽松的 schema 自动转换？**
隐式转换把错误推迟到业务层，而且通常以“成功但错位”的形式出现，比直接失败难查得多。宁可返回 schema_mismatch 并给出期望类型，让上游决定是改调用还是改配置。

**问 4｜超时设多少合适？**
按下游 P99 加余量、按 server 分级，而不是全局一个值。更关键的是取消：超时后要发 cancel 并本地回收，否则 server 仍在执行，产生幽灵副作用。只设超时不设取消，等于把延迟问题换成了重复执行问题。

**问 5｜外部内容“清洗干净”就能进上下文了吗？**
清洗只能降低概率，给不出保证。更可靠的是隔离：标记来源、限制进入系统规则层、禁止它触发高权限工具。把不可信内容当数据而不是当指令，是唯一能稳定执行的规则。

## 九、小结与延伸阅读

MCP 把工具接入标准化，让 host 能用统一方式发现与调用能力；它不负责权限、配额、超时取消、结果可信度与故障隔离，这些仍是 harness 的职责。接得多的关键不在协议本身，而在命名空间、严格映射、可控超时、信任分级与逐 server 熔断。

延伸阅读建议：官方文档类可看 MCP 的初始化、工具发现与传输层规范；工程博客类可看各 host 如何做 server 隔离与工具前缀；论文类可关注工具协议安全与提示注入防御的讨论。阅读时把“对端不可信”作为默认假设，再决定放行到什么程度。
