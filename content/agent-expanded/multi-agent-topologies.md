## 一、开场问题：三个代理一定比一个强吗

把一个大任务拆给三个角色——研究员、撰稿人、审稿人——听起来天然比单个 Agent 更可靠：有人查证，有人动笔，有人挑错。但真实系统里，常见的结局是研究员查了重复的资料，撰稿人拿到两份互相矛盾的摘要，审稿人只审了文字通顺度，最后的总输出既不比单 Agent 好，成本还高出数倍（来源：示意）。问题不在角色设定，而在拓扑：谁把任务分给谁，结果如何汇合，冲突由谁裁决，这些结构决定了协作是加成还是内耗。

多智能体的讨论很容易滑向“角色扮演”，仿佛给模型加上头衔就能获得能力。实际上，拓扑是一种组织设计，它改变的是信息流向、并行度与责任归属，而不改变单个模型的能力上限。理解这一点，才能判断什么时候该拆，什么时候该合。

判断的依据是协调成本能否被收益覆盖。协调成本包括：每多一个代理就多一份上下文构造、一次模型调用、一次结果解析；还包括更隐蔽的部分——信息在传递中被压缩、在汇合处被误读、在冲突时无人裁决。收益则来自并行（缩短墙钟时间）与分工（缩小单次上下文）。两边都是可估算的量，不估算就只能靠演示效果决策。

## 二、概念界定：四种基本拓扑

第一种是流水线。代理按固定顺序接力，前者产出后者输入，例如抽取、校验、格式化。它的优点是责任清晰、每段可独立测试；缺点是串行导致延迟累加，且上游错误会原样传给下游，缺少回头修正的通道。流水线适合阶段边界清楚、每阶段有明确验收标准的任务。

第二种是辩论。多个代理针对同一问题独立给出结论，再互相批评、投票或收敛。它的价值在于暴露分歧，抑制单一路径的盲点；代价是轮次开销与“从众效应”——模型容易在第二轮放弃正确但少数的意见。辩论适合答案可判定、争议点集中的问题，不适合需要快速出结果的场景。

第三种是主管—工人。一个主管代理负责拆解任务、派发给工人、收集结果并验收，工人只处理边界清晰的子任务。这是最常用的结构，因为它把全局规划与局部执行分开，主管可以控制预算与优先级。风险在于主管成为瓶颈与单点：拆解错了，所有工人都白干；验收松了，错误会被汇总成漂亮的总报告。

第四种是共享黑板。所有代理读写同一份结构化工作区，谁有进展谁更新，没有固定的派发关系。它适合探索性任务，例如联合排查故障、共同写方案；缺点是并发写冲突、上下文污染与责任模糊，必须配合字段级锁、版本号与仲裁规则，否则黑板会变成一锅粥。

四种拓扑可以组合：主管把任务派给几条流水线，流水线内部用黑板共享证据，关键结论再走一轮辩论。组合的自由度很高，但每加一层协调，就多一层失败可能。

## 三、机制拆解：主管—工人的一次派发

以主管—工人为例，最小可运行结构包含四件事：任务拆解、派发、回收验收、失败补偿。下面是一段示意配置，重点在预算与验收，而不是角色话术。

```yaml
supervisor:
  max_workers: 4
  decompose:
    granularity: "independent_verifiable_subtask"
    require_acceptance_criteria: true
  dispatch:
    budget_per_task: {steps: 8, tokens: 60000, seconds: 300}
    share_context: "summary_only"      # 不复制完整轨迹，避免上下文爆炸
  collect:
    require_evidence: true
    on_conflict: "supervisor_arbitrate"
  accept:
    checks: [schema_valid, evidence_cited, criteria_met]
    reject_action: "return_once_with_reason"
```

这段配置里最容易被低估的是 share_context。把主管的完整上下文复制给每个工人，看似信息充分，实际会让工人被无关细节干扰，也让 token 成本随工人数量线性上升。更稳的做法是只下发子任务说明、必要证据与验收标准，工人完成后只回传结论、证据与未决问题。

验收环节要防止“放水”。主管如果只读工人的自然语言总结，很容易被流畅的表述说服。可行的约束是要求每条结论附证据指针，验收器先做结构化检查（字段齐全、引用可解析、验收条件逐条命中），再让主管做语义判断。两次都通过才计入完成，否则带原因退回，且只允许退回一次，避免无限返工。

冲突处理也需要预先定义。两个工人给出矛盾结论时，默认不应由主管“综合一下”了事，而应触发补证：要么追加一个只做核对的工人，要么回退到检索工具寻找第三方证据。若证据仍不足，正确输出是“存在未决冲突”，而不是一个折中的假结论。

## 四、工程取舍与反例

协调成本是多智能体最主要的隐性开销。每增加一个代理，就增加一次上下文构造、一次模型调用、一次结果解析与一次可能的冲突处理；消息轮次、上下文复制与结论合并会同时放大延迟和费用。工程上常见的经验是：当子任务之间需要频繁共享中间状态时，拆分的收益很快被协调成本吃掉，此时单 Agent 加多个工具反而更简单。

可以用三条判据决定是否退回单 Agent。第一，子任务耦合度高：如果完成 B 必须先看 A 的全部中间过程，那么 A、B 更适合在同一个上下文里顺序完成。第二，验收标准难切分：如果只有整体结果可判定，子任务各自的“完成”没有意义，拆分只会制造虚假进度。第三，时延敏感：并行看似更快，但派发、等待与合并的固定开销在短任务上占比很高，交互式场景往往得不偿失。

常见反例有四类。其一是“角色膨胀”，为每个职能设一个代理，但任务之间高度重叠，最后几个代理反复读同一批资料。其二是“辩论空转”，没有裁判与终止条件，代理互相说服，轮次不断增加而结论不变。其三是“黑板污染”，一个代理写入未经证实的猜测，其他代理把它当事实继续推理。其四是“主管失真”，主管把工人的局部结论直接拼接，没有做一致性检查，输出内部自相矛盾。

还有一个治理层面的问题：多智能体让责任链变长，出错后很难定位是拆解错、执行错还是验收错。解决办法不是减少代理，而是让每次派发都有 id、每次回收都有证据、每次裁决都有理由，把组织过程变成可回放的数据。做不到这一点，多智能体就只是一次昂贵的演示。

## 五、工程案例：三个角色的调研报告为什么自相矛盾

背景示意：要在一周内产出某类产品的竞品调研，团队搭了三角色——研究员两名（分工定价、功能），撰稿人一名，审稿人一名，主管负责拆解与汇总。

输入：调研范围三条（目标客群、定价模式、核心功能矩阵），验收要求两条（每条结论有来源、矩阵不留空格）。

失败轨迹（示意）：两名研究员各自检索，六成来源重叠，分别抓了 11 条和 9 条证据；主管把两人的完整轨迹都塞进了撰稿人上下文，撰稿人从中各取一半，产出里“价格区间 99–299”与“按席位计费”同时存在且未标注冲突；审稿人只检查行文通顺与错别字，把矛盾当成“表述差异”放过；主管读了三份自然语言总结，判断“结构完整”，直接交付。结果是客户第一轮就指出数据互相矛盾，返工一天。

四个根因都在拓扑与契约，不在模型。拆解按“职能”而不是按“可独立验证的结论”，导致两个工人的检索空间重叠；share_context 传了全量轨迹，撰稿人面对的是两份未对齐的推理过程，而不是对齐后的事实；验收只有“有没有来源”这一层，没有交叉校验；冲突没有仲裁路径，默认被主管“综合”掉了。

处理做了四件事。其一，拆解改为按结论切分：定价结论（含来源与抓取时间）、功能矩阵（每格独立来源）、客群画像，每结论最多 3 条证据，超出的必须合并去重。其二，上下文改为摘要加证据指针，工人之间不共享推导过程，只共享一个去重后的证据池，重复来源在池子里合并并计数。其三，验收器代码化：先跑 schema 检查（每条结论必须带 source_url 与 retrieved_at），再跑交叉校验（同一实体两个值不一致即判冲突），最后查覆盖度（矩阵空格数为 0）。其四，冲突不进综合环节，触发一个只做核对、不改结论的第三方工人；仍无法收敛则输出“存在未决冲突”并附双方证据。

结果（示意）：交付周期 2 天，矛盾 0 处，成本约 2.1 倍单 Agent（重叠检索被去掉后比原来低了一半），客户方追问从 11 条降到 3 条。改动里最起作用的是“去重证据池”和“交叉校验”，两者都不需要更强模型。

一个反直觉的观察：让工人共享同一个证据池，比让它们共享彼此的观点更有效。共享观点会带来趋同与污染，共享证据只带来一致性——因为证据可以被核对，观点不能。

## 六、与相邻概念的边界

多智能体常被和三类东西混为一谈，边界不清会导致技术选型跑偏。

与编排框架的边界：编排描述“步骤怎么走”，拓扑描述“谁对谁负责”。一条流水线拓扑在实现上就是一段编排代码，此时多智能体没有独立价值；只有当决策权被分发到不同执行者、且需要汇合与仲裁时，拓扑才成为独立的设计对象。

与角色提示词的边界：给一个模型写三段不同人设的提示词，轮流调用，仍是单 Agent 的多次调用，因为上下文与责任没有真正分离。判断标准是：每个角色是否有独立的上下文边界与独立的验收标准。

与人在环的边界：人也可以是拓扑里的一个节点，例如审批者或仲裁者。这时要考虑的是人的响应延迟与批量处理能力，而不是模型调用次数；把人工节点当普通工人排进流水线，通常会让整体延迟被最慢的节点拖住。

## 七、落地检查清单

1. **先算账再拆**：把“代理数 × 单代理固定开销”与预期并行收益写成数字对比，而不是凭感觉决定拆不拆。
2. **拆解可独立验收**：每个子任务有独立验收条件，且完成它不需要读其他子任务的完整轨迹。
3. **上下文不复制**：只下发子任务说明、证据与验收标准，禁止把主管全量轨迹传给工人。
4. **每任务三项预算**：步数、token、墙钟各自有上限，超限返回未完成，不静默扩大。
5. **证据强制**：每条结论带可解析的来源指针，无指针的结论不计入完成。
6. **验收两段式**：结构化检查（schema、引用、验收条件）在前，语义判断在后，两段都过才算完成。
7. **退回有上限**：只允许退回一次，第二次失败升级为人工或替换执行者。
8. **冲突有路径**：默认补证（第三方核对），禁止主管“综合一下”生成折中结论。
9. **黑板有锁与版本**：字段级锁加版本号，每次写入必须附证据，冲突写入可见。
10. **过程可回放**：派发有 id、回收有证据、裁决有理由，能回答“这个结论是谁在哪一步给出的”。

## 八、常见误区与面试追问

**追问一：给三个代理分别写“你是资深研究员”“你是主编”这类人设，算多智能体吗？**

答：不算，那是一个模型的三次调用。多智能体的判据是上下文边界与验收责任是否真正分离。人设改变语气，不改变信息流向，也不产生独立的验收点。

**追问二：并行一定比串行快吗？**

答：短任务上往往更慢。派发、等待汇合与结果合并是固定开销，任务越短占比越高。并行真正的收益在墙钟时间受限于单个长任务时，比如三个各自需要五分钟的独立检索。

**追问三：多个代理投票，能靠多数压制幻觉吗？**

答：只在答案可判定时有效，而且要注意趋同。所有代理读同一批上下文时，错误会一起犯；真正的多样来自证据来源不同，不是采样次数不同。没有裁判的投票也只是把分歧藏起来。

**追问四：主管要不要读一遍所有工人的原始轨迹？**

答：不要全读，要能按需读。全读会让主管上下文爆炸、判断被细节带偏；完全读不到又无法仲裁。可行做法是主管只看结论与证据指针，仲裁时按指针定向取原文。

**追问五：任务再复杂一点，是不是该上几十个代理的 swarm？**

答：规模不是解法，可验证性才是。代理数量上升时，仲裁与一致性成本是超线性的。多数场景下，把代理数压到 3 到 5 个、把验收做严，比扩到几十个更容易得到稳定结果。

## 九、小结与延伸阅读

拓扑选择本质是组织设计：流水线换确定性，辩论换视角，主管—工人换可控并行，黑板换自由协作。它们都只在“任务能切出低耦合子问题、且验收标准可切分”时才划算。拆之前先算协调成本，拆之后先建验收与冲突规则，比给代理起名字重要得多。

延伸阅读建议：论文类可看多智能体辩论与协作综述，重点关注它们如何度量一致性与通信开销；官方文档类可对比 AutoGen、CrewAI 等框架的协作模式；工程博客类可看 supervisor 与 swarm 的架构说明。阅读时关注“失败如何回收”，这是拓扑设计真正的分水岭。
