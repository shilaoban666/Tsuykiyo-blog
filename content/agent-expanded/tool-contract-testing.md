## 一、开场问题：改了字段名，模型开始胡乱调用

一个内部平台有三十多个工具，某次重构把订单查询工具的返回字段从 order_id 改成了 orderId。改动很小，单元测试也通过了，因为测试只断言了“返回 200”。上线后 Agent 的表现开始变差：它在后续调用里反复传 order_id 作为参数，工具返回参数缺失，它又换个写法重试，最终在步数耗尽后给用户一段道歉。排查花了半天，最后发现根因只是一个字段改名，而模型并不知道。

这类问题不属于“模型不行”，而属于“工具契约没有被测试”。单元测试验证了函数能跑，但没有验证“模型看到的描述与真实的输入输出是否仍然一致”。本文讨论的是怎样用契约测试把工具的 schema、成功返回、错误语义与超时行为固定下来，让工具变更可以被回归。

## 二、概念界定：契约的四个面

工具契约不只是参数 schema，它包含四个面。第一个面是描述：工具名称、用途说明、参数含义，这些是模型选择工具的依据。第二个面是结构：参数的类型、必填、枚举、取值范围，以及返回值的字段与类型。第三个面是语义：成功时返回什么、失败时错误码是什么、哪些错误可重试。第四个面是行为边界：超时多久、限流阈值、幂等键如何生效。

契约测试要覆盖的正是这四个面，而不是只测“函数能返回”。对应四类用例：快照类，把 schema 与描述存成快照，变更时显式确认；结构类，用合法与非法参数各跑一遍，断言校验行为；语义类，构造权限拒绝、参数错误、下游超时，断言错误码与可重试标记；边界类，构造慢响应与重复请求，断言超时与幂等。

契约有多个读者，这一点常被忽略：模型读描述，调用方代码读结构，值班人读语义；同一次变更对三者的影响可能完全不同——字段改成驼峰命名，对调用方是编译期错误，对模型却是静默的认知错位。描述与结构分家是最高频的漏测来源：参数加了可选字段而描述没跟上，模型就永远不知道它存在。

与端到端评测的区别在于粒度。端到端评测回答“Agent 能不能完成任务”，受模型、提示、工具、上下文共同影响，失败时难以定位；契约测试回答“这个工具是否仍然按约定工作”，范围小、跑得快、失败原因明确。两者不能互相替代：契约测试全绿，Agent 仍可能因为提示不佳而失败；契约测试红了，端到端一定不稳。它的边界也要说清：不评估模型选工具的能力，只保证模型决定调用某个工具时，参数、返回与错误都是它预期的样子。

## 三、机制拆解：快照、夹具与错误路径

一个可运行的最小方案是三层：schema 快照、录制回放夹具、错误路径参数化。下面用 pytest 的写法示意。

```python
import json, pytest
from pathlib import Path

SNAP = Path("tests/contracts/snapshots")

def test_schema_snapshot(tool_spec):
    name = tool_spec["name"]
    path = SNAP / f"{name}.json"
    current = json.dumps(tool_spec, ensure_ascii=False, indent=2, sort_keys=True)
    if not path.exists():
        path.write_text(current, encoding="utf-8")
        pytest.skip("snapshot created, review and commit")
    assert current == path.read_text(encoding="utf-8"), "工具契约变更，请确认兼容性"

@pytest.mark.parametrize("bad_args, expect_code", [
    ({}, "missing_required"),
    ({"order_id": 12345}, "type_mismatch"),
    ({"order_id": "x", "status": "unknown"}, "enum_invalid"),
])
def test_invalid_args(tool, bad_args, expect_code):
    result = tool.run(**bad_args)
    assert result.ok is False
    assert result.error["code"] == expect_code
    assert result.error["retryable"] is False

def test_timeout_is_retryable(slow_tool):
    with pytest.raises(TimeoutError):
        slow_tool.run(timeout_ms=50)
```

这套用例里有三个值得展开的设计。第一，快照不是“自动通过”，首次生成时跳过并提示人工确认，之后任何变更都会让测试失败，迫使提交者说明这是不是破坏性变更。第二，非法参数的断言精确到错误码，而不是笼统的“失败”，因为模型正是靠错误码决定下一步。第三，超时被显式建模成可重试错误，而不是让异常直接穿透到主循环。

录制回放解决的是外部依赖不稳定。把真实调用录成夹具，含请求、响应、耗时与状态码，CI 中按请求指纹匹配重放：测试不需要网络，也不受第三方限流影响；风险是夹具会过期，真实接口变了而夹具没变，测试仍然绿。缓解办法是定期用真实调用做一次“采样校验”，把差异报出来而不是直接失败。

指纹决定回放的可信度。原始请求里混着时间戳、幂等随机数与顺序不稳的数组，直接哈希不可行，要先归一化再算；匹配失败时给出最接近的候选与字段级 diff，而不是只报“找不到夹具”。夹具过期分级处理：字段新增记警告并自动补录，字段删除、类型变化、错误码变化必须失败并要人确认。

兼容性判定要有明确规则。加可选字段、放宽枚举、增加新的错误码，通常是非破坏性的；删字段、改字段类型、把可选改必填、改错误码语义，是破坏性的。破坏性变更必须同时改三处：工具实现、schema 快照、以及给模型的描述。只改前两处，模型仍会按旧描述调用，问题会推迟到线上才暴露。

错误路径要覆盖全。除了参数错误，至少还要测：权限拒绝（不可重试）、下游超时（可重试）、限流（可重试且带退避提示）、返回空结果（成功但无数据）、返回畸形数据（不可重试，需告警）。这五类覆盖了模型在真实环境里最常遇到的岔路，缺哪一类，模型就会在那一类上瞎试。

错误码最好做成一张固定表，每行写清错误码、是否可重试、建议的下一步。示意：invalid_args 不重试，应改参数或换工具；permission_denied 不重试，应上报；throttled 可重试但需退避；malformed_response 不重试，应告警。这张表同时是给模型的提示素材和给测试的断言来源，共用一份才不会出现“测试说不可重试、描述说可以重试”的分裂。

## 四、工程取舍与反例

第一个取舍是快照的粒度。整个工具描述存一份快照，变更时一起失败，简单但噪声大；拆成参数、返回、错误码三份，定位准但维护成本高。通常按“谁会独立变更”来拆：描述与参数常一起改，可以合并；返回结构与错误码影响调用方，值得单独快照。

第二个取舍是回放与真实调用。全回放稳定、快、便宜，但可能与环境脱节；全真实调用准确，但慢、贵、不稳定。可行的比例是日常 CI 全回放，每日定时跑一小批真实调用做采样校验，两者结果都进同一份报告。

第三个取舍是严格与效率。把每个字段都做成强校验，工具会更可靠，但也会拒绝一些模型本来能处理的宽松输入。折中是“入口严、出口宽”：参数校验严格，返回结构允许附加字段，避免下游因为多了个字段就崩。

反例有三类。其一是“只测 happy path”：成功用例写得很全，错误路径一个没有，模型一遇到限流就开始乱试。其二是“快照自动更新”：测试失败时直接覆盖快照，等于没有契约，变更仍然无声无息。其三是“夹具万能”：所有外部依赖都回放，从不校验真实环境，接口早已下线而测试全绿。

还有一类反例是“契约与描述脱节”：schema 改对了，但给模型看的描述还写着旧字段名，模型照着描述调用，测试却因为只校验 schema 而通过。另一种是“测试跑在 mock 层”，为了跑得快绕过参数校验、序列化、截断与错误包装，测的东西和线上跑的不是同一个。

最后一个提醒是：契约测试要跑在“模型看到的那一层”。如果平台在工具与模型之间做了适配层，例如重命名参数、包装返回值，那么测试必须针对适配后的形态，否则测的是实现，不是模型实际面对的接口。

## 五、工程案例：一次回归事件

以下场景为示意，数字用于说明量级，不代表任何真实系统。

某平台周一 14:20 发布一个“无行为变更”的重构，把订单查询的返回字段统一改成驼峰命名。14:40 客服反馈“助手一直问订单号，明明刚给过”。值班人先看错误率，没有明显上升；再看平均步数，从 4.1 涨到 9.3；无效重复调用率从 3% 涨到 27%。三个指标指向同一件事：模型在反复尝试同一个调用。

15:00 抽三条失败轨迹并排对比：第一条里模型收到结果后仍用 order_id 再调一次；第二条换成 orderId 后成功；第三条在两种写法之间来回切换直到步数耗尽。三条轨迹的错误码都是 invalid_args，而返回里明明写了 retryable=false——问题不只是字段改名，还有“不可重试错误被当成可重试”这个既有缺陷被同时引爆。

15:30 定位到 PR，diff 只有六行：返回字典的键名、两处内部引用、一个类型注解。没有 description 改动，没有快照改动，单元测试因为只断言状态码而全绿。根因清楚：契约的“结构”面变了，“描述”面没变，错误语义也没有被测试锁住。

16:10 完成修复，三处。实现层加别名兼容，旧字段名在一个发布周期内仍返回，给下游和缓存留过渡时间；更新 description，写明返回字段名，并补一句“参数错误时不要重试同一调用，改用在返回里给出的候选字段名”；补三类测试——description 快照、错误码不可重试的断言、五条端到端小样本。

复盘得三条结论。其一，字段改名不是内部重构，只要它出现在工具返回值里就是对外契约变更，必须走契约测试与描述更新的同一流程。其二，错误语义的测试价值被长期低估：模型行为很大程度由错误码驱动，错误码不测等于把控制流交给模型的猜测。其三，指标要提前埋：没有“无效重复调用率”，这次故障只能靠客服反馈发现。

## 六、落地检查清单

以下九条按“能不能挡住一次真实回归”设计，每条给出判据。判据要求可执行，不接受“已注意”。

1. 每个对外工具都有 description 快照。判据：快照文件存在且在 CI 中生效，改 description 会让构建失败并要人工确认。
2. 快照做了规范化。判据：同一份代码连续构建两次 diff 为空，时间、构建号等易变字段已剔除。
3. 参数校验覆盖至少三类非法输入。判据：缺必填、类型错误、枚举越界各有用例，断言到具体错误码。
4. 错误码表是单一来源。判据：测试断言、工具描述、值班手册引用同一份表；抽三个错误码，三处说法一致。
5. 不可重试错误有明确断言。判据：至少一个用例断言 retryable=false，并有端到端样本验证模型不会重试同一调用。
6. 幂等有测试。判据：同一幂等键调两次，假工具记录的副作用次数为 1，第二次返回首次结果。
7. 超时被建模成可重试错误。判据：慢响应夹具触发超时后返回结构化错误而非未捕获异常，重试次数有上限。
8. 回放夹具带指纹归一化与过期分级。判据：能演示一次“字段新增只告警、字段删除则失败”的采样校验结果。
9. 破坏性变更走三处同步。判据：最近三次破坏性变更的提交里，实现、快照、描述在同一 PR 内，评审记录中有兼容性结论。

清单之外还有一条隐性要求：这些测试要能在十分钟内跑完，跑不完的会被跳过。

## 七、常见误区与面试追问

**问一：契约测试和端到端评测，能不能只做一个？**
不能互相替代，但优先级不同。契约测试是地基：便宜、快、定位准，红了就说明工具坏了，端到端不必跑。端到端评测回答“模型会不会用这些工具”，覆盖提示、上下文与工具组合，代价高且难归因。可行顺序是先让契约全绿，再用小规模端到端守住关键路径；反过来只做端到端，故障会以“通过率掉四个点”的形式出现，排查成本极高。

**问二：快照测试是不是就是让测试跟着代码变？**
区别在谁做决定。自动更新快照是让代码做决定，契约就没了；人工确认是让人做决定，快照只负责把变更摆到台面上。要防的正是“顺手更新快照”：快照更新需要单独的提交信息与评审人，或在 CI 里禁止自动写快照。

**问三：有了类型系统和 schema 校验，为什么还要契约测试？**
类型系统保证实现内部正确，schema 保证结构合法，但都不保证“模型理解的和实际一致”。description 的措辞、错误码的可重试语义、超时后的行为、截断时的标记，都不在类型系统里。契约测试补的正是这一层：面向模型的语义。

**问四：夹具会不会让测试变成自欺欺人？**
会，如果只有夹具。夹具用来隔离不稳定性，不能替代真实，判据是：删掉采样校验之后，夹具是否在慢慢腐烂而无人知晓。稳妥组合是日常全回放、每日小批真实采样、发布前一次真实冒烟，结果进同一份报告。

**问五：小团队没有平台支持，从哪一条开始？**
从 description 快照和错误码断言开始，这两条几乎零成本，挡住的是最高频的故障类型。做法：把工具清单导出成 JSON，排序后存文件，CI 里比对；再挑三个最常被调用的工具，每个写三条非法输入用例，断言错误码与 retryable。做完这两步再考虑回放与幂等。

## 八、小结与延伸阅读

工具契约测试的价值，是把“模型能不能正确调用”这个模糊问题，拆成四个可断言的面：描述、结构、语义、边界。快照负责发现变更，夹具负责隔离依赖，错误路径负责覆盖真实岔路。三者合起来，工具变更才敢发版。

延伸阅读建议：标准规范类可看消费者驱动的契约测试方法；官方文档类可看 pytest 的 fixture、parametrize 与异常断言；工程博客类可看录制回放式测试的实践，重点看它如何处理夹具过期。
