## 一、开场问题：审批流里塞进一个“聪明的节点”

一家银行把信贷审批做成了工作流：资料录入、征信查询、额度试算、风控规则、人工审批、放款，每一步都有明确的状态与责任人。后来他们想在“风控规则”之后加一个智能体，让它综合客户经理的尽调笔记、行业新闻与历史案例，给审批人一段建议。想法本身没问题，落地时却出现了两个方向的抱怨：技术团队说工作流引擎的重跑机制会把智能体重复执行，产生重复的调用与不一致的建议；业务团队说智能体给出的建议无法回溯，出了问题不知道是依据哪份材料。

这两个抱怨指向同一件事：确定性编排与开放决策混在一起时，边界没有划清。本文讨论的是怎样划分确定性边界、怎样交接状态、怎样保证重跑幂等，让工作流引擎与 Superagent 各司其职。

## 二、概念界定：两种编排的控制权

工作流引擎的核心是“预先定义的路径 + 持久化的状态”。路径由人写死，引擎负责按顺序推进、失败重试、超时升级、状态落盘。它的优势是可审计、可重放、可补偿；劣势是遇到未预设的分支就无路可走。

Superagent 的核心是“运行时决定路径”。它根据目标与当前观察决定下一步做什么，优势是能处理开放问题；劣势是路径不可预知，同一输入可能走不同路线，回归与审计都更难。

混合模式不是把两者简单串起来，而是按“这一步的决策是否可以预先写死”来划分。可以写死的，交给引擎：审批、扣款、通知、归档，这些步骤需要确定的时间点、确定的负责人、确定的补偿动作。必须临场判断的，交给 Superagent：材料是否相关、风险点是否成立、建议如何措辞，这些没有固定规则，写死就会僵化。

划分的判据有三条。第一，可审计性要求：监管要求逐步留痕的步骤，应由引擎承担，因为引擎的状态机天然产生完整轨迹。第二，可逆性：不可逆的动作（放款、对外承诺）应由引擎执行，并配套补偿；可逆的分析与草稿可以交给代理。第三，输入的不确定性：输入是结构化字段且规则明确，用引擎；输入是长文本、需要理解与取舍，用代理。

边界还有一个反向判据：如果某一步的规则能写成表格，就不要交给代理。表格能表达的东西交给代理，只会带来不确定性与更高的单次成本；反过来，如果规则需要写三段例外说明才能覆盖，那它其实不是规则，应该交给代理判断。

## 三、机制拆解：状态交接与幂等贯穿

混合模式的关键接口是“状态交接”。引擎调用代理时，要传三样东西：任务说明、上下文引用、验收标准；代理返回时，要交三样东西：结构化结果、证据引用、置信度与未决问题。双方都不应假设对方理解自己的内部状态。

```json
{
  "activity": "risk_advice",
  "workflow_id": "loan-2026-004417",
  "attempt": 2,
  "idempotency_key": "loan-2026-004417:risk_advice:v1",
  "input": {
    "application_ref": "artifact://app-4417",
    "notes_ref": "artifact://visit-notes-4417",
    "news_query": "行业政策 近三个月",
    "constraints": ["不得引用未公开信息", "结论须区分事实与推测"]
  },
  "output_contract": {
    "required": ["advice", "evidence", "confidence", "open_questions"],
    "acceptance": ["每条风险判断至少一个 evidence", "confidence 为 0-1 的小数"]
  },
  "timeout_sec": 90
}
```

这份交接单里有三个要点。第一，上下文用引用而不是全文，避免引擎把整份档案塞进模型，也避免代理拿到超出职责的数据。第二，幂等键贯穿重跑，代理侧据此判断“这次调用是不是上一次的重放”，从而复用结果而不是重新生成。第三，验收标准随请求下发，代理在生成时就知道要交什么，减少来回。

重跑幂等是混合模式最容易出事的地方。工作流引擎的典型语义是“活动失败后重试”，如果代理的活动没有幂等键，重试就会产生第二份建议，甚至第二次外部调用。解决办法是把代理活动视为“带副作用的远程调用”：读类活动可重试，写类活动必须带幂等键，且代理内部要维护“已处理请求”的记录。

可重放还有一层含义：给定同一份输入与同一个版本配置，重跑应得到可比较的结果。完全一致很难，因为模型采样有随机性；工程上追求的是“结论稳定”，即关键判断不随重跑翻转。做法包括固定随机种子、降低温度、把关键证据以结构化形式给定，以及对重跑结果做差异比对，差异超过阈值时告警而不是静默接受。

超时回传也要设计。代理超时后，引擎不应立即判定活动失败并重试，而应先查询代理侧的执行状态：是仍在运行、已产出部分结果，还是已失败。这一步查询能避免大量重复执行。若代理支持“取消”，引擎在放弃等待时应主动取消，释放配额。

交接单还有版本问题。代理侧的提示词、工具集与验收标准都在变，同一个幂等键在不同版本下可能产出不同结果。稳妥做法是把配置版本作为独立字段随交接单一起传，重放时版本不一致就不复用结果，标记为“需人工确认的差异”，避免把旧版本的结论当成新版本的重放。

## 四、工程取舍与反例

第一个取舍是边界粒度。边界划得太细，引擎与代理之间频繁交接，每次交接都要序列化与校验，开销大；划得太粗，一个代理活动包住半个流程，引擎失去对中间状态的可见性。通常以一个“有明确验收标准的决策单元”为边界。

第二个取舍是状态归属。状态放在引擎，代理无状态，易于重放但每次都要重新构造上下文；状态放在代理，上下文连续但引擎难以审计。折中是“引擎持有权威状态，代理持有会话缓存”，缓存可丢，权威状态不可丢。

第三个取舍是失败归属。代理失败时，是引擎重试、代理内部重试，还是升级人工？三层都重试会放大故障。可行的约定是：瞬时错误由代理内部重试，业务性失败回传引擎由引擎决定，权限与合规问题直接升级人工。

反例有三类。其一是“引擎里跑自由代理”：把代理当成一个黑盒活动，输入输出都不结构化，重跑时结果面目全非，审计无法解释。其二是“代理里模拟工作流”：用提示词让代理按固定步骤执行，看似可控，实际没有状态机与补偿，一步失败全盘重来。其三是“双写状态”：引擎与代理各存一份状态，长期不一致，排查时无法确定哪份为准。

交接单还要考虑失败语义的对齐。引擎的“活动失败”与代理的“任务未完成”不是一回事：代理可能返回了部分结果、可能给出低置信度结论、可能建议人工介入。这些都应映射成引擎能识别的显式状态，而不是统一塞进“失败”里，否则引擎只会重试，而重试对“需要人工裁决”这类状态毫无意义。

边界不是一次划定的。上线三个月后，原本由代理承担的建议环节往往会被规则化，因为积累的案例足够多，判断可以写成条件；反过来，原本写死的分支会因为业务变化变得需要解释，于是转给代理。边界应当随案例积累移动，而不是当作架构图上一条固定不动的线。

## 五、工程案例：一次重放事故

（示意场景）信贷审批流程里，风控建议是一个代理活动，超时 90 秒。某次超时后引擎按默认语义重试，attempt 从 1 变 2。交接单里没有幂等键，代理生成了第二份建议，措辞不同，风险等级从“关注”落到“正常”。两份都进了审批材料，通知活动也跑了两次，审批人收到两条互相矛盾的消息。

排查花了两小时（示意）：先怀疑规则引擎，再怀疑上游数据，最后才在代理日志里看到两次执行。修复三步——交接单加幂等键，代理侧维护已处理请求表；引擎在重试前先查代理执行状态；通知活动按事件去重，同一流程同一事件只发一次。

修复后仍有一次险情：代理先写了建议缓存，随后通知失败，引擎重试复用了缓存，但缓存里的配置版本是旧的。于是加版本校验——版本不一致不复用，改为重新生成并记录差异。这类问题的共同点是：幂等键解决“重复执行”，版本校验解决“重复使用旧结果”，两者不能互相替代。

## 六、从单 Agent 迁移的步骤

把一个已经在跑的单 Agent 迁到混合模式，顺序比方案重要。

第一步，画出当前步骤轨迹。用真实运行日志统计代理实际做了哪些动作、哪些动作有外部副作用。这一步常会暴露你以为的“分析”其实在写数据。

第二步，按可审计性、可逆性、输入不确定性把步骤分成两栏，写成边界表，每条注明归属方与理由。边界表要与业务方一起过，因为它同时决定责任归属。

第三步，先把写操作收进引擎。读类活动可以继续留在代理里，写类必须由引擎发起并带幂等键与补偿。这是迁移中风险最高的部分，建议逐条迁移而不是整批切换。

第四步，接持久化与重放。让引擎持有权威状态，代理侧只留会话缓存；用历史输入做重放，比较关键结论是否稳定。

第五步才是灰度。先影子运行（引擎只记录不执行），再小比例放量，最后全量。每一步都保留回退开关，回退开关要能在一分钟内生效，否则它不是开关，是仪式。

## 七、落地检查清单

1. 边界按三条判据划。判据：每个步骤能回答可审计性、可逆性、输入不确定性三个问题，答案落在同一侧才归给一方。
2. 交接单结构化。判据：输入、输出契约、验收标准、超时四项齐全，缺项的活动不允许上线。
3. 写类活动必带幂等键。判据：活动定义里 idempotency_key 为必填，读类活动可豁免但要标注理由。
4. 重试前查执行状态。判据：引擎侧有状态查询调用记录，超时后不直接重试。
5. 配置版本随单传递。判据：缓存命中前校验版本，不一致走重算。
6. 权威状态单点归属。判据：引擎与代理不双写同一状态，代理缓存可整体丢弃而流程仍能推进。
7. 失败归属三选一。判据：瞬时错误代理内重试、业务失败回传引擎、权限合规直接升级，三层不叠加重试。
8. 重放可比较。判据：同输入同版本重跑，关键判断一致；差异超阈值告警而不是静默接受。
9. 补偿与边界事件对齐。判据：每个不可逆活动都有对应补偿活动，且补偿本身幂等。
10. 轨迹可解释。判据：给定一次运行，能按时间还原“哪一步交给谁、依据什么、结果如何”。

## 八、常见误区与面试追问

**问：既然代理能自己规划，为什么还需要工作流引擎？**
答：因为可审计、可重放、可补偿这三件事在监管场景里不能靠模型自觉。引擎负责“什么时候做、谁负责、错了怎么撤”，代理负责“这一步怎么看、怎么写”。

**问：把代理包成一个活动，是不是就混合了？**
答：只是形式上混合，实际常常是黑盒。真正的混合要求输入输出结构化、验收标准随单下发、重跑可比较，缺一项就退化成“引擎里跑自由代理”。

**问：用提示词让代理按固定步骤走，能不能替代引擎？**
答：不能。提示词没有持久化状态、没有补偿、没有超时升级，一步失败就全盘重来，排查时也拿不到步骤级轨迹。

**问：状态放引擎还是放代理？**
答：权威状态放引擎，代理只持会话缓存。缓存可以丢，代价是重新构造上下文；权威状态丢了的代价是无法审计和无法续跑。

**问：幂等键怎么设计？**
答：用业务标识加步骤名加版本，保证同一业务动作在同一版本下只生效一次。不要用随机 uuid，那样每次重试都是新键，幂等形同虚设。

## 九、小结与延伸阅读

混合模式的要义不是“两者都用”，而是按可审计性、可逆性与输入不确定性划出一条清晰的边界：确定性的、不可逆的、需要留痕的步骤交给引擎；开放的、可逆的、需要理解与取舍的步骤交给代理。边界之间用结构化交接单连接，用幂等键贯穿重跑，用状态归属约定避免双写。
