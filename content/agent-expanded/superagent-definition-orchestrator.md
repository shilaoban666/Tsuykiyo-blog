## 一、开场问题：换个更强的模型，就成 Superagent 了吗

两个团队都在做“超级助手”。第一个团队把最强的模型接进来，给它很长的系统提示、几十个工具，希望它什么都能干。第二个团队用同样的模型，但多做了一件事：把任务拆成子任务，派给专门的子代理，收回结果后验收，不合格就退回重做。三个月后，第一个团队的助手在简单问答上很亮眼，遇到跨系统、多步骤的任务就频繁失控；第二个团队却能稳定完成那些需要查证、执行、复核的复杂工单。

差别不在单次推理能力，而在组织能力。第一个团队做的是“更强的单兵”，第二个团队做的是“编排者”。本文要界定后者：什么样的系统可以被称为 Superagent，它与单 Agent 加多工具的区别在哪里，以及它最常见的失效模式是什么。

需要先排除一种幻觉：换模型带来的提升往往在两周内就被任务复杂度的增长吃掉。第一周演示很好，第二周用户开始提跨系统、多步骤、需要复核的需求，单兵结构的边际收益迅速下降。这不是模型不行，而是结构没有随任务形态变化。

## 二、概念界定：三条判定标准

本文把 superagent 定义为：在 harness 之上做任务分解、多智能体编排与自我修正的上层智能体。这个定义有三个关键词：之上、编排、修正。它不直接替代底层执行，而是决定“谁来做、做完没有、做错了怎么办”。

判定一个系统是不是 Superagent，可以看三条标准，缺一不成立。第一是派发权：它能把子任务分配给不同的子代理或工具链，并决定每个子任务的输入、预算与截止时间。第二是验收权：它能判断子任务是否达到验收标准，并决定接受、退回还是升级，而不是把所有返回都当成完成。第三是全局状态：它维护跨子任务的目标、约束、进度与未决问题，能在子任务之间传递必要信息，而不只是把结果简单拼接。

三条标准对应三种能力：分解、治理、记忆。只有派发没有验收，是“任务转发器”；只有验收没有全局状态，是“流水线质检员”；只有全局状态没有派发，是“带笔记的单 Agent”。三者齐备，才构成编排意义上的“超级”。

还要区分 Superagent 与“单 Agent + 多工具”。工具扩展的是动作空间，让一个智能体能做更多事；编排扩展的是组织能力，让多个执行者围绕一个目标协作。工具再多，仍然是一个决策中心，遇到超出单上下文的复杂任务就会吃力；编排则把复杂度分摊到多个执行者，用结构换容量。反过来，如果任务本身不需要分工，硬加一层编排只会增加延迟与失败面。

这里有一个成本上的分界。动作空间的成本是线性的：多一个工具，多一段描述、多一种误选。编排的成本是乘性的：多一层派发，就多一次上下文构造、一次结果解析、一次验收，每一环都可能失败。判据不是“能不能编排”，而是“这段复杂度是否必须由结构承担”。

## 三、机制拆解：派发、回收、验收与修正

Superagent 的一次完整循环包含四段：分解、派发、验收、修正。下面是一段示意伪代码，重点在验收与修正，而不是派发本身。

```python
def orchestrate(goal, constraints):
    plan = decompose(goal, constraints)          # 子任务 + 依赖 + 验收标准
    results = {}
    for task in topo_order(plan):
        if not deps_ready(task, results):
            continue
        sub = spawn(task.agent, task.input, budget=task.budget)
        out = sub.run()
        verdict = accept(task.criteria, out, evidence_required=True)
        if verdict.ok:
            results[task.id] = out
        elif verdict.retryable and task.retries < 1:
            results[task.id] = spawn(task.agent, verdict.feedback,
                                     budget=task.retry_budget).run()
        else:
            return escalate(goal, task, verdict.reason, results)
    if not globally_consistent(results, constraints):
        return replan(goal, results)             # 目标漂移或冲突时重排
    return synthesize(goal, results)
```

这段伪代码里有三个设计点。第一，分解时就要求给出验收标准，而不是执行完再想怎么判断。验收标准最好是可检查的：字段齐全、引用可解析、数值在范围内、测试通过。第二，退回只允许一次，且必须带具体原因与修改建议，避免子代理在同一个问题上反复试错。第三，全局一致性检查独立于单任务验收，防止每个子任务都“合格”，合起来却自相矛盾。

验收标准有可执行性的分级，工程上要分开对待。机器可校验的断言（字段、枚举、引用能否解析、数值范围）成本最低，应当占大多数；需要取证的断言（关键数字必须挂到来源 ID、时点与口径）次之，靠结构化输出约束；需要人判断的断言（措辞是否得体、商业取舍是否合理）成本最高，只能抽检。把三类混成一句“做好即可”，等于把验收责任推回给模型自己。

全局状态是这套机制的中枢。它至少要保存：原始目标与硬约束、子任务图与依赖、每个子任务的产出与证据、未决问题与冲突、已消耗预算。子代理只拿到与自己相关的切片，而不是整份全局状态；收回结果时，Superagent 更新全局状态并判断是否需要重排。这样既控制了上下文，又保证了跨任务的一致性。

自我修正有两个层次。局部修正是退回某个子任务重做，成本低，适合实现层面的错误；全局修正是重排计划甚至修改目标分解方式，成本高，适合方向性错误。触发条件要写死：局部修正用于验收不通过且原因可定位；全局修正用于多个子任务结论冲突、关键前提被证伪或预算消耗与进度明显不匹配。把两者混为一谈，系统就会在细节上反复打磨，却不肯承认方向错了。

## 四、工程取舍与反例

第一个取舍是编排深度。一层派发最容易控制，两层以上会出现“子代理再派子代理”的递归，预算与责任都难以追踪。可行的约束是限制最大深度，并要求每层都必须能独立验收，不能把验收责任一路下推。

第二个取舍是集中与自治。Superagent 集中决策，一致性好但容易成为瓶颈；子代理高度自治，响应快但可能各自为政。折中方案是“目标集中、方法自治”：目标、约束与验收标准由上层定，具体怎么做由子代理决定。

第三个取舍是成本与可靠性。多一层编排就多一次模型调用、多一次上下文构造、多一次结果解析。示意场景下，三层编排的 token 消耗可能是单 Agent 的数倍（来源：示意），因此只有在任务确实需要分工时才值得。判断标准是子任务能否并行、是否超出单上下文、是否需要不同工具权限。

常见反例有三类，正好对应三条判定标准。其一是目标漂移：分解后的子任务越做越细，最后完成了一堆局部目标，却偏离了原始意图；这是全局状态缺失。其二是子任务重复：两个子代理查了同一份资料、做了同一件事，浪费预算还可能给出冲突结论；这是派发前缺少去重与依赖分析。其三是验收放水：Superagent 只读子代理的总结，不看证据，子代理说“已完成”就接受；这是验收权形同虚设。

还有一类反例是“编排表演”：系统画出了漂亮的多代理拓扑，实际上每个子代理都调用同一个模型、拿同一份上下文、做同一类判断，只是换了角色名。这种系统增加了成本，却没有增加组织能力。识别方法很简单：看子任务是否真的可以独立验收，看子代理是否真的拥有不同的工具与权限，看失败是否真的能被定位到某个子任务。

## 五、工程案例：一个多代理的投标应答场景

某团队用 Superagent 做招标应答（示意）：输入是一份六十页的招标文件加公司资质库，目标是在三天内产出应答初稿。它拆出六个子任务——资质核验、技术方案、报价测算、法务风险、排版成稿、独立复核，分别派给六个子代理。

第一个冲突是共享前置被重复拉取。报价与资质都要用“人员简历底册”，两个子代理各自查了一遍，抽查时发现人数口径差三人。处理是在派发前做一次依赖分析，把共享的只读查询提到上层执行一次，产物带内容摘要后分发；子代理只能读、不能改，口径以该产物为准。

第二个冲突是环形等待。商务子代理等资质结果，资质在等技术方案确认范围，技术在等商务给交付边界，四个小时空转。处理是允许破环：子代理可以带着显式假设继续，但假设必须写入全局状态并标注“待确认”，复核阶段优先检查假设是否成立。环不是靠更强的规划消除的，而是靠“假设—验证”的显式机制绕过的。

第三个冲突是复核失效。独立复核子代理只读了各方的总结，接受了一条已被否决的技术参数。处理是把复核从“读总结”改成“抽检证据”：随机抽一成结论，回查到原始来源与时间点；抽检不通过的，整份复核重做。抽检比例和成本直接相关，这个比例本身是个需要业务确认的参数。

结果：初稿在两天半内交付，返工集中在法务措辞而非数据矛盾。代价是多了一层产物版本管理，且“待确认假设”清单最后仍需人工收尾。这个代价是值得的，因为它把不确定性集中到了一个小清单上，而不是散落在六十页文档里。

## 六、边界与失败模式

编排替代不了领域判断。投标要不要压低报价、要不要放弃某个不擅长的标段，这些是商业取舍，Superagent 只能把选项和依据摆清楚，不能替你决定。让模型“自行判断商业策略”，得到的通常是最像平庸答案的那个。

验收不能全自动。需要人判断的断言越多，人就越可能成为瓶颈；反过来，为了跑通而把这类断言删掉，等于把风险留给出稿之后。可行的做法是固定抽检比例与升级规则，而不是追求全自动验收。

深度限制不是万能的。浅编排下子代理仍可能越权——不是通过再派发，而是通过工具权限本身。所以深度约束要和工具权限授予一起设计，每个子代理的工具集应当贴着它的子任务目标。

验收本身会漏。任何验收都是一次判断，都会出现假阳性。降低这类风险靠抽检与外部对照（例如拿历史成交案例比对），而不是把验收模型换得更强。

## 七、落地检查清单

1. 每个子任务都有可判定的验收断言。判据是任取一个子任务，验收失败时能指出是哪条断言未通过。
2. 派发携带预算与截止时间。判据是超预算的子任务会被中断，而不是跑完才报错。
3. 退回次数受限且必须带原因。判据是轨迹中同一子任务的重试次数不超过一次。
4. 全局状态只有一个写入者。判据是子代理只能提交提案或事件，不能直接改全局状态。
5. 全局一致性检查独立于单任务验收。判据是所有子任务通过后仍有一次交叉校验，能发现互相矛盾的结论。
6. 子任务图无环，或有显式的破环机制。判据是规划阶段检测到环即拒绝，或用“待确认假设”显式破环并记录。
7. 验收看证据，不看总结。判据是随机抽样结论都能在证据层找到来源与时间点。
8. 最大编排深度受限且可观测。判据是超限派发被拒绝，并在轨迹中记录原因。
9. 子代理工具权限最小化。判据是每个子代理的工具集与其子任务目标一一对应，没有多余的写权限。
10. 失败可归因到子任务与断言。判据是最终失败报告能指到具体子任务、具体断言与已消耗预算。

## 八、常见误区与面试追问

**问 1｜接最强的模型、配几十个工具，不就是 Superagent 吗？**
那是更强的单兵。工具扩展动作空间，编排扩展组织能力。判定看三条：能否派发并规定输入与预算、能否按证据验收、能否维护跨子任务的目标与冲突。少一条，就只是一个工具很多的单 Agent。

**问 2｜子代理是不是越多越好？**
不是。协调成本随子任务数量上升，而收益只在“可独立验收”的子任务上成立。子任务切到无法独立验收的程度，合并阶段会变成第二次开发。判断粒度看耦合度，不看数量。

**问 3｜验收能不能交给另一个模型自动做？**
可以，但必须给它断言和证据，而不是给它总结。让模型读总结做验收，等于让它复述子代理的自我评价；同一模型自评还会系统性偏松。验收的价值来自证据，不来自裁判是谁。

**问 4｜全局状态会不会成为瓶颈或单点？**
会。常见缓解是按切片下发（子代理只拿相关部分）、单一写入者（并发提交提案而不是直接改）、事件化（记录状态变更而非只存终态）。这三点做不到，全局状态会从“一致性来源”退化成“并发冲突源”。

**问 5｜什么情况下不该上编排？**
任务线性、单上下文能装下、不需要不同工具权限时，编排只是加延迟和失败面。这类任务用单 Agent 加少量工具，配好验收与回滚，效果通常更好。编排是给“复杂度必须分摊”的场景准备的。

## 九、小结与延伸阅读

Superagent 的“超级”不在单次推理，而在组织：能派发、能验收、能维护全局状态，并在局部与全局两个层次上修正。它与“单 Agent + 多工具”的分界，是组织能力与动作能力的分界。判断一个系统是否名副其实，不看它有几个代理，而看它能否说清每个子任务为何被派发、依据什么被接受、出错时由谁重做。

延伸阅读建议：官方文档类可看主流编排框架对 supervisor 与子代理的实现；工程博客类可看多代理系统如何做任务分解与验收；论文类可关注多智能体协作中的任务分配与一致性研究。阅读时把“验收权在谁手里”作为主线，这比拓扑图更能说明系统的真实能力。
