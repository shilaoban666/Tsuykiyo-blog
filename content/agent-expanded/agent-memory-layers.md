## 一、开场问题：窗口越来越大，为什么还是记不住

一个常见的争论是：既然模型的上下文窗口已经能装下几十万字，为什么还要单独做记忆系统？把历史对话全部塞进去不就行了。实践很快给出反例。第一，成本和延迟随输入线性上升，长上下文意味着每一轮都为无关内容付费；第二，窗口再长也有边界，长任务累积的工具返回、日志与文档会轻易越过它；第三，也是更根本的，信息多不等于信息对，塞满窗口的结果往往是关键约束被埋在中段，模型反而更容易忽略。

所以记忆不是“存多少”的问题，而是“什么时候取什么”的问题。一个 Agent 如果记得用户三个月前的一次偏好，却忘了上一轮工具刚刚返回的失败原因，它的记忆系统就是失败的。本文给出一个三层记忆模型，并讨论写入、检索与遗忘三个动作如何共同决定记忆质量。

还有一个前提常被忽略：记忆的读者是模型，不是人。模型没有稳定的“通读”能力，它只看到这一个 token 序列，所以每种记忆形态都要回答同一个问题：这条信息以什么形式进入序列，才会在被需要的那一轮被真正用上。

## 二、概念界定：三层记忆各管什么

第一层是工作上下文，也就是本次运行中模型每一步真正看到的 token 集合。它的容量由模型窗口和预算共同决定，寿命以“步”为单位，失效方式是溢出或压缩。工作上下文的原则是只放决策必需的信息：当前目标、关键约束、最近若干步的观察、可用工具的摘要。它追求的是密度，不是完整。

第二层是会话记忆，跨越多轮对话但局限于一个会话或一个任务线程。它通常以摘要、结构化槽位或滚动窗口的形式存在，容量有限，通常只覆盖最近若干轮，寿命从小时到天。会话记忆解决的是“用户刚才说过什么”“这个任务已经完成了哪几步”，它的失效方式是摘要失真——多次压缩后，限定条件、否定句与例外被磨平。

第三层是长期记忆，落在外部存储里，可能是向量库、关系表、文档库或知识图谱。它容量近乎不受限，寿命以月计，失效方式是检索错、过期、污染与隐私违规。长期记忆解决的是“这个用户是谁”“这个组织有哪些稳定事实”，它必须与来源、时间、置信度一起存储，否则就是一堆无法追责的断言。

三层不是替代关系，而是缓存层次：长期记忆按需上浮到会话记忆，会话记忆按需装配进工作上下文。设计时要问的永远不是“放哪一层”，而是“这条信息在什么条件下应该出现在哪一层”。补充一个判断口径：信息变化频率越高，越应该待在上面两层；越高风险、越需要追责，越应该待在最下面一层并把来源写全。

## 三、机制拆解：写入、检索、遗忘

记忆系统真正的工程量在三个动作上。写入决定什么值得记，检索决定什么被取出，遗忘决定什么必须消失。三者缺少任何一个，系统都会在几周内退化成噪声仓库。

```yaml
memory:
  working:
    max_tokens: 24000
    keep_recent_steps: 6
    compress_at: 0.8
  session:
    summarize_every: 8          # 每 8 轮提炼一次
    slots: [goal, constraints, decisions, open_questions]
    ttl_hours: 72
  long_term:
    write_gate: "confidence >= 0.7 and has_source"
    dedup: "semantic + entity_key"
    retrieve:
      top_k: 6
      recency_weight: 0.3
      require_source: true
    forget:
      ttl_days: 180
      on_user_delete: hard
```

写入策略的第一条是门槛。不是每句话都值得进入长期记忆；稳定偏好、明确事实、已确认的决策才值得，临时情绪与一次性的中间结果不应固化。第二条是去重，按实体键加语义相似度合并，保留最新值与历史版本，而不是不断追加同义条目。第三条是溯源，每条记忆记录来源会话、写入时间、置信度与是否经人工确认。没有来源的记忆在出问题时无法判断该信谁。

检索策略要解决配额问题。工作上下文的空间有限，检索结果必须与最近观察、系统规则竞争名额。可行的做法是混合排序：相关性为主，时效与来源可信度为辅，并对同一实体的多条记忆做合并，避免六个片段说的是同一件事。检索结果还应带上时间戳与适用范围，让模型知道“这是三个月前的偏好，可能已变化”，而不是把旧事实当成当前约束。

遗忘常被忽略，但它是记忆系统能否长期可用的关键。三类遗忘必须同时设计：时效性遗忘，按 TTL 清理短期任务数据；纠正性遗忘，用户否认或事实变更时使旧条目失效而非删除，保留审计线索；合规性遗忘，用户要求删除时必须硬删除，并同步清理派生摘要与向量索引。只做前三层而不做遗忘，系统迟早会因为一条过期事实给出自信的错误答案。

三者之间还有一条隐含耦合：写入时的结构决定检索时的可排序性。只存一段自然语言，检索就只能靠相似度；同时存了实体键、类型与适用范围，才能先按类型过滤再排序。省在写入环节的成本，会以检索精度和排查难度的形式还回来。

## 四、工程取舍与反例

第一个取舍是摘要还是原文。摘要省 token，但会丢失限定条件；原文保真，但挤占预算。稳妥的组合是“摘要常驻 + 原文可回查”：摘要里保留结论与指针，需要细节时再按指针取原文。这样既控制上下文，又保留了可解释性。摘要里最好显式保留“否定与例外”，例如“不要发给个人邮箱”这类约束一旦被磨平，后面的所有推理都会建立在错误前提上。

第二个取舍是自动写入还是确认写入。全自动写入体验好，但噪声与错误会累积；全确认写入质量高，但用户很快会厌倦。折中方案是按风险分级：低风险偏好自动写入并标记置信度，高风险事实（金额、权限、医疗与法律信息）必须确认或双源校验。

常见反例有四类。其一是“全量回放”，每轮把完整历史塞进上下文，短期效果尚可，成本随轮次增长，且模型对中段信息利用率下降。其二是“摘要套摘要”，连续压缩十几轮后，摘要里只剩下“用户讨论了几个问题”，约束全丢。其三是“只写不读”，记忆库越建越大，但检索从未接入主流程，等于没有。其四是“只读不删”，用户已经更正的信息仍被召回，系统在旧事实与新事实之间摇摆。

还有一个隐蔽的反例是把记忆当成状态机。记忆是概率性的、可能过期的参考信息，而任务状态必须是确定的、可校验的。把“任务已付款”这种关键状态放进向量库靠相似度检索，是把确定性交给了不确定性。正确做法是状态放数据库，记忆放检索层，二者通过实体键关联。

## 五、工程案例：一封发错地址的对账单

背景示意：某财务助手接入了记忆系统，三层都做了。用户与它打过半年交道，长期记忆里存着偏好、常用对象与一批历史结论。

输入（5 月的一次会话）：“把这个月的对账单发给张明。”历史上 3 月还说过一句话：“对账单只发 finance-ops 这个组邮箱，别发个人邮箱。”

失败轨迹（示意）：写入门槛只校验了“有来源”，两条信息都进了长期记忆，但都没带类型。检索时 top_k=6、相关性排序，“张明”这条因为与当前请求字面高度相关排在第一，“组邮箱”这条排第五且片段里恰好只截到了“.com”结尾。会话摘要链在第 8、16、24 轮各压缩一次，3 月那句否定句在第二次压缩后就消失了。模型据此判断收件人是张明个人邮箱，发送成功，返回 `{delivered: true}`。

处理（四项改动）。其一，写入增加类型字段：约束类（constraint）与任务参数类（task_param）分开，前者要求来源会话 id 加确认人，后者只允许进会话层，不进长期库。其二，去重键改为 entity_key=statement_recipient，同键多条按 updated_at 保留最新，但 constraint 不允许被 task_param 覆盖；值冲突时返回“存在冲突，需确认”，而不是静默取一条。其三，检索改为类型配额：constraint 最多占 2 个名额且强制入列，task_param 占 1 个，其余按相关性；每条结果附带时间戳与适用范围。其四，摘要策略改为“否定句与数字不参与压缩”，并保留指向原文的指针。

结果（示意）：同一批 60 次发送任务中，发错地址 0 次，其中 7 次因冲突返回了确认请求；工作上下文里记忆相关部分从约 3.1k token 降到约 1.4k，因为不再需要塞入五六个互相重复的片段。改动没有引入新模型，全部落在写入结构与检索规则上。

这类事故的教训不在“记得更多”，而在“记得有类型”。记忆系统一旦把偏好、约束、任务参数混在同一堆向量里，检索就只能靠字面相似度做决定，而字面相似度恰好是最不懂业务语义的那种信号。

## 六、与相邻概念的边界

记忆常与三个相邻概念混在一起，边界不清就会重复造轮子。

记忆与 RAG 的区别在对象：RAG 检索的是外部知识库，回答“世界上有什么”；记忆检索的是交互历史与用户事实，回答“我们之间发生过什么”。两者可以共用一个向量基础设施，但写入策略完全不同——知识库可以离线灌入，记忆必须在线受控写入。

记忆与状态机的区别在确定性：状态可枚举、可校验、必须唯一；记忆是概率参考、允许过期与冲突。把订单状态、审批节点这类东西放进检索层，等于用相似度代替主键。

记忆与微调的区别在时效与成本：微调把知识压进权重，适合稳定风格与格式，不适合“昨天改了口径”的事实；记忆外置，改一条记录就能生效，也能删。选择标准是变更频率，不是数据量。

## 七、落地检查清单

1. **分层有寿命**：三层各自的容量、寿命、失效方式写进配置，能被代码读取，而不是只写在设计文档里。
2. **写入门槛可执行**：`confidence >= 0.7 and has_source` 这类条件由代码判定，且拒绝写入的原因可统计。
3. **每条记忆五元组齐全**：来源会话、写入时间、置信度、适用范围、是否人工确认。缺字段的条目视为不可检索。
4. **类型可区分**：约束、偏好、任务参数、结论至少四类分开存储，检索时按类型配额而非混合排序。
5. **去重可复现**：同一 entity_key 的去重结果是确定的，且能看到被合并掉的历史版本。
6. **冲突显性化**：同键不同值时返回冲突并请求确认，不允许静默取一条。
7. **检索带元信息**：每条召回结果都带时间戳与适用范围，模型能看到“这是三个月前的”。
8. **遗忘三类齐全**：TTL 清理、纠正性失效（保留审计）、合规硬删（含派生摘要与向量索引）。
9. **状态不进检索层**：任务状态、金额、权限等确定性数据存在关系表，通过实体键关联。
10. **召回可回归**：维护一组“应召回／不应召回”的固定用例，任何记忆策略改动后跑一遍。

## 八、常见误区与面试追问

**追问一：窗口已经很大了，单独做记忆系统是不是过度设计？**

答：不是容量问题，是配额问题。窗口越大，无关内容越多，关键约束被埋的概率越高，而且每一轮都在为历史付费。记忆系统真正买到的是“选择权”——决定这一轮该看什么，窗口大小买不到这个。

**追问二：把历史定期摘要一遍，不就等于有了长期记忆？**

答：摘要能保住结论，保不住约束与例外。多次压缩后，“不要发给个人邮箱”这类否定句最先消失，而它恰好是决策的关键前提。可行做法是摘要常驻加原文指针，关键约束不进摘要通道。

**追问三：检索 top_k 调大一点，召回率不就上去了？**

答：召回上去、精度下来，而且挤掉的是最近观察与系统规则的名额。更麻烦的是重复片段：同一件事被六个片段重复描述时，模型会误以为它更重要。配额加去重比调大 top_k 有效。

**追问四：记忆写错了怎么办，让用户自己去删？**

答：用户不会去删，也找不到在哪删。要么在写入时按风险分级要求确认，要么在检索时把低置信条目降权并标注来源，要么提供“这条不对”的反馈入口并联动纠正性遗忘。三者至少要有一个。

**追问五：长期记忆能不能直接当用户画像，给运营做分群？**

答：技术上可以，合规上要另说。记忆里混着用户原话、推断结论与第三方信息，直接导出去做画像会把推断当事实。做法是把“原始事实”和“推断标签”分开存，画像只用经过确认的那部分。

## 九、小结与延伸阅读

记忆分层的目的不是造一个更大的仓库，而是让正确的信息在正确的时刻进入上下文，并在不该出现时消失。工作上下文管密度，会话记忆管连续性，长期记忆管稳定性；写入要有门槛与溯源，检索要有配额与时效，遗忘要有 TTL 与合规删除。三者合起来，才是一个可运维的记忆系统。

延伸阅读建议：论文类可看检索增强生成与 agent memory 综述，重点关注写入筛选与检索评测方法；官方文档类可对比各家长上下文最佳实践与缓存机制；工程博客类可看主流框架 memory 组件的生命周期设计。阅读时留意它们如何定义“遗忘”，这通常比“记住”更能暴露设计水平。
