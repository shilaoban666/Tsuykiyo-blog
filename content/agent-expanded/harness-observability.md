## 一、开场问题：回答错了，然后呢

线上反馈“这个 Agent 答得不对”，工程师打开日志，只看到最终回复和几条零散的打印。想知道当时检索到了什么、模型为什么选了那个工具、工具返回了什么、是不是权限被拒后模型自己编了一个答案——全都查不到。于是只能复现：把同样的问题再问一遍。但模型有随机性，工具状态也变了，复现出来的往往不是同一个问题。

可观测性要解决的正是这件事：让一次运行的决策链路可以被完整回看。它不是“多打几行日志”，而是建立一套数据模型，把提示、候选动作、工具参数、返回值、耗时与成本挂到同一条轨迹上，并且让失败可以被分类、被统计、被归因。没有这套东西，Agent 的迭代只能靠感觉。

## 二、概念界定：trace、span 与 event

沿用分布式追踪的术语，但赋予 Agent 场景的含义。一次用户请求或一个批处理任务对应一个 trace，trace id 贯穿始终。一次模型调用、一次工具调用、一次上下文压缩、一次审批等待，各对应一个 span，记录开始时间、结束时间、状态与关键属性。细粒度的事实，例如“检索命中三条”“参数校验失败”“预算剩余多少”，记录为 event，挂在所属 span 上。

Agent 的 span 有几类专属属性必须记录。模型调用要记录模型名与版本、输入 token、输出 token、是否命中缓存、采样参数；工具调用要记录工具名、规范化参数、副作用等级、是否命中幂等键、返回码与耗时；上下文装配要记录各层占用、被压缩的内容与指针；权限判定要记录申请的能力、判定结果与审批人。缺少任何一类，归因就会断链。

成本核算要能落到单任务。模型费用按 token 与单价计算，工具费用按调用次数或外部计费计算，基础设施费用按运行时长分摊。关键是口径统一：输入 token 是否含系统提示、缓存命中如何计价、重试是否重复计费，都要在指标定义里写死。口径不一致，团队之间的成本数字就对不上，优化也无从谈起。

## 三、机制拆解：指标、采样与归因

指标不在多，而在能回答四个问题：任务是否成功、花了多少步、花了多少钱、慢在哪。对应五个核心指标：任务成功率、平均步数、单任务 token 消耗、端到端时延分位、单任务成本。每个指标都要带维度：任务类型、模型版本、工具集版本、租户。没有维度的平均值会掩盖问题。

```yaml
observability:
  trace:
    sample: {errors: 1.0, slow: 1.0, normal: 0.1}
    redact: [phone, id_card, token, cookie]
    retain_days: {full: 14, metrics: 180}
  spans:
    model:  [model, version, tokens_in, tokens_out, cached, latency_ms]
    tool:   [name, args_hash, side_effect, idempotent_hit, code, latency_ms]
    context:[layer_usage, compressed, pointer_ids]
    guard:  [capability, decision, approver]
  metrics:
    success_rate: "accepted_tasks / finished_tasks"
    cost_per_task: "model_cost + tool_cost + infra_share"
    latency: "p50, p95, p99 by task_type"
  attribution:
    classes: [model_choice, tool_defect, context_missing,
              permission_denied, dependency_failure, acceptance_error]
```

采样策略要按风险分层。错误与慢请求全量保留，正常请求按比例采样；涉及资金、权限、对外发送的任务不做降采样。这样既控制存储成本，又保证关键事件可追。脱敏必须在写入前完成，而不是查询时再做，否则敏感数据已经落盘。

失败归因是这套体系最有价值的部分。把失败分成六类：模型选择错误（工具选错、参数填错）、工具缺陷（返回格式不符、超时、幂等失效）、上下文缺失（该给的信息没给）、权限拒绝（能力不足或被策略拦截）、外部依赖故障（下游不可用）、验收错误（判定标准本身有问题）。每类对应不同的修复路径，也对应不同的责任团队。分类不准确，修复就会打错靶子。

归因不能只靠人工。可以从轨迹里自动提取特征：工具返回码、是否重试、上下文各层占用、模型是否在权限拒绝后继续尝试。用这些特征做规则打标，再人工抽检校正。随着样本积累，规则可以逐步细化，最终形成可统计的失败分布，而不是每次事故都从零分析。

## 四、工程案例：一次真实的归因失败

示意场景。一个客服 Agent 回答退款政策问题，答案与现行规则不符。值班工程师按流程查 trace：有 model span，有 tool span，模型调用了检索工具，最后输出了答案。归因系统把这次失败打了 `model_choice` 标签——理由是“没有工具错误码、没有超时、没有权限拒绝记录”。

真相不是这样。那天的 trace 里缺了两类 span。其一是 context span：没有任何字段记录这次装配塞了哪些证据、各层占了多少 token。其二是 guard span：检索工具实际上返回了 403，因为这个租户的检索配额当天用完了。403 被工具网关吞掉，只在一个内部计数器上 +1，没有写入轨迹；模型拿到的是一个空结果，于是按上下文里残留的旧话术作答。

归因错了，修复方向就错了。团队花了三周调提示词，让模型“不要编造”，问题却在另一批租户上复发——配额耗尽不是提示词能解决的。真正的修复是两件事：检索失败必须作为 observation 显式上抛，模型不得在检索为空时给出政策结论；租户配额要有独立告警，而不是等答案错了再倒查。

这次失败还暴露了三个成本与完整性问题。第一，tool span 只记了 `args_hash` 没记参数，事后无法判断模型到底检索了什么关键词，只能靠猜。第二，归因标签由“有无错误码”规则生成，规则本身假设了“所有失败都会留下错误码”，而 403 被吞掉正好违反了这个假设。第三，成本汇总漏了重试：账单比 trace 汇总高三成（示意），因为重试的调用没有独立 span，被合并进了同一次工具调用的耗时里。

修复后加了四样东西。补齐 context span 与 guard span，后者记录“申请的能力、判定结果、拒绝原因”，403 也走同一条路径；tool span 存脱敏后的规范化参数，同时保留 hash 用于去重比较；运行时加一条校验：回答中若出现政策条款编号，必须携带对应的证据 id，没有证据 id 的回答直接降级为“转人工”；归因规则加一条否定条件——`model_choice` 只能在“上下文完整且无权限拒绝”时打，否则先查前两类。

值得说的是第四条。归因的价值不在于给失败一个名字，而在于让这个名字可被证伪。如果打标规则不能说明“在什么条件下这个标签不成立”，那它只是在给事故编故事。

## 五、工程取舍与反例

第一个取舍是全量记录与成本。完整保存每次模型输入输出，存储成本会随任务量线性增长，还可能触碰隐私红线。分层保留是现实解：结构化事件长期保留，完整上下文短周期保留并按错误/慢请求加权采样，敏感字段写入前脱敏。

第二个取舍是指标口径的复杂度。口径越细，越能定位问题，但维护成本也越高。建议先固定五个核心指标与四个维度，稳定运行一个季度后再扩展。频繁改口径，会让历史数据失去可比性。

第三个取舍是实时性与准确性。实时看板便于发现突增，但流式计算容易在重试与延迟到达上出错；离线核算准确，但有滞后。可行做法是实时看趋势、离线做结算，两者共用同一套事件定义。

常见反例有四类。其一是“只记结果”，最终答案入库，中间过程丢弃，失败无法归因。其二是“指标无维度”，全站成功率看起来稳定，某个租户或某类任务其实已经崩了。其三是“成本不计重试”，账单远高于预估，却找不到是哪类重试造成的。其四是“脱敏靠查询”，日志里明文存着手机号与令牌，合规审计直接不通过。

还有一个常见反例是把可观测性做成“事后工具”。真正有用的轨迹数据应该在运行时就被使用：循环控制用它检测打转，权限模块用它关联审批，评测系统用它回放失败样本。只在出事故时才打开，等于浪费了最有价值的信号。

## 六、指标与阈值怎么定

五个核心指标之外，还需要三个“元指标”，用来衡量这套观测本身靠不靠谱。

归因覆盖率：有明确归因类别的失败数除以失败总数，目标 100%。低于这个值，说明有一部分失败连分类都没有，讨论修复顺序没有意义。span 完整率：四类关键 span（model、tool、context、guard）齐全的任务占比，目标 95% 以上；缺失的往往是 context 与 guard，因为它们最容易被当成“内部细节”。采样偏差：采样集与全量的成功率差值，超过 1 个百分点说明采样策略偏了，通常是错误样本被过度采样。

核心指标的告警阈值建议这样定：成功率按小时滑动窗口比较，下降 2 个百分点持续一小时即告警；时延看 p95，翻倍即告警；单任务成本取上月的 p95 作为预算线，超出 20% 告警；平均步数没有绝对阈值，但分布形态突变（比如中位数不变、p99 翻三倍）必须查，那通常是某类任务在打转。

成本口径必须写死三条，否则不同团队算出来的数字永远对不上：输入 token 是否包含系统提示与工具定义；缓存命中的 token 按折扣价还是原价；重试产生的调用是否计入。三条都写进指标定义文档，并在看板上标注口径版本。

## 七、落地检查清单

1. trace id 贯穿全链路。判据：从用户请求到工具调用、审批、压缩，任意事件都能按 trace id 一次查出。
2. 四类 span 齐全。判据：抽样 50 条任务，model、tool、context、guard 四类齐全的比例达标。
3. 工具参数可还原。判据：span 里既有 args_hash 也有脱敏后的规范化参数，能回答“检索了什么”。
4. 失败可归因。判据：每条失败都有 attribution_class，且类别口径有文档定义。
5. 归因规则可证伪。判据：每条打标规则写明否定条件，抽检时能给出反例。
6. 成本口径写死。判据：系统提示、缓存、重试三条规则有版本号，看板标注口径。
7. 采样按风险分层。判据：错误与慢请求全量，敏感任务不降采样，配置可查。
8. 脱敏在写入前。判据：抽查存储层原始记录，不含手机号、证件号、令牌、cookie。
9. 轨迹被运行时消费。判据：循环控制、权限、评测至少各有一处读取轨迹数据。
10. 有回放能力。判据：能用历史 trace 重跑失败样本，且指标可对比。

## 八、常见误区与面试追问

问：多打日志不就是可观测性吗？
答：日志是原料，不是模型。可观测性要求数据有结构、可关联、能回答“为什么”：同一条 trace 上的输入、候选动作、观察、判定与成本要能串起来。散落在几十个文件里的 print，出事后仍然只能靠猜。

问：只存最终答案和 token 数，够不够？
答：够算账，不够排障。你无法回答“模型当时看到了什么”“它为什么选了这个工具”“工具到底返回了什么”。这三个问题答不上来，任何失败都只能归因为“模型不行”，而这通常是最没用的结论。

问：采样会不会漏掉关键故障？
答：会，所以采样必须分层。错误与慢请求全量保留，敏感与资金类任务不降采样，正常请求才按比例。另外要做采样偏差检验：定期比对采样集与全量的成功率，差值超过阈值说明策略偏了。

问：归因应该靠人工还是自动？
答：先自动后人工。自动规则负责把失败分成大致几类，人工抽检负责校正规则、补充新类别。纯人工撑不住量，纯自动会自我强化错误假设。关键机制是让规则可证伪：每条规则都要说明什么情况下它不成立。

问：成本口径为什么要写死，难道不是按账单算就行？
答：账单只有总数，没有归因。要优化成本，必须知道钱花在哪个任务类型、哪类重试、哪个模型版本上，这要求统一口径。口径不统一时，两个团队会得出互相矛盾的结论，最后谁也不信这些数字。

## 九、小结与延伸阅读

Agent 的可观测性，本质是让决策可回溯：同一条 trace 串起提示、动作、观察、权限与成本，五个指标回答成败、步数、费用与快慢，六类归因把失败变成可分配的修复任务。做到这些，团队才能从“再问一遍看看”转向“看轨迹定位”。更进一步，轨迹本身也是产品资产：它记录了真实任务的分布，能反哺提示、工具与预算的调整。

判断一套观测是否够用，有个简单测试：随便挑一次线上失败，问“它当时看到了什么、做了什么、为什么这么做”。五分钟内能答出来，说明可用；答不出来，日志再多也只是噪声。

延伸阅读建议：官方文档类可看分布式追踪的 span 与语义约定；工程博客类可看 Agent 平台如何做轨迹回放与成本核算；论文类可关注 agent 评测中对失败模式分类的讨论。阅读时重点看“口径如何定义”，这决定了指标能不能跨团队对齐。
