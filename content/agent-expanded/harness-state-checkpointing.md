## 一、开场问题：恢复之后，它把已经做完的事又做了一遍

一个处理报销的 Agent 在第三步调用付款接口时遇到进程重启。平台有检查点，恢复后从第四步继续，看上去很稳。但用户随后收到两笔相同的付款：重启前那次调用其实已经成功，只是响应在写回状态前丢失了；恢复后系统认为该步未完成，又执行了一次。团队补了“付款前先查状态”的逻辑，却在另一个工具上遇到同样的问题——发邮件没有可查的状态。

断点续跑不是“把上下文存下来再读回去”这么简单。真正的问题是：哪些事实已经发生、哪些只是计划、哪些副作用不可重复。状态设计要能回答这些问题，否则恢复越顺畅，重复执行越隐蔽。

恢复机制越完善，重复执行越难被发现。没有检查点的系统重启后从头再来，错误是显性的；有检查点的系统只重跑“未完成”的那一步，而它判断“未完成”的依据，恰恰可能是丢失响应造成的误判。这是一类特殊的故障：系统的自愈动作本身就是错误来源。

## 二、概念界定：事件日志与快照

状态可以分成两类载体。事件日志是只追加的事实序列，记录每一次决策、每一次工具调用、每一次观察，以及它们之间的因果关系。它保证审计：任何最终结果都能追溯到具体的输入与动作。快照是某一时刻的完整状态副本，用于快速恢复，避免从头重放几千条事件。二者不是替代关系，而是互补：日志负责“发生了什么”，快照负责“现在是什么”。

两类载体必须版本对齐。快照记录它对应的事件序号与状态 schema 版本；恢复时先加载快照，再重放其后的事件。若 schema 在期间发生过迁移，还要先对快照做升级，再重放。版本不对齐的快照比没有快照更危险，因为它会让系统在一个自洽但错误的状态上继续运行。

状态还应分层。会话层保存用户偏好、长期目标与跨任务的约束；运行层保存本次任务的计划、预算与阶段；步骤层保存当前动作的参数、结果与重试计数。三层的生命周期不同，存储介质也应不同：会话层进数据库，运行层进带 TTL 的键值存储，步骤层进事件流。混在一起，会导致一次简单的步骤重试也要重写整个会话。

## 三、机制拆解：检查点位置与幂等恢复

检查点的位置比频率更重要。最关键的三个位置是：模型做出决策后、工具调用发起前、工具返回后。发起前落盘的是“意图”，返回后落盘的是“结果”。只有意图没有结果，恢复时状态是“不确定”，不能假设成功，也不能盲目重试；只有结果没有意图，则无法解释这个结果为何出现。

```yaml
checkpoint:
  store: "event_log + periodic_snapshot"
  snapshot_every_steps: 20
  on_event: [decision_made, tool_intent, tool_result, human_decision]
  recovery:
    load: "latest_snapshot_then_replay"
    schema_version: 3
    uncertain_action: "query_then_decide"   # 先查副作用，再决定是否重试
    max_replay_events: 500
  idempotency:
    key: "run_id + step_id + tool_name"
    store_ttl_days: 7
    on_duplicate: "return_cached_result"
```

这段示意配置里，uncertain_action 是恢复逻辑的核心。工具调用前已落盘、调用后未落盘，说明副作用可能发生也可能没发生。此时不能让模型“再试一次”，而应执行一个补偿查询：如果工具有查询接口，先查这笔操作是否存在；如果没有，就转人工确认或走对账流程。把“不确定”当成一种正式状态，是幂等恢复的前提。

幂等键的设计要与业务实体绑定，而不是与进程或时间绑定。run_id 加 step_id 能保证同一步不重复，但跨恢复、跨重试时 step_id 可能变化，因此还需要业务键，例如订单号加动作类型。两层键结合，才能既防同一步重复，又防不同步的同一业务动作重复。

还要注意幂等键要覆盖“框架层的重试”。很多 HTTP 客户端会在超时后自动重试，如果重试时换了新的请求 id，服务端就会当成两次独立请求；agent 层的幂等键再正确也没用，因为请求根本没有带上它。正确做法是把幂等键在意图落盘时生成，并沿调用链一路透传，包括 SDK 重试、网关重试与代理重试。

schema 演进要有一份检查清单。新增字段必须可空或有默认值；删除字段先标记弃用，保留至少一个版本的读取兼容；枚举扩展要考虑旧客户端遇到未知值的降级；状态机新增状态要定义迁移来源与去向。每次迁移都应留下版本号与迁移脚本，且迁移后的快照要能被旧版本安全拒绝，而不是被误读。

## 四、工程案例：一次真实的重复执行故障

示意场景。一个报销 Agent 的第三步是调用 `payment.transfer(order_id, amount)`。检查点按设计在三处落盘：决策后写 `decision_made`，调用前写 `tool_intent`，返回后写 `tool_result`。

故障链条是这样断的：`tool_intent` 落盘成功，HTTP 请求发出，对端处理成功，但响应在网关处超时。客户端 SDK 的默认策略是超时重试一次，重试时生成了新的 `X-Request-Id`，对端又把同一笔转账执行了一遍。第二次响应回到进程时，服务正好因内存超限被 kill，`tool_result` 没有写回。三十分钟后告警恢复，重放事件，系统看到 step 3 有意图、无结果，判定“未完成”，于是再发一次。

结果是一笔报销付了三次。当天日志里看不出异常：每一步都有事件，状态机每次都迁移正常，恢复流程也按设计执行。问题在 T+1 对账时才被发现。

从轨迹里能还原出三个当时的信号。其一，同一个 step_id 下有三个 tool span，但只有一个 `tool_result` 事件——span 数量与结果事件数量不一致，这是“副作用已发生但状态未确认”的直接证据，却没有任何告警在看这个差值。其二，幂等键用的是 `run_id + step_id + tool_name`，而重试路径里 step_id 自增了一次，键随之改变，去重表里出现两条不同记录。其三，SDK 重试的那次调用根本没有带 agent 层的幂等键，它只是把原始请求重放了一遍。

修复分四层。幂等键改成业务键优先：`order_id + "transfer" + 业务版本`，由意图落盘时生成并写入请求头，SDK 重试复用同一个值；`tool_intent` 落盘时同时写 `pending` 标记，恢复时遇到 pending 且无结果，统一走 `query_then_decide`，由对端查询接口确认是否已存在该笔转账；增加对账任务，对超过阈值仍未确认的 pending 动作做人工核对；把“span 数与 result 事件数不一致”做成监控项，差值大于零即告警。

还有一处设计要改：原来的恢复逻辑把“有意图无结果”直接映射为“重试”。这个映射在只读工具上无害，在写工具上就是把不确定性当成了失败。正确的默认值是“不确定即查询”，查询不可得才升级为人工，不要默认重试。

## 五、工程取舍与反例

第一个取舍是落盘频率与性能。每一步都同步落盘最安全，但会增加延迟；批量异步落盘更快，却可能在崩溃时丢失最后几步。可行的折中是：决策与工具意图同步落盘，工具结果异步落盘但带确认机制；关键写操作前后强制同步。用业务风险决定持久化强度，而不是一刀切。

第二个取舍是事件日志的体量。完整记录提示与返回值会让日志迅速膨胀，只记摘要又难以复盘。常见做法是分层存储：结构化事件长期保留，完整上下文按采样或异常触发保存，并设置保留期。这样既控制成本，又保留追责能力。

第三个取舍是恢复策略。自动恢复体验好，但如果状态不确定，自动恢复可能放大错误。稳妥的策略是分级：只读任务自动恢复，写任务先做补偿查询，高风险任务恢复后强制人工确认。恢复不是越快越好，而是越可解释越好。

常见反例有四类。其一是“只存对话”，把消息历史当状态，工具结果与决策理由丢失，恢复后模型只能重新猜。其二是“快照覆盖”，每次覆盖同一份状态，没有事件日志，出错后无法回放。其三是“恢复即重跑”，不区分已发生与未发生，把整个计划从头执行一遍。其四是“迁移即改字段”，直接改 schema 而不处理旧快照，恢复时读到缺失字段，行为悄悄退化。

还有一个容易被忽略的反例：把检查点写进模型上下文。上下文是易失的、会被压缩的，把关键状态放在里面，等于把持久化交给了摘要器。正确做法是状态存外部，上下文只放当前需要的投影。

## 六、与相邻组件的边界

状态存储很容易和周边组件职责重叠，边界不清就会互相推诿。

与消息队列：队列通常只保证至少一次投递，重复消费是常态。恢复逻辑叠在队列之上，如果指望队列提供恰好一次，等于把幂等责任外包给了一个不提供该保证的组件。分工应是队列负责送达，Agent 负责幂等。

与工作流引擎：引擎的检查点语义是节点级重试，它知道节点是否成功，但不知道模型在节点内部做了什么决策，也不理解“不确定”这种状态。两套状态机不应互相嵌套，用事件 id 关联即可。

与缓存：缓存随时可以失效，不能承担持久化。把未完成的意图放缓存，重启即丢，等于没有检查点。

与审计日志：审计面向合规，不可变、长期保留、字段偏业务；事件日志面向恢复与重放，需要完整技术细节。两者可以共用 trace id，但不要合并——合规要求会拖慢写入，脱敏规则又会破坏重放。

与上下文：上下文是投影，不是状态。它按需从状态里取当前步骤所需的部分，丢掉的部分必须还能从状态里取回。

判断某个数据该放哪，问两个问题：生命周期多长，谁需要读它。长于任务且要被人审计的进事件日志；只服务当前步骤的进上下文；只用于加速的进缓存。

## 七、落地检查清单

1. 事件日志只追加。判据：任何状态变化都产生新事件，代码里没有对历史事件的原地修改。
2. 快照带序号与版本。判据：每个快照记录对应事件序号与 schema 版本，恢复前先校验。
3. 三个检查点位置齐全。判据：decision、intent、result 三类事件都能在轨迹里找到。
4. 不确定是正式状态。判据：有意图无结果时，代码路径是查询或转人工，而不是重试。
5. 幂等键含业务键。判据：跨进程、跨重试键一致；构造重复调用只产生一次副作用。
6. 幂等键透传到重试层。判据：SDK 重试与网关重试携带同一键，能在请求日志里核对。
7. 幂等存储 TTL 够长。判据：TTL 大于最大任务时长的两倍，且有到期清理任务。
8. schema 迁移有清单。判据：新增字段可空或有默认值，删除字段先弃用一个版本，旧快照被新版本明确拒绝。
9. 恢复分级执行。判据：只读自动恢复、写任务先补偿查询、高风险恢复后人工确认，三条路径都有开关。
10. 有恢复演练。判据：定期注入进程 kill，验证恢复后副作用不重复、事件可完整重放。

## 八、常见误区与面试追问

问：把对话历史存下来，不就是状态了吗？
答：不够。对话历史只记录说了什么，不记录工具实际做了什么、结果是什么、决策依据是什么。恢复后模型只能根据历史重新猜测现场，猜错就重复执行。状态要记录事实，不是记录叙述。

问：既然有快照，为什么还要事件日志？
答：快照告诉你“现在是什么”，日志告诉“为什么变成这样”。排障要因果，审计要证据，重放要顺序，这三件事快照都给不了。反过来，只有日志没有快照，恢复要重放几千条事件，长任务的恢复时间不可接受。

问：幂等键用 run_id 加 step_id 不够吗？
答：只防得住“同一次运行的同一步”。跨恢复时 step_id 可能重排或自增，跨重试时可能换新 id，跨运行更不用说。业务键（订单号加动作类型）才是稳定的锚点，run_id 与 step_id 只适合做辅助。

问：恢复之后直接按原计划继续执行可以吗？
答：要看世界有没有变。恢复间隔可能是几秒，也可能是几小时；期间库存、权限、审批有效期、外部单据状态都可能变化。直接继续等于假设什么都没变。稳妥的做法是恢复时重新校验前置条件，不满足就重规划。

问：schema 加个字段为什么也算风险？
答：因为旧快照里没有这个字段。读取方如果默认字段存在，会拿到空值或抛错；如果默认字段有业务含义（例如“已审核”默认 false），就会把历史数据误判。所以新增字段必须可空或有明确默认值，且旧版本读到新快照要安全失败，而不是猜。

## 九、小结与延伸阅读

状态设计的核心是区分事实与视图。事件日志记录事实，保证可审计、可重放；快照记录视图，保证恢复速度；检查点记录边界，保证不确定的动作不被盲目重试。三者配合，断点续跑才不是重复执行的同义词。

最容易被低估的是“不确定”这一档。多数系统的状态只有成功与失败，于是“不知道成没成”被随手归入失败，恢复时重试一次——重复副作用基本都从这里来。把不确定做成显式状态，并配一条查询或人工的出口，比任何重试策略都更能止血。

延伸阅读建议：工程博客类可看事件溯源与幂等消费的实践文章；官方文档类可关注工作流引擎的检查点与补偿事务机制；论文类可关注分布式系统中共识与恰好一次语义的讨论。阅读时把“不确定状态如何处理”作为主线，这比记住存储选型更有价值。
