## 一、开场问题：通过率九成，上线却不行

一个团队给客服 Agent 建了评测集，两百条任务，跑出来的通过率看起来很漂亮，团队信心十足地上了线。第一周就收到大量投诉：用户的问题稍微绕一点，Agent 就开始反复调用同一个工具；遇到需要退款的场景，它倒是能给出正确答复，但把退款金额算错了，而评测集里这类任务只有两条，还都是简单情形。

复盘时发现三个问题。第一，评测集与训练/调试用的是同一批样本，提示词就是照着这些样本调的，属于典型的评测污染。第二，只看了最终答案对不对，没看过程，所以“绕了十步才蒙对”与“三步干净解决”被记为同一结果。第三，样本量太小，通过率的波动范围很大，团队把一次跑分当成了稳定结论。

本文讨论的是怎样搭一套能反映真实能力的评测体系：任务集怎么构建，过程指标看什么，通过率怎么解读。

## 二、概念界定：三层评测与两类指标

评测可以分三层。单元层测单个工具或单个判断，例如“给定订单号能否正确调用查询工具”；任务层测一次完整任务，例如“完成一次退款核查并给出结论”；系统层测多任务、多轮次下的整体表现，例如“连续处理一天的工单，错误是否会累积”。

本文主要讨论任务层与系统层。任务层的核心是任务集，系统层的核心是稳定性。两层都要回答三个问题：任务从哪来、什么叫通过、结果可不可信。

指标分两类。结果指标回答“做成了没有”，包括任务通过率、答案正确率、关键字段准确率。过程指标回答“怎么做的”，包括平均步数、工具调用次数、工具错误率、无效重复率、人工接管率、单任务成本、端到端时延。两类指标必须一起看，因为结果指标会被“蒙对”污染，过程指标会被“过度保守”污染——一个什么都不做、直接转人工的 Agent，过程看起来很干净，结果却什么都没完成。

## 三、机制拆解：任务集构建与统计口径

任务集的构建要解决来源、标注、去重、留出四个问题。来源应尽量贴近真实分布，从线上工单、客服记录、人工标注中抽取，而不是由工程师凭想象编写。标注要写清“什么叫完成”，最好落成可检查的断言，而不是一句“回答合理”。去重要按语义而不是字面，否则同一问题的十种问法会挤占样本。留出集必须在调提示之前就切好，并且调参期间不可见。

难度分层是必要的。可以按“单步、多步、需要跨工具、需要澄清、含对抗输入”分层，每层都要有足够样本。只测简单任务，通过率会虚高；只测最难的，又无法反映日常体验。分层之后，报告要按层给出通过率，而不是只给一个总数。

```python
def evaluate(agent, tasks, runs=3):
    report = {"by_difficulty": {}, "process": {}, "runs": runs}
    for task in tasks:
        outcomes = []
        for _ in range(runs):
            traj = agent.run(task.input)
            outcomes.append({
                "passed": task.assertions.all(traj.final_answer, traj.evidence),
                "steps": traj.step_count,
                "tool_calls": traj.tool_call_count,
                "tool_errors": traj.tool_error_count,
                "cost": traj.cost,
                "handoff": traj.human_handoff,
            })
        layer = task.difficulty
        report["by_difficulty"].setdefault(layer, []).extend(outcomes)
    return summarize(report)
```

这段代码有三个设计点。第一，每个任务重复跑多次，用多次结果估计稳定性，而不是一次定生死。第二，断言基于证据而不是最终文本，避免“说得像对的”被判通过。第三，过程字段与结果字段一起采集，后续可以分析“通过的任务平均几步”“失败的任务是否都伴随工具错误”。

统计口径要写死。通过率的分子是“多次运行中至少一次通过”还是“每次都通过”，结论完全不同；前者衡量能力上限，后者衡量稳定性，报告里必须标明。平均步数要说明是否包含失败任务，失败任务往往步数很长，混在一起会拉高均值。成本要区分模型成本与工具成本，否则优化方向会错。

置信区间不能省。样本量小的时候，通过率的波动很大，两次跑分差几个百分点可能只是噪声。报告里应给出区间，并在比较两个版本时看区间是否重叠。重复运行的方差本身也是指标：方差大说明行为不稳定，即使均值漂亮也不适合上线。

评测污染要从机制上防。除了留出集，还要做“时间去污”：用某个日期之前的数据建集，之后的线上数据做验证，避免模型见过未来。对检索类任务，还要检查索引版本是否与评测时一致，否则召回内容变了，分数不可比。

## 四、工程取舍与反例

第一个取舍是规模与成本。任务越多越可信，但每次评测都要花钱花时间。可行的做法是“小集高频、大集低频”：几十条核心任务每次提交都跑，几百条全量任务每日或每周跑一次。

第二个取舍是自动断言与人工评审。自动断言快、可重复，但对开放性任务难以覆盖；人工评审准，但慢且主观。折中是自动断言做初筛，人工只评审自动判不了的部分与抽样样本，并定期校准评审者之间的一致性。

第三个取舍是贴近真实与可控可复现。真实任务分布最可信，但输入长、依赖多、难复现；构造任务可控，但容易失真。可行的组合是“真实任务做回归、构造任务做边界”，两类分别报告。

反例有三类。其一是“自测自评”：用调提示的同一批样本做评测，通过率自然高。其二是“只看结果”：不记录步数与工具错误，无法解释为什么通过或失败，也无法发现“蒙对”。其三是“单次定论”：跑一次就宣布提升，忽略方差，下一次又下降，团队在噪声里反复横跳。

还有一类反例是“指标口径漂移”。这个月把“部分完成”算通过，下个月改回不算，历史数据就不可比。口径要版本化，改动要写进报告，否则趋势图会骗人。

评测报告本身也值得设计。一页纸能说清四件事就够：这次评的是什么版本、与上个版本差异在哪、哪些任务新失败、结论能不能支撑上线决定。把两百条任务的明细都贴上去，读者反而抓不住重点；把差异样本单独列出来，才是评审真正要看的部分。

## 五、工程案例：一次评测污染事件

以下场景为示意，数字用于说明量级，不代表任何真实系统。

某团队为退款客服 Agent 建了 200 条评测集，从最近三个月的工单里抽样。调提示的两周里，团队把失败样本一条条拿出来分析，其中 60 多条被直接写进提示的少样本示例。发布前最后一轮评测，通过率 91%，团队据此判断可以上线。

上线首周，投诉率没有下降。抽样 50 条投诉，人工复核后发现三类问题：一是问题换个说法就失败，二是多订单场景下漏处理，三是答案里堆了正确的关键词但金额算错。这三类在评测集里都没有体现。

复盘的第一个发现是样本泄漏：评测集里 200 条中有 140 条在调参期间被看过、改过提示、甚至直接作为示例写进提示。第二个发现是指标本身有洞：通过判定是“最终答案包含正确答案里的关键词”，于是模型学会了拼关键词，金额算错也能过。第三个发现是难度分布失衡：200 条里有 150 条是单轮单订单，多订单与需要澄清的场景加起来不到 20 条。

处置分四步。第一步，重新切分数据：从最近两个月工单中另抽 300 条做测试集，在调参结束前封存，只允许 CI 运行并只回传聚合指标。第二步，重写断言：从关键词匹配改为结构化校验——退款金额必须等于按规则计算出的值，订单号集合必须与输入一致，工具调用记录里必须有查询动作。第三步，按场景分层：单轮、多轮、多订单、需澄清、含对抗输入五层，每层单独报通过率。第四步，把历史分数作废并在报告里注明原因，避免拿新旧数字直接对比。

改造后再跑，通过率从 91% 掉到 68%。这个数字更接近真实水平，也更难被优化。随后两周迭代中通过率稳步升到 79%，同期线上投诉率下降，两边方向第一次一致。

复盘有三条结论。其一，污染不是道德问题，是流程问题：只要评测集对被调参的人可见，它就会不可避免地变成训练数据。其二，指标定义本身就是污染源，关键词命中这种口径会把优化引向“说得像”，而不是“做得对”。其三，分数下降有时是好事，它意味着度量变得更诚实；把“分数上涨”当目标，团队会先优化指标再优化能力。

## 六、评测污染怎么防

防污染的核心是把“能看”和“能改”分开，并让分数上涨必须付出真实代价。具体有五个动作。

数据隔离。至少分三集：开发集用于日常调试，验证集用于选方案，测试集只在发布前跑。测试集的访问要有记录，能跑测试集的人应当很少。

时间切分。用 t0 之前的工单做开发集，t0 之后的做测试集。模型与提示都不可能见过未来，这是最便宜的防泄漏手段。

语义去重。字面去重挡不住改写的问法。用嵌入做近邻检查，把测试集与开发集的高相似样本挑出来，人工判断是否算重复。阈值不作硬性规定，但检查报告要留档。

指标去污染。任何能被“堆关键词”满足的断言都会迅速失效。断言尽量读结构化结果与工具调用记录，迫使人去校验真实副作用。

泄漏巡检。定期做两件事：把测试集样本在开发集里找最近邻，看是否有高相似；监控分数是否出现无对应改动的跳升。跳升往往是泄漏或口径变化，而不是能力提升。

## 七、落地检查清单

以下九条按“这份评测能不能支撑上线决定”设计，每条带判据。

1. 三集分离且访问受控。判据：调参期间测试集不可被个人运行；谁跑过测试集在 CI 日志里可查。
2. 时间切分成立。判据：测试集样本时间晚于提示与示例的取材时间，报告里写明分界日期。
3. 语义去重有报告。判据：测试集与开发集的近邻检查已跑过，高相似样本有处置结论。
4. 断言基于证据。判据：断言读取结构化字段或工具调用记录；抽查三个任务，不改关键词也能判对错。
5. 通过口径版本化。判据：口径文件有版本号；口径改动后历史基线全部重跑，报告注明不可比。
6. 多次运行与区间。判据：每任务至少跑 3 次；报告给出置信区间；版本比较看区间而非点值。
7. 分层报告。判据：按难度与场景分层，每层样本量足够支撑结论；总数不能替代分层。
8. 过程指标同表。判据：步数、工具错误率、人工接管率与结果指标在同一张表里，能解释失败原因。
9. 污染巡检常态化。判据：每月一次近邻与分数异常检查，有结论、有签字。

清单本身要能被质疑：任何一条判据如果无法在半小时内验证，它就该被改写或删掉。

## 八、常见误区与面试追问

**问一：两百条任务够不够？**
看分层。两百条如果是均匀覆盖五个场景，每层只有四十条，置信区间会宽到无法判断差异；如果全部集中在单轮场景，数字再漂亮也不代表多轮能力。判断标准不是总数，而是“最关心的那一层有多少条”，以及报告里有没有给出区间。

**问二：用模型当裁判靠不靠谱？**
能用，但必须先校准。要做三件事：用人工标注的一小批样本测裁判与人的一致率；固定裁判的提示与版本，把它当作度量工具的一部分版本化；对位置偏置做交换顺序的复跑。没有一致率数据的自动裁判，只是把主观换成了另一个主观。

**问三：通过率掉了三个点，要不要回滚？**
先看区间，再看分层，最后看失败类型。区间重叠时不构成证据；区间不重叠但只掉在某一层，要判断那层是否是本次改动的影响面；如果失败集中在“新出现的错误类型”，即使总数只掉一点也该处理。

**问四：线上没有标准答案，怎么评？**
用代理指标加抽样复核。代理指标包括人工接管率、二次追问率、平均处理时长、投诉率；抽样复核由人按固定表单打分。关键是“代理指标与真实满意度的关系”本身也要被验证，否则只是在优化代理。

**问五：评测集多久换一次？**
取决于迭代速度与污染速度。换得太勤，跨版本不可比；换得太慢，提示会通过间接反馈过拟合。折中是保留一份固定的核心子集做长期趋势，另设一份轮换集做当期能力，两份分别报告，不混算总分。

## 九、小结与延伸阅读

Agent 评测的可信度，来自三件事：任务集与调试数据隔离、结果与过程指标并看、统计口径与置信区间写清。通过率只是一个入口，真正能指导决策的是“哪一层任务、因为什么、稳定不稳定”。

如果只能保留一个习惯：每次报告都写清“这次评的是哪一版、和谁比、差异是否在噪声范围内”。这句话能挡掉大部分自欺欺人的结论。
