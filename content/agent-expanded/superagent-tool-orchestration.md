## 一、开场问题：让模型自己决定先调哪个

一个报销审核助手接了六个工具：查员工、查发票、验真伪、查预算余额、写审核意见、发起打款。最初的做法是把六个工具全部交给模型，让它“根据情况自行决定调用顺序”。演示时很惊艳，模型会先查员工再验发票，看起来很像一个有经验的审核员。上线一周后出现一笔重复打款：模型在验真伪超时后重新走了一遍流程，第二次没有先查“是否已打款”，因为那个状态不在任何工具的返回值里。

这个案例说明，工具编排不是“把工具交给模型”那么简单。模型擅长在不确定的情况下做局部选择，不擅长维护一张跨工具的依赖关系与副作用约束。本文讨论的是：怎样把跨工具的调用组织成一张可分析的依赖图，在图上做并行、剪枝与降级，而不是把顺序决策全部外包给模型。

值得强调的是，重复打款不是模型“犯错”，而是系统没给它约束。模型看到的是“验真伪失败”，它选择重试，这是合理行为；真正的问题是重试路径上没有一条强制边要求先读账本状态。把这类缺陷归因于模型能力，会让团队一直在换模型，却始终不修图。

## 二、概念界定：依赖图与三类边

把一次任务涉及的工具调用画成有向图，节点是“一次具体的调用”，边是“必须先满足的关系”。边至少有三类。数据边：后一个调用的入参来自前一个调用的输出，例如打款需要发票 ID。约束边：后一个调用必须在前一个调用成功之后才能发生，例如验真伪通过才能写审核意见。资源边：两个调用共享同一份有限资源，例如同一个账户的余额、同一个接口的速率配额，它们未必有先后，但不能同时无约束地执行。

有了这三类边，才能谈并行。可并行的前提是：两个节点之间没有路径相连，且不共享资源边。只是“看起来无关”不够，很多事故就出在隐性的资源边上——两个子任务同时扣减同一笔预算，各自检查都够，合起来超额。

与“让模型自由串联”相比，依赖图的价值在于三件事：可分析（能算出关键路径与并行宽度）、可剪枝（前置条件不满足时直接跳过下游）、可补偿（失败时知道哪些已执行的节点需要撤销）。这三点都不是模型在一次推理里能稳定完成的。

节点还需要一个关键属性：副作用的可撤销程度。可以分成四级：纯读（无副作用、可无限重试）、计费读（可重试但会产生成本）、幂等写（可重试，需幂等键）、非幂等写（不可重试，只能补偿）。这个分级决定了重试策略、并发策略与失败处理，缺了它，图只是拓扑好看。

## 三、机制拆解：建图、调度与补偿

建图可以由模型辅助，但图本身要落成结构。一种可行的做法是让规划器输出节点与边的声明，再由运行时校验完整性，缺边就拒绝执行。

```yaml
plan:
  nodes:
    - id: n1
      tool: get_employee
      args: {emp_id: "$input.emp_id"}
      side_effect: read
    - id: n2
      tool: verify_invoice
      args: {invoice_id: "$input.invoice_id"}
      side_effect: read
      timeout_ms: 8000
    - id: n3
      tool: get_budget
      args: {dept: "$n1.dept"}
      side_effect: read
    - id: n4
      tool: check_paid
      args: {invoice_id: "$input.invoice_id"}
      side_effect: read
    - id: n5
      tool: write_opinion
      args: {invoice_id: "$input.invoice_id", verdict: "$n2.verdict"}
      side_effect: write
      idempotency_key: "$input.invoice_id:opinion"
  edges:
    - {from: n1, to: n3, type: data}
    - {from: n2, to: n5, type: constraint}
    - {from: n4, to: n5, type: constraint, when: "result.paid == false"}
```

这段声明里有两个关键字段：side_effect 与 idempotency_key。前者决定重试策略，只读节点可以放心重试，写节点必须带幂等键；后者让“重跑整张图”不会产生第二次副作用。缺失这两个字段的编排，一旦遇到超时重试就会重复写入。

校验完整性的重点是“入参可追溯”。每个节点的每个入参，要么来自输入，要么来自某条数据边的上游输出；出现无法追溯的入参，说明图缺边，应当拒绝执行而不是让模型即兴补全。这条校验能把大部分“看起来对”的图挡在执行之前。

调度器的工作是按拓扑序推进，同时受三个约束：资源配额、速率限制、关键路径优先级。一个实用的策略是“关键路径优先 + 就绪队列并行”：先算出从起点到终点的最长路径，路径上的节点优先获得配额；其余就绪节点在不违反资源边的前提下并行。这样在配额紧张时，延迟由关键路径决定，而不是被旁支拖慢。

失败传播需要事先定义。节点失败时有三种处理：整图回滚、局部跳过、替换实现。整图回滚适合强一致场景，例如付款；局部跳过适合旁支，例如补充材料；替换实现适合有备用工具的场景，例如主接口超时后切到缓存或备用供应商。选择哪种，取决于该节点的失败是否会污染下游结论，以及已执行节点是否产生不可撤销的副作用。

补偿是另一条线。对于已经执行且不可撤销的写操作，失败后不能“当作没发生”，而要执行补偿动作：撤销草稿、释放额度、发送更正通知。补偿动作本身也必须幂等，否则重试会把补偿做两遍。工程上常见的做法是把“正向动作 + 补偿动作 + 幂等键”作为一个事务单元登记，编排器按登记逆序补偿。

## 四、工程取舍与反例

第一个取舍是并行度。并行能压缩墙钟时间，但会放大瞬时配额消耗与外部接口压力。稳妥的做法是给每类资源设并发上限，并让调度器在配额不足时排队而不是报错。并行度不是越高越好，超过外部系统承受能力后，重试与限流会把收益吃回去。

第二个取舍是图的静态与动态。完全静态的图容易审计，但无法应对运行时才发现的分支；完全动态的图灵活，但每次都要重新规划，成本高且难以复现。折中方案是“骨架静态、分支动态”：主干与写操作固定，读操作与补充查询允许运行时扩展，但扩展出来的节点同样要经过校验。

第三个取舍是粒度。把每个 API 调用都作为一个节点，图会非常细，调度开销大；把一整段流程包成一个节点，又失去并行与补偿的精度。通常以“一次有意义的副作用边界”为节点粒度，读操作可以适当合并。

反例方面，最常见的是“无图直连”：模型想到哪调到哪，超时后从头再来，重复副作用无从约束。其次是“假并行”：图上并行了，但两个节点其实争同一份配额，实际仍是串行，还多了一层调度开销。第三是“只回滚不补偿”：写操作已经发生，回滚只是把本地状态改回去，外部世界没有复原。

## 五、工程案例：一个多代理的报销审核场景

把开头那套系统按依赖图重做一遍（示意），四处冲突都能定位到具体的边与字段。

输入：一张报销单（员工 ID、部门、发票号、金额），目标是在两分钟内给出审核结论并完成打款。

冲突一：重跑绕过账本。验真伪超时后整图重跑，重跑路径上没有读账本这一步，于是打了第二笔。处理是把 check_paid 从“可选查询”提升为打款节点的强制前置约束边，打款节点带幂等键 invoice_id:payout；重跑时先读账本状态，已打款则整条支路剪枝。这条修正的关键不是加一个工具，而是把一条隐性约束升级成显式边。

冲突二：假并行触发限流。查预算与查发票同时打同一个 ERP 接口，两者共享速率配额，实际互相触发限流退避，比串行还慢。处理是加资源边并按资源类型设并发上限（该接口并发 2），调度器在配额不足时排队而不是重试。收益是总时长稳定，代价是并行宽度被限制，局部场景变慢。

冲突三：补偿缺失。审核意见已写入 OA，打款失败后意见仍然是“通过”，运营据此认为已付款。处理是把写意见与打款登记为同一事务单元，失败时按逆序补偿：撤回意见、发更正通知。补偿动作带各自的幂等键，避免重试时补偿两次。

冲突四：该剪枝没剪。发票验真失败，下游仍然查预算、写意见，最后产出“审核通过但发票无效”的组合。处理是给 constraint 边加上 when 条件，失败即跳过下游并标注 skip 原因；最终结论由跳过状态决定，而不是让模型在残缺结果上自由发挥。

结果：重复打款归零，平均处理时长下降，失败单据的结论不再自相矛盾。代价是图要随业务流程变更同步维护，节点粒度调整（例如把验真伪拆成工商与税号两步）会牵动边与补偿登记，需要走一次评审。

## 六、如何验收：把依赖图变成可测对象

判断一张图是否真的可用，最直接的是“节点失败三问”：把任意一个节点标记为失败，问三个问题——哪些下游必须跳过，哪些已执行节点需要补偿，哪些旁支仍可交付。三个问题都能从图上直接读出答案，这张图才算完成；读不出，说明边或缺、或副作用未标注，图只是画给人看的。

第二项验收是重放：用同一份输入把整张图跑两遍，对账外部副作用，必须只发生一次。这项测试能同时暴露幂等键缺失、补偿重复与账本读取缺失，是投入产出比最高的一项。

第三项是配额压测：把并发上限压到正常值的四分之一，观察系统是退化为串行并给出预计等待，还是一片超时错误。能退化说明调度器在正常工作，直接报错说明缺失排队语义。

第四项是边完备性审计：取每个节点的入参，逐条追溯到输入或上游输出。追溯不到比例的应当为零，非零意味着存在“靠模型记住”的隐性依赖，这类依赖在换模型后会立刻失效。

第五项是补偿演练：在写节点之后注入失败，检查补偿是否按逆序执行、是否幂等、是否对外部系统真的生效。只在本地状态上“回滚”的系统，会在演练中被一眼看穿。

## 七、落地检查清单

1. 每个节点标注副作用级别。判据是四类级别齐全（纯读、计费读、幂等写、非幂等写），且非幂等写节点数量可统计。
2. 每个写节点有幂等键。判据是同一输入重放两次，外部副作用只发生一次。
3. 每个入参可追溯。判据是边完备性审计中无追溯入参的比例为零。
4. 三类边齐备且显式。判据是资源边能被列出，并对应到具体的并发上限配置。
5. 关键路径可计算。判据是给定一张图能输出关键路径长度与并行宽度，用于容量规划。
6. 失败传播策略按节点定义。判据是任一节点失败时，回滚、跳过、替换三种处理都有明确归属，不存在未定义的默认行为。
7. 补偿动作登记且幂等。判据是补偿演练中逆序执行、重复补偿被幂等键拦住。
8. 剪枝有原因标注。判据是被跳过的节点在轨迹里写明 skip 原因，最终结论引用这些原因。
9. 配额不足时排队而非报错。判据是压测到四分之一配额时，返回预计等待时间而不是错误码。
10. 图可审计。判据是任取一张历史执行的图，能还原当时的节点、边与副作用标注。

## 八、常见误区与面试追问

**问 1｜让模型自己决定顺序不是更灵活吗？**
灵活的是局部选择，不是全局约束。模型无法稳定记住“打款前必须查账本”这类隐性约束，也无法在配额紧张时安排并行。正确分工是模型提议节点与分支，运行时校验边、执行调度与补偿。

**问 2｜side_effect 标注是不是形式主义？**
它决定重试策略与并发策略，是最实用的一行元数据。缺了它，只读节点会被无谓地限制重试，写节点会被当成只读反复执行。标注本身不产生价值，被调度器和补偿器读取才产生价值。

**问 3｜并行度是不是越高越好？**
不是。并行放大的不只是吞吐，还有瞬时配额消耗与外部接口压力。超过外部系统承载能力后，重试与退避会把收益吃回去，还增加了失败面。并行宽度应当由资源边与并发上限共同决定。

**问 4｜补偿和回滚有什么区别？**
回滚改的是自己的状态，补偿改的是外部世界。写操作一旦落到下游系统，本地回滚无法复原它；必须有一个显式的补偿动作（撤销、释放、发更正），且补偿也要幂等。把回滚当补偿，是分布式系统里的常见错误。

**问 5｜静态图会不会太死板，跟不上业务变化？**
会，所以主流做法是“骨架静态、分支动态”：主干与写操作固定、可审计，读操作与补充查询允许运行时扩展，但扩展节点同样要过校验。完全动态的图省了建模成本，代价是无法复现与无法审计。

## 九、小结与延伸阅读

工具编排的核心产物不是一段调用日志，而是一张带三类边、带副作用标注、带补偿登记的依赖图。并行与剪枝的收益来自这张图，可靠性也来自这张图。把顺序决策完全交给模型，等于放弃了分析、剪枝与补偿的能力。

延伸阅读建议：官方文档类可看工作流引擎对 DAG、并行分支与补偿事务的定义；工程博客类可看并行函数调用与限流的实践；论文类可关注工具规划与工具组合的研究，重点看它如何表达前置条件。
