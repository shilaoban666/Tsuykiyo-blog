## 一、开场问题：共享一块白板之后

一个负责投标文件的多代理系统，最初的设计很朴素：所有子代理读写同一份“项目记忆”，谁查到的事实都往里写。头几天很顺，大家都能看到彼此进展。第二周开始出问题：商务代理按旧报价算出了总价，技术代理引用了一条已被否决的参数，法务代理则把一份内部风险备忘写进了要交付给客户的章节。三者都不是模型能力问题，而是记忆没有边界——写入没有审核，读取没有分级，过期没有标记。

共享记忆的诱惑在于“信息对称”，但信息对称的代价是责任模糊。本文要界定的是：在多代理系统里，哪些知识应该放在共享黑板上，哪些必须留在私有上下文，以及写入、读取与失效各自的规则。

这三起事故有一个共同点：每一条错误信息在被写入时都是“真实的”——旧报价确实曾经有效，被否决的参数确实曾被讨论过，内部备忘确实是重要提醒。问题不在真假，而在时机、范围与对象。记忆系统的职责不是判断真伪，而是让“这条信息在什么条件下对被谁有效”变得可判定。

## 二、概念界定：三种作用域与三个问题

可以把多代理的记忆分成三种作用域。第一种是全局黑板，存放跨子任务必须一致的事实，例如项目目标、硬约束、已确认的关键数字、对外承诺的口径。第二种是任务私有上下文，存放只与当前子任务相关的中间推理、草稿与试探性结论。第三种是归档层，存放已完成子任务的产物与证据，供追溯与复用，但默认不进入任何人的工作上下文。

这三种作用域对应三个必须回答的问题。谁能写：黑板不是谁都能写，写入应当被视为一次“发布”，需要来源、置信度与影响范围。谁能读：读权限要按角色与任务阶段控制，而不是默认全员可见。何时失效：任何一条记忆都要有生命周期，过期、被证伪或被替代时必须显式标记，而不是悄悄留在那里。

三个问题里，最容易被忽略的是“何时失效”。多数系统的记忆只增不减，看起来知识越来越丰富，实际上噪声越来越多，后来者无法判断哪条还有效。失效机制不是清理洁癖，而是保证记忆可信的必要条件。

判断一条信息该放哪里，有一个简单判据：它是否必须被多个子任务以同一口径使用。必须一致，就进黑板；只影响局部判断，就留在私有区。反过来说，凡是“共享出去只是方便”的信息，都不该进黑板——黑板的价值来自强制一致，而不是来自存储。

## 三、机制拆解：黑板条目与写冲突

把黑板设计成带元数据的条目集合，比设计成一段共享文本要可靠得多。每条记录至少包含：键、值、来源、写入者、写入时间、置信度、作用域、失效条件。下面是一段示意结构。

```python
@dataclass
class MemoryEntry:
    key: str                 # 规范化键，如 "bid.total_price"
    value: Any
    source: str              # 文档 ID / 工具调用 ID / 人工确认
    writer: str              # 子代理 ID 或 human:<id>
    scope: str               # global | task:<id> | archive
    confidence: float        # 0-1，人工确认记为 1.0
    valid_until: str | None  # 过期时间或条件表达式
    supersedes: str | None   # 被本条目替代的旧条目键

def publish(entry: MemoryEntry, board: Blackboard) -> WriteResult:
    if entry.scope == "global" and not entry.source:
        return WriteResult.reject("global 条目必须带来源")
    current = board.get(entry.key)
    if current and current.confidence > entry.confidence:
        return WriteResult.conflict(current, entry)   # 交由上层仲裁
    board.append(entry, supersedes=current.key if current else None)
    return WriteResult.ok(entry.key)
```

这段代码体现两个原则。第一，全局写入必须带来源，没有来源的事实只能留在任务私有区，不能升级为全局共识。第二，并发写入不采用“后写覆盖”，而是比较置信度并保留冲突，交给上层仲裁。覆盖式写入看起来简单，却会把“两个子代理得出不同结论”这个重要信号直接抹掉，等到最终文档自相矛盾时已经无从追查。

键的设计同样影响一致性。bid.total_price 与 bid.total.price 若被当成两个键，同一件事会有两份值，读取方各取一份，冲突就永远不会被检测到。可行的规则是键空间按域分层、写入前规范化、同义键只允许存在一个别名映射，且别名映射本身要有维护者。

读取侧同样需要规则。子代理构造上下文时，只应装入三类条目：与当前子任务键空间匹配的、全局作用域且未失效的、由本次任务显式引用归档产物得到的。其余条目即使存在，也不应主动注入。这样做的目的不是保密，而是防止无关信息干扰判断——上下文里每多一条不相干的事实，模型就多一次误用的机会。

失效有四种触发方式：到期、被更高置信度的条目替代、来源被撤回、任务阶段结束。前三种是内容层面的失效，第四种是作用域层面的失效。任务结束时，该任务的私有上下文应当整体降级为归档，而不是继续以“当前事实”的身份留在黑板上。很多系统的记忆污染就发生在这里：任务早已结束，它的中间结论还在被后来的任务当作前提使用。

还有一个细节是“事实”与“判断”要分开存。事实例如“客户在三月确认了报价口径”，判断例如“因此我们应该主推方案乙”。事实可以被引用、被校验，判断只能作为建议，且必须带上提出者与依据。把两者混在一条记忆里，后来者就无法区分哪部分可以依赖、哪部分需要重新论证，这也是多代理系统里“结论层层放大、错误越传越真”的常见来源。

## 四、工程取舍与反例

第一个取舍是集中与分布。单一黑板易于保证一致性，但会成为读写热点与故障单点；按主题分片可以降低耦合，但跨片的一致性需要额外机制。折中的做法是按“事实域”分片，例如报价、资质、进度各一片，跨域引用通过键而不是复制值。

第二个取舍是共享粒度。共享整份文档，信息完整但容易泄漏与干扰；共享结构化条目，干净但需要前期建模。多数团队应先从少量高价值键开始，例如目标、预算、关键结论，而不是一上来就追求“全量知识共享”。

第三个取舍是自动写入与人工确认。自动写入效率高，但噪声与错误会快速累积；全部人工确认则失去多代理的速度优势。可行的分级是：低风险事实自动写并标记置信度，高风险事实必须人工或独立复核后才能升级为全局条目。

反例有三类。其一是“黑板变草稿纸”，所有中间推理都往里写，后来者无法分辨事实与猜测。其二是“只写不删”，过期报价与旧口径长期驻留，最终被下游误用。其三是“越权共享”，把甲租户或甲项目的私有上下文写进全局区，造成信息越界。第三类往往不是技术漏洞，而是缺少写入时的作用域校验。

## 五、工程案例：一个多代理的投标文件场景

把开头那套系统按条目化重做一遍（示意），能看清每条规则挡住了什么。

输入：一份招标文件、一份历史成交报价库、一张已确认的技术参数表，目标是在四天内产出商务标与技术标。参与的子代理有五个：商务、技术、法务、交付、成稿。

冲突一：旧报价复活。商务代理读到历史报价条目，按旧单价算总价，比本次确认价低一截。处理是把报价条目的失效条件从“时间”改成“事件”：参数表确认事件一旦发布，所有旧报价条目自动失效并指向新条目；读取侧只取未失效条目。旧条目不被删除，作为 supersedes 链保留，用于回答“为什么这次报价变了”。

冲突二：否决参数被引用。技术代理引用了一条在评审会上被否决的参数。处理是把否决建成状态而不是删除：条目增加 status 字段（active/rejected/superseded），读取侧默认过滤 rejected，但保留可查。否决理由本身是重要知识，删掉它，下一个项目会再犯一次。

冲突三：内部备忘进入交付物。法务把风险备忘写进客户章节。处理是给交付渲染单独设一条规则：只取 scope 属于 deliverable 的条目，internal 条目在任何导出路径上都不可见。这条规则必须以测试用例固定住，而不是靠提示词叮嘱。

冲突四：总价冲突被覆盖。两个子代理给出不同总价，后写的覆盖了先写的。处理是改成保留冲突：两条并存并标记 conflict，由上层仲裁，仲裁结果作为新条目一次性替代两条，轨迹里保留仲裁人。

结果：交付前拦下三处口径冲突，交付物中未出现内部信息；代价是写入门槛提高，低置信度事实大量堆在私有作用域，最后仍需人工合并一次。这个代价是可控的，因为它发生在固定位置，而不是散落在交付物里。

## 六、边界与失败模式

黑板保证可追溯，不保证为真。来源、时间、置信度只是让错误可定位，不能阻止代理写入错误。想提高真实性，只能靠独立复核与来源校验，而不是靠更复杂的记忆结构。

置信度会通胀。若置信度由写入方自报，几乎所有条目都会写成 0.9。可行的约束是让置信度由来源类型推导（人工确认、内部系统、公开网页各一档），而不是让模型自由填数。

作用域判定有争议。一条“客户倾向方案乙”的信息，商务认为该共享，法务认为该保密。默认策略应当是“私有优先，升级需理由”，把争议挡在共享之外，而不是先共享再回收。

删除与失效不是一回事。审计要求回答“当时看到的是什么”，因此撤回的条目必须保留并标记，物理删除只用于合规要求的场景，且要留删除记录。

跨租户隔离靠命名空间，不能靠约定。键里带租户前缀、读取时按前缀强制过滤、写入时校验前缀归属，三者缺一，越界只是时间问题。

## 七、落地检查清单

1. 条目字段完整。判据是任取一条记忆，能回答来源、写入者、作用域、时效四个问题。
2. 全局写入强制带来源。判据是无来源的全局写入被拒绝，且拒绝事件可查。
3. 写冲突不覆盖。判据是两个高置信度冲突条目能同时存在，并能定位到仲裁结果。
4. 读侧按作用域裁剪。判据是子代理上下文里不出现与其子任务无关的作用域条目。
5. 失效有触发条件。判据是过期条目在读取时被过滤，同时历史版本仍可查询。
6. 事实与判断分字段。判据是判断类条目必带依据与提出者，且能被单独筛出。
7. 任务结束即作用域降级。判据是新任务默认读不到旧任务的私有条目。
8. 交付渲染只取允许作用域。判据是存在一条自动化用例，证明内部条目无法进入导出产物。
9. 撤回保留审计痕。判据是撤回后仍能重建“当时的视图”，包括被撤回的条目。
10. 键空间有规范与维护者。判据是同义键不会并存两份，别名映射有明确责任人。

## 八、常见误区与面试追问

**问 1｜共享记忆是不是越多越好？**
不是。共享的收益是一致性，成本是干扰与泄漏。只把“必须被多个子任务以同一口径使用”的信息放进黑板，其余留在私有区。共享整份文档通常是最省事也最危险的做法。

**问 2｜用置信度能解决写冲突吗？**
只能排序，不能裁决。置信度高的条目未必正确，且由写入方自报时会普遍通胀。工程上更稳的是保留冲突并交仲裁，仲裁结果再以新条目替代旧条目，形成可追溯的链。

**问 3｜为什么不允许后写覆盖？简单又快。**
后写覆盖会把“两个代理结论不一致”这个信号抹掉，等最终文档自相矛盾时已无法归因。覆盖适合单写入者的配置类数据，不适合多写入者的判断类数据。

**问 4｜过期记忆为什么不直接删掉？**
因为审计需要重建当时的视图。删掉之后，“当时为什么做出那个决定”就永远查不清。正确做法是失效标记加归档，物理删除只用于合规要求。

**问 5｜多租户下黑板怎么隔离？**
三层：键带租户前缀、读取强制按前缀过滤、写入校验前缀归属。只做其中一层，另外两层迟早会被绕过。物理隔离（一租户一库）隔离性最好，代价是跨租户的共享知识需要另建通道。

## 九、小结与延伸阅读

多代理记忆的设计，本质是在“共享带来的协同”与“边界带来的可信”之间取平衡。可操作的落点是三句话：写入要带来源与置信度，读取要按作用域裁剪，失效要有明确触发条件。把这三件事写进数据结构和接口，比在提示词里叮嘱“注意信息隔离”有效得多。
