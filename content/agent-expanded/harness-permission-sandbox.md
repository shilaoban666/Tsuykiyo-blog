## 一、开场问题：提示词写了“不要删库”，它还是删了

一个运维助手在测试环境表现良好，团队在系统提示里加了一行“禁止执行删除类命令”，就把它放进了预发环境。某次排查磁盘占用时，模型先执行了查看目录，随后“顺手”清理了一个它认为是缓存的目录，而那个目录挂载的是共享数据卷。事后复盘，提示词确实写了禁止，但运行时没有任何机制阻止这条命令。

这是权限设计中最常见的误解：把提示词当成安全策略。提示词影响的是模型的倾向，不是系统的能力边界。模型可能被诱导、可能误解、可能在长上下文里忽略某条规则。真正可靠的边界必须由运行时在动作执行前强制，模型无论说什么，越界的动作都执行不了。

## 二、概念界定：能力令牌与三类沙箱

最小权限原则在这里可以落成“能力令牌”：每次任务开始前，运行时根据任务类型、用户身份与审批结果签发一组临时能力，明确允许哪些路径、哪些域名、哪些命令、有效期多久。默认拒绝，未列出的能力一律不可用。令牌随任务结束而失效，不跨任务复用。

文件、网络、进程三类沙箱的隔离强度不同。文件沙箱的核心是路径解析：不仅要限制根目录，还要处理符号链接、相对路径、挂载点与大小写差异，防止通过链接跳出边界。网络沙箱的核心是出口控制：默认禁止外联，按域名或地址段放行，并限制协议与方法，防止数据外带。进程沙箱的核心是系统调用与资源限制：限制可执行文件、禁止提权、限制 CPU 与内存、隔离命名空间。

隔离技术的强度大致可分三档。容器隔离部署轻、启动快，但共享内核，配置不当容易逃逸；系统调用过滤能收窄攻击面，但规则维护成本高；虚拟机或微虚拟机隔离最强，代价是启动慢、资源占用高。选择哪一档，取决于任务能接触到的数据敏感度与命令执行的必要性，而不是统一追求最强。

## 三、机制拆解：从申请到审计

权限执行可以拆成五步：申请、判定、执行、记录、复核。下面是一段示意实现，重点在路径解析与默认拒绝。

```python
def authorize(run, action):
    cap = run.capabilities.get(action.kind)      # 任务开始时签发
    if cap is None or cap.expired():
        return Deny("no_capability")
    if action.kind == "file_write":
        real = os.path.realpath(action.path)     # 解析符号链接与 ..
        if not under(real, cap.roots):           # 逐段比较，非字符串前缀
            return Deny("path_outside_root")
    if action.kind == "network":
        if action.host not in cap.allow_hosts:
            return Deny("host_not_allowed")
    if action.kind == "exec":
        if not allowed_binary(action.argv[0], cap.binaries):
            return Deny("binary_not_allowed")
        if touches_sensitive(action.argv, cap.sensitive_paths):
            return Escalate("need_human_approval")
    return Allow(timeout=cap.timeout, quota=cap.quota)
```

这段代码有三个要点。第一，路径判断用解析后的真实路径，并逐段比较目录，而不是简单的字符串前缀匹配，否则 /data 与 /data-backup 会被误判为同一棵树。第二，命令执行先校验可执行文件，再检查参数是否触及敏感路径；只看命令名，无法阻止用合法命令操作非法目标。第三，高风险动作返回“升级”而不是直接拒绝，把决定交给人工审批，而不是让模型自行绕过。

审批升级需要与风险分级绑定。可逆且影响范围小的动作可以事后抽检；不可逆或影响面大的动作必须前置审批，例如对外转账、删除生产数据、修改权限、发送群发消息。审批请求应包含动作、目标、参数、预期影响与回滚方案，审批人看到的必须是结构化信息，而不是模型的一段自述。

审计留痕要能与轨迹关联。每次授权决定记录：谁申请、申请什么、依据哪条能力、判定结果、审批人、执行结果。审计日志与运行轨迹共用 trace id，事后可以从一次异常调用反查到当时的授权上下文。只记录“执行成功”而不记录“为何允许”，等于没有审计。

## 四、工程案例：一次真实的越权执行故障

示意场景。一个运维 Agent 的能力令牌声明了 `roots = ["/srv/app"]`，实现里用字符串前缀判断：`action.path.startswith(root)`。命令白名单是 `[ls, du, df, rm]`，敏感路径列表里手写了几个生产库目录。

预发环境有一层运维留下的历史配置：`/srv/app/cache` 是一个符号链接，指向共享数据卷 `/srv/app-data/cache`——当初为了省系统盘空间做的，没人在文档里记过。

故障当天，磁盘告警触发了这个 Agent。它先执行 `du -sh /srv/app/*`，看到 cache 目录占了大部分空间，于是执行 `rm -rf /srv/app/cache/*`。路径前缀检查通过：字符串确实以 `/srv/app` 开头。命令白名单通过：rm 在白名单里。敏感路径检查通过：`/srv/app-data` 不在手写列表里，而且检查的是 `action.path`，不是解析后的真实路径。shell 展开通配符后，共享卷上的缓存与同级的业务附件一起被删。

三个检查点都放行了同一条命令，每一个单独看都合理：前缀匹配是为了限制目录，白名单是为了限制工具，敏感列表是为了保护已知的重要路径。它们失效的共同原因是都作用在“声明值”上，而不是“实际值”上：前缀比的是字面字符串，敏感列表比的是未解析的路径，白名单只看命令名不看参数。

事后从审计里能捞到四个信号。第一，`du` 的输出显示该目录占了 40GB，而任务的原始描述是“清理构建缓存，预计释放 200MB”——量级差了两个数量级，没有阈值拦。第二，命令参数里含通配符 `*` 且目标是删除操作，这类组合本可以要求二次确认。第三，符号链接的真实路径与请求路径不同，审计只记了请求路径，realpath 从未出现。第四，同一条 trace 里，模型在删除前没有执行任何列举操作（`ls`），直接从 `du` 跳到了 `rm -rf`。

修复有六处：路径判断改为 realpath 后逐段比较，`os.path.commonpath` 而不是 `startswith`；符号链接在写入类动作上默认拒绝，需要显式能力；命令白名单升级为“命令 + 参数模式”，删除类动作禁止通配符，或要求先列举再删除；删除前强制 dry-run，输出待删条目数与总字节数，超过阈值升级审批；挂载点单独标记为只读，跨挂载点写入直接拒绝；审计同时记录请求路径与真实路径。

这个案例值得记住的点是：三道检查全部通过，才最危险。单点失守会让人警觉，三重通过会让人相信“系统已经校验过了”。设计权限时应该问的是“这条规则作用在哪个值上”，而不是“我加了几道检查”。

## 五、工程取舍与反例

第一个取舍是隔离强度与可用性。微虚拟机最安全，但启动慢、调试难；容器轻便，但需要额外的内核与运行时加固。可行的路径是按任务分级：只读检索用轻隔离，代码执行用强隔离，涉及生产凭证的任务默认不允许自主执行，必须走审批与专用通道。

第二个取舍是审批密度与效率。每个动作都审批会让系统不可用，审批太少又形同虚设。按风险分级是唯一可行的解：低风险自动放行并留痕，中风险抽样复核，高风险前置审批。即便如此，高风险审批也会带来明显时延，示意场景下可能让平均任务时长增加约两成（来源：示意），因此审批点应尽量合并，一次审批覆盖一组相关动作。

第三个取舍是网络策略。完全断网最安全，但很多任务需要查文档、调 API。按域名白名单放行是折中，但要防止通过允许的域名做数据外带，例如把敏感内容拼进查询参数。更稳的做法是对出口做内容审查与速率限制，并禁止将敏感字段发送到非受信域名。

常见反例有四类。其一是“提示词即策略”，规则写得再严厉，运行时仍以全权限执行。其二是“路径前缀匹配”，用字符串前缀判断目录归属，被 /data-backup 或符号链接绕过。其三是“命令黑名单”，只禁 rm，攻击者换一个等价命令或脚本即可绕过。其四是“审批无上下文”，审批人只看到“是否允许执行”，看不到参数与影响，只能凭感觉点通过。

还有一个隐蔽的反例：权限令牌的生命周期与任务生命周期不一致。任务结束后令牌未回收，或令牌按用户而非按任务签发，导致一次授权被后续所有任务复用。正确做法是能力令牌短时有效、按任务签发、随任务结束立即失效，并在审计中记录令牌 id。

## 六、指标与阈值怎么定

权限系统的指标要能回答：边界有没有被试探、审批有没有失效、审计有没有缺口。

越界尝试率：拒绝次数除以动作总数。它不是越低越好——长期为零通常意味着策略太松或没有人在探边界，反而应该检查；持续在 1% 到 5% 之间属于正常，突增说明任务分布变了或提示被改坏了。拒绝原因分布：能力缺失、路径越界、域名不允许、命令不允许各占多少，某一类占到八成说明配置写错了，而不是模型在攻击。审批通过率：长期高于 95% 说明分级失效，审批已经退化成点击，这时要减少审批面或改触发条件，而不是加人。审批时延 p95：超过 SLA 的比例直接决定任务超时率。令牌复用次数：一个令牌被用于多个任务即告警，这个值应恒为 1。审计覆盖率：有授权记录的写操作占比，必须是 100%，低于它就是存在无记录路径。

阈值设定要区分“安全阈值”与“效率阈值”。安全阈值（如审计覆盖率、令牌复用）不能妥协，设成硬性 100% 或 0；效率阈值（如审批时延、拒绝率）用真实分布定，取正常任务的 95 分位作告警线。

## 七、落地检查清单

1. 默认拒绝。判据：能力未显式列出时动作被拒，配置里找不到“默认允许”分支。
2. 令牌按任务签发。判据：令牌有任务 id、有效期，任务结束后立即失效，复用能被检出。
3. 路径解析后再比较。判据：判断基于 realpath，分段比较；构造 `../`、符号链接、大小写变体三个用例都能被拦。
4. 挂载边界独立标记。判据：跨挂载点写入被拒或升级，有配置项可查。
5. 命令校验含参数。判据：删除类命令禁止通配符或要求先列举，参数模式有白名单。
6. 高风险动作走升级。判据：不可逆动作返回 Escalate 并进入审批队列，拒绝与升级两类结果分别可查。
7. 审批带结构化上下文。判据：审批页包含动作、目标、参数、影响范围与回滚方案，只有“允许/拒绝”不算。
8. 审计记录真实值。判据：同时记录请求路径与解析后路径，含令牌 id 与 trace id。
9. 出口有内容控制。判据：白名单域名之外一律拒绝；白名单域名上敏感字段被拦截有日志。
10. 定期越权演练。判据：用构造的绕过用例（链接、通配符、等价命令）回归，全部被拦。

## 八、常见误区与面试追问

问：提示词里写清“禁止删除”，再配一个强模型，不够吗？
答：不够。提示词是给模型的建议，模型可能被长上下文稀释、被文档里的文字带偏、被用户话术诱导。安全边界必须放在模型之外，动作执行前由运行时判定。判断标准很简单：把提示词全部删掉，越界动作还能不能执行？能执行，就没有边界。

问：用容器隔离是不是就够了？
答：容器解决的是进程与文件系统的可见范围，不解决“允许删哪个目录”这种业务级问题。容器内仍有 rm，仍有网络，仍可能通过挂载卷影响宿主机。容器是底座，能力令牌是策略，两者不能互相替代。

问：路径前缀匹配为什么会失效？
答：因为它是字符串比较，不是路径语义比较。`/data` 是 `/data-backup` 的前缀；`/srv/app/cache` 可能是指向别处的符号链接；大小写不敏感的文件系统上 `/Data` 与 `/data` 是同一个目录。这三种都会让前缀检查通过，而实际目标在边界之外。

问：每个动作都审批，是不是最安全？
答：最安全的是不让人参与的系统，但审批不是免费的安全。审批量一大，人就会退化成橡皮图章，通过率接近 100%，那时审批提供的是心理安慰，不是控制。正确做法是按风险分级、聚合审批点、让人看到结构化信息。

问：沙箱会不会拖慢正常任务？
答：会，尤其是强隔离与审批。所以要按任务分级：只读检索用轻隔离，代码执行用强隔离，高风险写操作走审批。全量上最强隔离的代价是启动时间与调试成本，最终会逼团队绕开系统，那才是真正的安全损失。

## 九、小结与延伸阅读

Agent 的安全边界必须由运行时强制：默认拒绝、按任务授权、解析真实路径、控制出口、限制可执行文件、对高风险动作升级审批、把每次判定写入轨迹。提示词可以表达意图，但不能承担边界。判断一套系统是否安全，不看它写了多少禁令，而看它能否在模型试图越界时让动作根本执行不了。

最后一个判断方法：把所有检查项列出来，逐条问“它作用在字面值还是真实值上”。作用在字面值上的检查，都可以被链接、通配符、等价命令绕过；作用在真实值上的检查，才需要攻击者真的突破内核或挂载。

延伸阅读建议：官方文档类可看容器与微虚拟机的隔离机制、操作系统访问控制模型；工程博客类可看最小权限与能力令牌的落地实践；论文类可关注提示注入与 Agent 安全边界的综述。阅读时把“绕过路径”作为重点，这通常是沙箱最先失守的地方。
