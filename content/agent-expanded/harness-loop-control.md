## 一、开场问题：它跑了四十步，还在说“我再确认一下”

夜里跑批时，一个负责对账的 Agent 连续执行了四十多步：查订单、查流水、再查订单、再查流水，日志里每一条都写着“已确认部分信息，继续核实”。它没有报错，也没有卡死，只是在原地打转，直到把当天的调用预算烧完。第二天团队复盘，发现模型每一轮都能给出一个看似合理的下一步，但没有任何机制判断“这些步骤是否在推进”。

这类问题不能靠更严厉的提示词解决。模型没有内在的步数感，也无法可靠判断自己是否重复。可靠的循环必须由运行时提供两样东西：可观测的终止信号，以及不可协商的硬预算。前者告诉系统“什么时候算完”，后者保证“算不完也要停”。

## 二、概念界定：四类终止信号与循环状态

终止信号分四类，含义完全不同，必须能区分并分别记录。第一类是任务完成，由验收条件判定，例如目标字段齐全、测试通过、用户确认；它是最理想的出口，但需要可判定的标准，不能只看模型说“完成了”。第二类是明确失败，例如前置条件不成立、权限被拒、依赖不可用；这类失败不应重试，而应带着原因退出。第三类是预算耗尽，包括步数、token、时间、成本四个维度任一触顶；它表示“没做完但不能再做”，输出应包含已完成部分与未决问题。第四类是人工中止，包括用户取消、审批拒绝、运维熔断；它优先级最高，必须立即生效并可恢复。

与四类信号对应，循环有几个明确状态：规划中、执行中、等待观察、等待人工、已完成、已失败、已中止。状态迁移必须是显式的，且每次迁移都写入事件日志。很多系统的循环控制实际上只有一个 while 循环加一个最大步数，状态藏在模型上下文里，出问题时无法回答“它卡在哪一步、为什么没停”。

还要区分“步”与“调用”。一步通常指一次“决策加动作”的完整回合，可能包含一次模型调用和一次工具调用；重试是否计入步数，必须在设计时定死。若重试不计步数，一个持续失败的工具可以无限重试；若计入，正常重试又会过快消耗预算。常见做法是重试计入调用次数但不单独计步，同时给同一动作设置独立的失败上限。

## 三、机制拆解：指纹、无进展计数与四维预算

死循环的识别不能依赖模型自述，而要靠运行时可计算的特征。三个特征最实用：动作指纹、状态哈希、无进展计数。动作指纹由工具名与规范化参数计算，用于发现“同一动作反复执行”；状态哈希由关键状态字段计算，用于发现“状态没有变化”；无进展计数则在连续若干步既没有新增事实、也没有推进验收条件时递增。

```python
FP = lambda name, args: sha1(name + canonical_json(args))
seen, stagnant = {}, 0
for step in range(budget.steps):
    decision = model.next(goal, state, tools)
    if done(goal, state):        return finish(state)
    if decision.kind == "abort": return abort(decision.reason)
    fp = FP(decision.name, decision.args)
    before = state_hash(state)
    result = gateway.call(decision, budget.slice())
    state = reduce(state, decision, result)
    seen[fp] = seen.get(fp, 0) + 1
    stagnant = stagnant + 1 if state_hash(state) == before else 0
    if seen[fp] >= 2 or stagnant >= 3:
        return circuit_break("no_progress", state)
    if budget.exhausted():
        return budget_stop(budget.first_hit(), state)
```

这段示意代码里有三个设计点。第一，指纹在调用前计算，因此重复动作可以在执行前被拦截，避免第二次副作用。第二，状态哈希只覆盖关键字段，不能把时间戳、随机 id 这类每次都变的字段算进去，否则永远检测不到停滞。第三，熔断不是直接抛异常，而是返回一个带原因的状态，让上层决定是降级、转人工还是换策略。

指纹的有效性完全取决于参数规范化。工具参数里常带 `request_id`、`now()` 形式的时间窗、临时目录名，这些字段每步都不同；不先归一化，指纹永远不重复，检测形同虚设。做法是按 schema 声明参与指纹的字段，时间窗对齐批次边界，路径做 realpath 归一。

四维预算的触发顺序需要设计。通常时间与步数先兜底，token 与成本随后，因为前两者决定用户体验，后两者决定账单。任一体积触顶后，降级路径应当预先定义：压缩上下文后重试一次、切换到更便宜的模型、缩小任务范围、转人工、直接返回部分结果。没有降级路径的预算只是一个更昂贵的报错。

预算还要能分配，而不是全局共享。一个任务里若有多个阶段，应给每个阶段设子预算，避免检索阶段把整轮预算吃光，导致执行阶段无钱可用。子预算的回收也重要：前一阶段未用完的额度可以按比例释放给后一阶段，但要有上限，防止单阶段无限扩张。

## 四、工程案例：一次真实的循环失控

示意场景，数字用于说明量级。夜里跑批的对账 Agent 有两个工具：`query_orders(account, window)` 与 `query_ledger(account, window)`。团队按常规做法加了最大步数 50，并在日志里打印了每一步的动作，看起来该有的都有。

失效从指纹开始。`window` 的右边界用 `now()`、左边界是“七天前”，每步都会生成新的时间窗；参数里还有网关自动注入的 `request_id`。同一个业务查询每步算出的指纹都不同，`seen[fp]` 恒为 1，重复检测从未触发。状态哈希也失灵：它由整个 state 的 JSON 计算，其中 `updated_at` 与 `trace_id` 每步都变，`stagnant` 永远归零。

剩下的唯一约束是步数。每步模型都说“还缺一部分流水，再查一次”，工具偶发超时后又自动重试三次，而重试不计入步数。一夜下来 49 步、187 次工具调用，其中 61 次是重试。凌晨那轮跑批成本接近正常单任务的九倍（示意），月度 token 配额被削掉一大块。

恢复能力同样缺席。步数耗尽时循环直接返回“未能完成对账”，没有部分结果，也没有未决清单；第二天人工只能从头再查一遍。

事后从轨迹里能读出四个信号，当时都无人查看：动作分布集中在两个工具上，占 96%，远高于正常任务的 40% 左右；步均新增事实只有 0.02 条，说明每一步几乎没有带来新信息；状态哈希每步都变，但业务关键字段（订单数、差额）从头到尾没动；工具调用数除以步数等于 3.8，正常的重试放大系数应低于 1.5。

修复分五处：指纹参数按 schema 白名单化，排除 `request_id`，时间窗对齐到批次边界；状态哈希改为只含订单数、差额、已匹配条数等业务字段；加入无进展计数，连续三步无新增事实即熔断；重试计入失败上限（同一动作最多三次），并计入调用预算；熔断返回 `no_progress` 状态加已完成部分，而不是一句失败。改完之后同一批任务平均 11 步收敛，成本降到原来的七分之一（示意）。

这个案例的教训是：检测机制本身也会失效，而且失效时悄无声息。指纹与状态哈希都是算出来的特征，输入里混进时间戳和随机 id，它们就从检测器退化成计数器。上线前用历史轨迹回放验证一次“重复动作能不能被检出”，比在代码里多加判断都有效。

## 五、工程取舍与反例

第一个取舍是严格熔断与宽容重试。阈值太严，正常的探索会被误判为打转；阈值太松，死循环会烧掉大量预算。可按任务类型分档：只读探查允许更多重复，写操作与外部调用则应在第二次相同动作时立即拦截。

第二个取舍是提前终止与尽量完成。有些任务在预算耗尽时已经完成了大部分，直接失败会浪费已有结果。更好的做法是输出“部分完成 + 未决清单 + 建议下一步”，让上层决定是否续跑。但必须明确标注未完成，不能把半成品包装成完成。

第三个取舍是可观测性与开销。记录每一步的完整上下文成本很高，只记指纹与状态哈希又难以复盘。折中方案是分层采样：所有步骤记录结构化事件，关键步骤额外保存上下文快照，异常步骤全量保存。这样既能控制存储，又能在出问题时还原现场。

常见反例有四类。其一是“只限步数”，不限重复动作，模型用两个工具来回调用也能耗满预算。其二是“假完成”，验收条件写成“模型认为已完成”，循环立刻退出，但结果没人校验。其三是“重试黑洞”，工具超时后自动重试，重试不计预算，一次故障放大成几十次调用。其四是“熔断即崩溃”，检测到打转后直接抛异常，没有保留状态，恢复时只能从头再来。

还有一个组织层面的反例：把循环参数当成一次性配置，上线后从不调整。任务分布会变，工具会变，模型的默认行为也会随版本变化，预算与阈值需要定期用真实轨迹校准。没有校准，参数只是拍脑袋的数字，既解释不了成功，也解释不了失败。

## 六、指标与阈值怎么定

循环控制要的指标不多，但每个都要能直接对应一个决策。

有效步比例：产生新事实或推进验收的步数除以总步数，健康值高于 0.6，低于 0.4 说明大部分步数在空转。重复动作率：相同指纹的步数占比，超过 15% 告警；只读探查可放宽到 25%，写操作应接近 0。无进展步数：连续无新增事实的步数，三次即熔断，这个阈值不必调，它已经足够宽容。重试放大系数：工具调用数除以步数，高于 1.5 说明重试过密。首停原因分布：完成、失败、预算、人工各占多少，预算类超过一成说明配比或任务定义有问题。

阈值不要凭经验定死。做法是按任务类型分组，取失败轨迹里各指标的分位数作起点，例如重复动作率取失败样本的 10% 分位先做告警，跑两周看误报再调。同一套阈值不要横跨只读与写入任务，两者的正常分布差一个量级。

## 七、落地检查清单

1. 四类终止信号可区分。判据：日志能按完成、失败、预算、人工分别计数，而不是统一记为“结束”。
2. “步”的定义写死。判据：文档明确一步包含哪些调用、重试是否计步与计入预算，代码与文档一致。
3. 指纹在调用前计算。判据：重复动作能在产生副作用之前被拦截。
4. 指纹参数已规范化。判据：schema 列出参与指纹的字段，时间戳、随机 id、临时路径被显式排除。
5. 状态哈希只含业务字段。判据：构造一个只改时间戳的状态，哈希不变。
6. 有无进展计数。判据：连续三步无新增事实能触发熔断，且有对应用例。
7. 预算四维齐全。判据：四个维度都有上限，能报告各自触顶次数。
8. 子预算存在。判据：多阶段任务每阶段有独立额度，单阶段无法吃光全局预算。
9. 触顶有降级路径。判据：触顶后执行预定义动作（压缩重试、降级模型、缩小范围、转人工），不是直接抛错。
10. 阈值有校准机制。判据：每季度用真实轨迹重算一次分布，参数变更有记录与理由。

## 八、常见误区与面试追问

问：为什么不能靠提示词让模型自己判断该停了？
答：模型没有可靠的步数感，也无法比较自己前后两步是否重复——它看到的只是上下文里的一段文字，不是可计算的状态。要求它“不要重复”属于请求，不是保证。停止条件必须由运行时计算并强制执行。

问：最大步数设多少合适？
答：没有通用值，要看任务的可分解深度。可行做法是先统计同类成功任务的实际步数分布，取 95 分位再上浮 50% 作为上限；超过这个数仍没完成的任务，多数不是差几步，而是方向错了。

问：重试到底该不该计入预算？
答：计入，但要用两层：重试计入调用次数与成本，避免一次故障放大成几十次调用；同时给同一动作单独设失败上限。只做其中一层都会漏——只计调用会让网络抖动过早耗尽预算，只设失败上限则挡不住跨动作的重复。

问：熔断之后直接把任务重跑一遍行不行？
答：多数情况下不行。熔断说明状态已经打转，直接重跑大概率走同一条路径再撞一次。应该先看熔断原因：参数不规范导致误判就修检测，信息缺失导致反复查询就补上下文或换工具，外部依赖不稳就等恢复并降并发。

问：怎么区分“正常探索”和“打转”？
答：看新增事实，不看动作次数。探索会带来新信息，即使动作看起来相似，状态也在推进；打转则是动作变化但信息不增。所以判据应是“连续若干步没有新增事实或验收进展”，而不是“某个工具被调用了三次”。

## 九、小结与延伸阅读

循环控制的本质是把“什么时候停”从模型的判断变成系统的判断。四类终止信号让退出有语义，三个特征让打转可检测，四维预算让成本有上限，降级路径让失败可收场。做到这些，Agent 才敢在无人值守时运行。

还有一条容易被忽略：检测器本身需要测试。指纹、状态哈希、无进展计数都是计算出来的，输入里混进一个时间戳就可能全部失灵，而且失灵时不报错。用历史轨迹回放验证“重复能被检出”，应该成为上线前的固定动作。
