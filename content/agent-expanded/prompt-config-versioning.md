## 一、开场问题：上周还好好的，这周就复现不了

一个客服 Agent 上线后表现平稳，两周后开始出现答非所问。团队查了提示词，没改；查了工具，没改；查了模型，也没换。最后发现是检索配置变了：知识库做了一次重建，索引的分块策略从按段落改成按固定长度，召回的内容片段变碎，模型拿到的是半句话。还有一次，问题是模型供应商把默认版本悄悄升级了，行为略有变化，而团队以为“没换模型”。

这类问题的共同点是：Agent 的行为由多个部件共同决定，但团队只对其中一两个部件做了版本管理。本文讨论的是把提示、工具 schema、模型参数、检索配置打成一个版本单元，让“上周的版本”可以被精确重建。这两次故障的归因过程也说明一件事：前者靠读 diff 能发现，后者只能靠比对实际运行值才能发现，这正是版本清单存在的理由。

## 二、概念界定：一个版本单元包含什么

一个可复现的 Agent 版本，至少包含五类内容。第一是提示：系统提示、任务模板、少样本示例、输出格式约束。第二是工具契约：工具清单、每个工具的参数 schema、错误语义、可用的工具组合。第三是模型参数：模型标识、温度、最大输出长度、停止词、随机种子。第四是检索配置：索引版本、分块策略、嵌入模型、召回数量、重排规则。第五是运行时策略：最大步数、预算、重试次数、权限规则。

这五类内容必须一起打标签，而不是各自维护一个版本号。原因很简单：单独看每个部件都没变，组合起来的行为却可能变。例如提示没变、模型没变，但工具 schema 加了一个可选字段，模型的调用分布就会偏移。版本单元的意义是把“组合”也纳入版本。

还有两类常被漏掉的组件：运行时本身（harness 版本、编排代码）与开关（功能开关、租户级配置）。它们同样会改变行为，却往往不在“提示库”里。判断标准很简单：这个值变了，同一输入是否可能得到不同输出。答案为是，就该进版本单元。

可复现的定义要写清楚：给定同一份输入、同一个版本标签、同一份外部数据快照，重跑应得到可比较的输出。逐字一致很难，因为采样有随机性；工程上追求的是关键字段一致、结论不翻转，因此版本单元还要记录“判定一致”的口径，并分三档写进报告：强一致、字段一致、结论一致。多数业务只需第二档，但“结论是否翻转”必须能被机器判定，否则复现只是口头承诺。

版本号建议区分三层：主版本表示不兼容变更（输出契约变了、工具删了），次版本表示行为可能变化（提示大改、模型升级），修订号表示不影响行为的修正（错别字、日志字段）。灰度与回滚都以这个版本号为单位。

## 三、机制拆解：清单、锁定与灰度

落地时最有效的手段是一份“发布清单”，把版本单元写成可校验的文件，随代码一起提交。

```yaml
release: cs-agent-2026.11.3
components:
  prompt:
    system: prompts/system.v7.md
    task: prompts/task.refund.v3.md
    few_shot: prompts/examples.refund.v2.jsonl
  tools:
    manifest: tools/manifest.v12.json
    schema_hash: "sha256:9f2c..."
  model:
    id: "provider/model-x"
    temperature: 0.2
    max_output_tokens: 1200
    seed: 42
  retrieval:
    index: "kb-2026-11-01"
    chunking: "paragraph-512-overlap-64"
    top_k: 8
    rerank: "cross-encoder-v3"
  runtime:
    max_steps: 12
    budget_tokens: 60000
    retry: {max_attempts: 2, backoff: "exp+jitter"}
checksum: "sha256:4a71..."
```

这份清单有三个作用。第一，发布时校验：任何一项的实际值与清单不符，构建直接失败，避免“以为发的是这个版本”。第二，回滚时定位：出问题时能一眼看出哪个组件与上个版本不同。第三，复盘时归因：同一份清单可以把当时的输入、配置与输出对应起来。

清单要能被机器校验，否则它会退化成一份写给人看的文档。可行的做法是在服务启动时计算一次“实际配置指纹”：把所有组件的实际取值按稳定顺序序列化后取哈希，与清单里的 checksum 比对，不一致就拒绝启动或在健康检查里报降级。这样做的价值在故障排查时最明显：拿到一次失败请求的指纹，就能排除“配置漂移”这一整类猜测。

模型参数的锁定要特别注意“浮动标签”。很多供应商允许写一个不带日期的模型别名，别名背后会指向新版本。稳妥的做法是锁定到带日期的具体版本，并定期做一次“影子跑”：用新版本在固定任务集上跑一遍，与当前版本对比，差异可接受再升级。没有这一步，升级就是赌博。

检索配置的版本要与索引绑定。索引重建后，即使分块策略没变，内容也可能变。因此清单里要记录索引的生成时间与内容摘要，而不是只写一个逻辑名称。否则“同一个配置”在不同时间点召回的内容并不相同，复现就成了一句空话。

灰度发布按变更风险分级。文字微调可以小流量直接放；工具 schema 变更要先跑契约测试，再放小流量；模型升级影响面最大，应先在离线任务集上对比，再按流量比例逐步放开，每一步都保留回切开关。灰度的单位应与版本单元一致，否则一部分请求用新提示、旧模型，出了问题无法归因。

灰度的分配键要固定，不能每次请求随机：按会话或租户哈希分桶，同一会话始终命中同一版本，否则同一用户会在两种行为之间横跳，反馈无法解释。

回滚要能在分钟级完成。前提是旧版本的所有组件都还在：旧提示文件没删、旧索引没下线、旧模型版本仍可调用。很多团队的回滚失败，不是因为不想回，而是旧索引已经被覆盖、旧模型已经退役。版本保留策略要与回滚目标匹配。

## 四、工程取舍与反例

第一个取舍是版本粒度。整个 Agent 一个版本号，简单但任何小改都要全量重发；每个组件独立版本，灵活但组合爆炸。折中是“组件有版本、发布有清单”，组件独立演进，清单固定组合。

第二个取舍是严格锁定与快速迭代。锁定一切会让实验变慢，完全放开又无法复现。可行的做法是区分环境：实验环境允许浮动，预发与生产必须锁定，且从实验到生产要经过一次“固化”——把实验里用到的实际版本写进清单。

第三个取舍是自动化与人工判断。校验可以全自动，但“这个差异是否可接受”仍需人判断。把差异报告做得可读比追求全自动更重要：列出关键指标的变化、失败样本的对照、受影响的工具调用分布，让人能在几分钟内做决定。

反例有三类。其一是“只版本化提示”：提示有 git 记录，模型与索引却是浮动的，出了问题查不到根因。其二是“清单与实际脱节”：清单写的是旧值，部署脚本读的是环境变量，两者长期不一致。其三是“回滚无门”：版本号有了，但旧索引被覆盖、旧模型下线，回滚只能改回去再祈祷。

还有一类反例是“用日期当版本号”。日期能排序，但不表达兼容性，也无法回答“这次变更是否破坏输出契约”。语义化版本加发布清单，比单纯的时间戳更能支撑灰度与回滚决策。

还有一类反例是“把清单当审批表”：清单只用来签字，每一栏都勾了，实际值没人比对。把清单里某个值改错、构建却不失败，这份清单就只是流程装饰。

## 五、工程案例：一次配置漂移事件

以下场景为示意，数字用于说明量级，不代表任何真实系统。

某客服 Agent 发布 v3.2，变更内容只有三处提示文案的错别字修正，清单里模型、工具、检索三项都与 v3.1 完全相同。发布后两天，投诉开始出现：用户问“退款多久到账”，回答里夹着半句无关的运费说明；追问时又给出另一套说法。第一周这类投诉约占会话量的 4%，第二周升到 9%。

排查从最可疑的地方开始，逐项排除。提示 diff 只有错别字，排除；模型标识未变，且同一批离线任务重跑结果与上周一致，排除；工具 manifest 哈希一致，排除。剩下检索：清单里写的是 kb-2026-11-01、paragraph-512-overlap-64，与实际运行值完全一致。

转折点是对比召回内容。用同一个问题在 v3.1 与 v3.2 上各跑十次，把召回的片段并排看：v3.1 拿到的是完整段落，v3.2 拿到的是被切成两半的句子。再查知识库操作记录，发现在 v3.2 发布当天有人做了一次“重建索引”，重建时用的分块器版本不同，逻辑名称仍是 paragraph-512，但实际切分规则变了。

到这里，故障链完整：清单记录的是“配置的逻辑名称”，索引重建改变的是“名称背后的内容”。危险在于它完全绕过评审——没有任何一次提交是错的，每一步单独看都合理，只有组合起来才不对。

处置分四步。第一步，冻结索引写入，禁止再次重建，先止血。第二步，回滚检索到上一份索引快照，v3.2 的提示保留不动；回滚后投诉在一天内回到基线。第三步，给清单加 index_digest 字段记录索引摘要与构建时间，并把启动校验扩展到检索：摘要不符即拒绝启动。第四步，重建索引纳入变更评审，必须产生新版本号，不得在旧名称上原地覆盖。

复盘有三条结论。其一，版本单元里最脆弱的往往不是提示，而是那些“看起来没变”的资产：索引、嵌入模型、重排模型。它们的逻辑名称稳定，内容却在变。其二，清单要记录内容的指纹而不只是名称；名称给人看，指纹给机器校验。其三，灰度期间要对比召回片段，而不是只看最终答案的通过率——通过率对检索退化不敏感。

## 六、落地检查清单

以下八条按“能不能挡住一次配置漂移”设计，判据要能当场执行。

1. 五类组件都在清单内。判据：抽一次发布逐项核对提示、工具、模型、检索、运行时，缺任何一类即不合格。
2. 清单带整体 checksum 且被启动校验。判据：故意改错清单里的一个值，服务启动失败或健康检查报降级。
3. 模型锁定到带日期的具体版本。判据：配置里不出现浮动别名；供应商侧能看到所选版本的固定标识。
4. 检索记录内容指纹。判据：清单里有 index_digest 与构建时间；重建索引后指纹必然变化。
5. 可复现口径写明。判据：发布说明里写明本次采用“字段一致”还是“结论一致”，并有对应的自动判定脚本。
6. 灰度按会话或租户分桶。判据：抽同一会话的十条请求，版本标签一致；分桶键在日志里可见。
7. 回滚演练过。判据：最近一次回滚在分钟级完成，且旧索引、旧模型仍可调用；演练记录里有耗时。
8. 版本保留满足回滚目标。判据：保留策略写明 N-2 或按时间，抽查两代前的索引与模型仍可用。

清单本身也要版本化，归档时连同勾选结果与例外项一起存，复盘才能回答“当时检查了什么”。

## 七、常见误区与面试追问

**问一：提示词放在平台上管理，不进代码仓库，行不行？**
行，但前提是平台提供不可变版本与导出能力。风险在于平台上的“最新版”是浮动指针，一旦有人编辑，线上行为就变了，而仓库里没有任何痕迹。可行做法是平台只做编辑与评审，发布时把具体版本导入仓库清单，仓库清单是唯一事实来源。

**问二：模型锁到日期版本，供应商下线了怎么办？**
锁定不等于永久可用，需要一条“退役路径”：盯供应商的弃用公告，提前在影子跑里验证替代版本。真正的风险是公告被忽略，某天调用直接报错。因此清单里应记录每个组件的“最后可用日期”，到期前必须有人处理。

**问三：版本号打在请求上、会话上还是租户上？**
三者都要，用途不同。请求级标签用于排查单次故障；会话级保证同一会话行为一致；租户级用于灰度与合同约定。只打请求级，会出现同一会话前后两个版本、用户感知到“人格分裂”的问题。

**问四：有了配置中心，发布清单是不是重复建设？**
不重复，职责不同。配置中心管“值怎么下发、怎么变更”，清单管“这次发布用的是哪一组不可变的值”。前者要动态性，后者要可复现性，目标相反，必须同时存在。判断标准：能否用清单重建两周前的环境。不能，就还需要清单。

**问五：灰度的比例和时间怎么定？**
没有通用答案，但有一条硬规则：先看指标再看比例。小流量阶段观察错误率与人工接管率这类“坏结果”指标，稳定后再扩量观察质量指标。时间上至少覆盖一个业务周期，否则可能错过只在特定时段出现的输入分布。扩大比例要有人签字，依据是差异报告而不是感觉。

## 八、小结与延伸阅读

Agent 的可复现性，不取决于某一个部件管得多细，而取决于提示、工具 schema、模型参数、检索配置与运行时策略是否作为一个单元发布、校验、灰度与回滚。版本单元是复现的最小单位，发布清单是它的可执行形态。

判断清单是否有效，有个很朴素的测试：随便改错其中一个值，系统会不会拒绝启动。会，说明它是契约；不会，它只是文档。

延伸阅读建议：官方文档类可看模型厂商的版本锁定与弃用说明；工程博客类可看配置即代码的实践；标准规范类可看语义化版本的定义，重点理解“不兼容变更”的判定。
